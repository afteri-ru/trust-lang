## Пространства имён

*TrustLang* поддерживает пространства имён; разделитель, как и в C++, — двойное двоеточие `::`.
Область имён может быть указана как для отдельного идентификатора, так и для целого
[блока кода](concept/#block).

В отличие от `namespace` в C++, области имён в *TrustLang* служат не только для организации кода
логическими группами и избежания конфликтов имён: имя, в котором явно указана область имён, относится
к **статическим** объектам (память под которые выделяется на этапе компиляции).

Глобальное имя не может быть перекрыто макросом или локальной переменной при
[разрешении имён (name lookup)](naming/#name-lookup). Чтобы создать глобальную (статическую)
переменную, достаточно записать её имя с глобальным квалификатором `::var`. Пространство имён для
блока кода указывают перед открывающей фигурной скобкой (`ns:: { ... };`).

```
::var := 0;    # глобальная переменная (не перекрывается макросом/локальной)

ns:: {          # область имён ns
    a:Int32 := 2;   # ns::a
    sub:: {         # вложенная область имён
        c:Int32 := 3;   # ns::sub::c
    };
};
```

## Модули и группы

*TrustLang* организует исходный текст в **файлы**, объединённые в **группы** (каталоги), и
**пакеты-архивы**. Разделитель пути — обратная косая черта `\`; точка в этой роли не используется.

**Файл** — единица исходного текста (`.src`), AST, семантики, импорта и интерфейса.
**Группа** — каталог первого уровня в проекте или пакете, группирующий файлы. Группа не является
единицей AST/семантики и не создаёт собственного пространства имён: это путь и принадлежность файла.
**Пакет** — один архив `.trust` с манифестом `trust.toml`; единица дистрибуции. Пакет не содержит
импортируемых вложенных пакетов: `.trust` внутри пакета — обычный файл/ресурс.
**Программа** — входной файл; может не иметь заголовка.

Имена компонентов пути — только строчные латинские буквы, цифры и `_`; `_` не может начинать или
завершать компонент. Ограничение связано с прямым отображением имён на файловую систему.

### Терминология файлов, групп и импорта {#module-terms}

- **Файл** — идентифицируется **логическим путём** (относительно корня проекта или пакета), а не
  заголовком и не абсолютным путём кэша. Заголовок (если есть) обязан совпадать с этим путём и
  именем файла: это контроль состава пакета.
- **Группа** — каталог-группировка; не единица AST/семантики. Импорт всегда адресует **файл** или
  **группу файлов**; «импортировать группу как объект» нельзя.
- **Импорт файла** — `path()`; **импорт группы** — `dir-path()`: разворачивается в импорт всех
  `.src` **непосредственно** в каталоге (нерекурсивно). Для подкаталога — отдельный `dir-path()`.
- **Заголовок** — первая значимая строка `path;` (пропуская BOM, shebang, `#`-комментарии и
  `/* */`). Заголовок статичен: макроподстановка в него не применяется; в AST он не входит.
- **Интерфейс файла** — экспортируемые идентификаторы и их объявления; его можно задать явно
  блоком в заголовке (см. [Интерфейс файла](#file-interface)). Маски задают набор ВИДИМЫХ имён.
- **Исходная форма** — обычный `.src`; **скомпилированная форма** — тот же `.src`, где вместо тел
  стоят предварительные объявления и native-импорты.

### Префиксы путей и заголовок {#roots}

Тип префикса задаётся **только в первой позиции**; все последующие разделители — одиночный `\`.

| Префикс | Первый компонент | Пример файла | Смысл |
|---|---|---|---|
| `\` | файл | `\hello` | файл в корне проекта |
| `\\` | группа | `\\util\string` | файл в группе `util` |
| `\\\` | пакет | `\\\tensor\tensor` | файл в пакете `tensor` |

Формы путей:

- `\file` — файл в корне проекта;
- `\\group\file` — файл в группе; `\\group\dir\file` — файл в подкаталоге группы;
- `\\\pkg\file` — корневой файл пакета; `\\\pkg\group\file` — файл в группе пакета.

Заголовок файла совпадает с его логическим путём:

| Файл | Заголовок |
|---|---|
| `hello.src` в корне проекта | `\hello;` |
| `util/string.src` | `\\util\string;` |
| `tensor/tensor.src` в пакете `tensor` | `\\\tensor\tensor;` |
| `tensor/math/matrix.src` | `\\\tensor\math\matrix;` |

Заголовок обязателен для импортируемых файлов, файлов групп и пакетов. Он опционален только для
**корневой программы** (`\file`); программа в группе/пакете обязана иметь заголовок. Импорт файла
без заголовка — ошибка.

`@__MODULE_NAME__` вычисляется из логического пути файла: **тип scope входит в имя** — `m_`
для файла группы, `p_` для файла пакета; разделитель `\` кодируется как `_`. Для **составных**
путей символ `_` дополнительно кодируется как `__` (`\\util\open_file` → `m_util_open__file`,
`\\\tensor\math\matrix` → `p_tensor_math_matrix`), поэтому `\\a\b_c` (`m_a_b__c`) и
`\\a_b\c` (`m_a__b_c`) различимы, а проектный `\\a\b` (`m_a_b`) не совпадает с пакетным
`\\\a\b` (`p_a_b`). Однокомпонентное имя (stem программы или `\file`) остаётся как есть; если
два РАЗНЫХ пути дают одно производное имя, компилятор сообщает ошибку.

Кодированное имя модуля (`m_util_open__file`) служит **именем заголовка модуля** (`<enc>.hpp`) и
базой имени entry-функции (`<enc>__main__`) — это структурная согласованность артефактов сборки.
В **ABI символов** имя модуля НЕ входит: C++-имя сущности выводится только из её области имён
(`ns::f` → `ns::f`, `MyStr.count` → `MyStr::count`), поэтому модуль прозрачен относительно C++
(как translation unit). Изоляцию одноимённых экспортов разных модулей обеспечивает программист
обычными областями имён (`a:: { ... }`); без неё одноимённые определения дают `multiple
definition` — компилятор диагностирует коллизию раньше линкера. Вне областей остаются
entry-функция (`<модуль>__main__`) и top-level C++-вставки `{% %}`. Headerless root-программа не
импортируется: ссылаться на её символы некому.

### Интерфейс файла {#file-interface}

Экспортируемый набор файла можно задать явно — блоком в заголовке:

```
\lib {
    f(x:Int32):Int32 := ...;      # объявлено здесь, определено в теле
    counter:Int32 := ...;         # то же для переменной
    :Point ::= :Struct{ x:Int32 := _; };   # публичный тип — полное определение здесь
};
```

Правила:

- блок — часть **первой значимой конструкции** файла (после пути заголовка), заканчивается `};`;
- в **экспорт-набор файла** (маски импорта и forward-declarations) входят только объявления из
  блока; остальные top-level объявления **не входят в него**: они не видны импортёру, регистрируются
  под module-qualified ключом и эмитятся в C++ anonymous namespace (одноимённые приватные имена
  разных файлов не конфликтуют). Определение типа, завершающее forward из интерфейса, — реализация
  владельца: клиенту не публикуется;
- объявление **функции/переменной** с `...` **обязано** быть определено в этом же файле (иначе —
  ошибка компиляции); `...` означает «предварительное объявление», `_` — «не инициализировано»
  (в интерфейсе не используется);
- объявление **типа** с `...` (forward) — обычное предварительное объявление: имя экспортируется,
  представления типа в этой точке нет. Полное определение типа задаётся определением в блоке
  интерфейса (`:T ::= :Struct{...};`) — тогда клиент использует тип по значению. Определение в
  теле за forward'ом интерфейса — реализация владельца: клиенту оно не публикуется, тип остаётся
  неполным (доступны невладеющие ссылки `ptr`/`ref`; по значению — ошибка компиляции);
- **неполный тип для клиента — это forward в экспорт-наборе**, а не отдельный маркер. Полное
  определение типа прямо в блоке интерфейса делает тип полным. Внешний C/C++-тип описывается
  native class forward (`T ::= %cpp_name { };` + `@[include]`);
- внутри блока разрешены области имён (`ns:: { ... }`), атрибуты (`@[...@]`) и **операторы загрузки
  с круглыми скобками** (`\lib(a, b);`) — такой импорт означает **реэкспорт**: отфильтрованный
  масками набор имён входит в экспорт-набор этого файла (владелец имён не меняется, в заголовок
  файла попадают `#include` заголовков этих модулей). Реэкспорт **транзитивен**: фасад может
  реэкспортировать имена другого фасада — владельцем по-прежнему остаётся исходный файл. Здесь же
  задаются **алиасы функций**
  (`f :- g;`, см. [Алиасы имени](#func-alias)) — курирование фасада: клиент видит новое имя;
  оператор загрузки-реэкспорта допускается **только на верхнем уровне** блока интерфейса; импорт
  внутри вложенной namespace-области (`ns:: { \lib(f); };`) — ошибка (qualified-семантика
  реэкспорта не определена). Непубличные области (`__::` — private, `_::`/`_{...}` — protected) запрещены на любой глубине, а
  `\path;` без скобок — не загрузка. Из макросов допустимы
  только определённые вне модулей (DSL/ключевые слова): интерфейс не должен зависеть от того, кто
  импортирует файл, поэтому макрос, определённый в модуле (в т.ч. унаследованный от импортёра),
  в блоке интерфейса — ошибка компиляции;
- entry-функция (`@main`) и системные имена в интерфейсе не нуждаются;
- файл без блока: экспортируются все top-level объявления.

### Импорт файлов и групп {#import}

- `\path()` — импорт одного файла; маски фильтруют экспорт этого файла.
- Скобки **обязательны**: голая первая значимая строка `\path;` — это заголовок файла (см. выше),
  а не импорт.
- `\\group()` / `\\group\dir()` — импорт всех `.src` **непосредственно** в каталоге (нерекурсивно);
  для подкаталога нужен отдельный `\\group\dir()`.
- `\\\pkg()` — группы первого уровня (их `.src` непосредственно) плюс корневые `.src` пакета.
- Порядок обхода группы — лексикографический; пустая группа — ошибка; маски группы применяются к
  объединённому экспорту.
- Если существует `dir.src` — импорт файла; иначе, если существует каталог `dir/` — импорт группы;
  если существуют оба — ошибка неоднозначности. Для явно группового пути `\\dir()` файл `dir.src`
  недопустим: ожидается каталог (иначе — ошибка «module directory expected»).
- Импорт **позиционен**: имя видно только после оператора импорта (семантика однопроходна —
  объявление до использования). Импорт допустим в любом блоке и действует в текущем скоупе.
  Импорты не поднимаются к началу блока: ставьте их до первого использования импортируемых имён.
- **Циклическая зависимость файлов — ошибка компиляции** (с цепочкой импорта в диагностике).
- **Маски импорта** — список через запятую; `*` — любая (в т.ч. пустая) последовательность, `?` —
  ровно один символ. Маска с `::` сравнивается с полным trust-именем (`ns::f`), маска без `::` — с
  коротким (`f`, `*`). Пустой список масок означает «все имена». Имя, не совпавшее ни с одним
  экспортом, даёт диагностику `-Wunmatched-mask` (по умолчанию предупреждение; `-Wunmatched-mask=error` —
  ошибка), а импорт, не принёсший ни одного имени, — диагностику `-Wempty-import`;
  непроэкспортированные имена в интерфейс не входят.
- **Маски группового/пакетного импорта применяются к объединённому экспорт-набору сайта:** маска
  считается совпавшей, если имя нашлось хотя бы в одном файле группы. `-Wunmatched-mask`
  сообщается только для маски, не совпавшей ни в одном файле.

### Принципы загрузки файлов {#module-loading}

- **Один разбор и одна конверсия:** AST файла конвертируется ровно один раз
  (`ModuleRegistry::m_bodyAst`); все сайты импорта и `.cppt` файла используют те же узлы.
- **Один семантический прогон:** `.cppt` файла — codegen-проекция уже проанализированных фактов.
- **Повторный импорт:** загрузка файла идемпотентна (файл читается и анализируется один раз).
  `duplicate-import` — ошибка только при том же файле, том же scope и тех же нормализованных масках;
  разные маски или разные scope допустимы. Severity настраивается (`-Wduplicate-import`), по умолчанию
  Error; на один сайт импорта выдаётся ОДНО сообщение (в т.ч. для группы файлов). Загрузка сама по
  себе не диагностируется.
- **Поиск файлов проекта:** `\`/`\\` разрешаются от корня проекта (`--module-root`; по умолчанию —
  каталог входного файла) и от дополнительных корней `-I` в порядке указания. Файл, найденный в
  корне `-I`, получает этот корень как свою область: относительные пути **внутри него** считаются
  от этого корня.
- **Поиск пакетов:** `\\\pkg` ищется в путях: локальный пакет в области импортёра, `--package-path`,
  `TRUST_PACKAGE_PATH`, встроенный каталог `share/trust` (`TRUST_RESOURCE_DIR` перекрывает его),
  текущий каталог. Если пакет найден в нескольких местах разными архивами/каталогами — ошибка, а не
  «первый победил».
- **Build-каталог не является корнем поиска** ни для файлов проекта, ни для пакетов.
- **Файл не является namespace-сегментом:** namespace задаётся явно (`::`/`name::`); файл участвует
  в идентичности private-имён и C++-компоновке, но **объявления не наследуют имя файла**.
- **Импорт не транзитивен:** имена, импортированные самим файлом, не попадают в скоуп его
  импортёра. Импорт фильтрует ВИДИМОСТЬ имён, а не анализ: тела функций импортированного файла
  продолжают видеть все свои объявления.
- **Дубли:** внутри файла — всегда ошибка; одноимённые экспорты разных файлов сосуществуют, а
  голое имя становится неоднозначным (диагностика на сайте использования); private-имена не
  конфликтуют; повторная регистрация того же объявления того же файла — не дубль.

### Диагностики определения и загрузки модулей {#module-diagnostics}

Определение модуля начинается с первой значимой конструкции файла — `<path>;` (без интерфейса)
или `<path> { … };` (блок интерфейса). Загрузка — оператор `<path>(...)` (круглые скобки, как
вызов функции). Число ведущих `\` задаёт тип пути (`\` — файл, `\\` — группа, `\\\` — пакет) и
одинаково в заголовке и в операторе загрузки; `\std();` — загрузка файла-зонтика стандартной
библиотеки.

| Ситуация | Диагностика |
|---|---|
| У импортируемого файла нет заголовка | `module file '…' has no module header; expected '<path>;' as the first significant line` |
| Заголовок не совпадает с логическим путём | `module header '…' does not match path (expected '…')` |
| Невалидное имя в заголовке | `invalid module header '…'` |
| Путь не выражается от корня области | `cannot compute module path relative to scope root '…'` |
| Заголовок начат, но не завершён `;` | `module header must end with ';'` |
| Заголовок не завершён | `unterminated module header` |
| Невалидное имя модуля в операторе | `Module name - backslash, underscore, lowercase English letters or number!` |
| Загрузка не дала ни одного файла | `Module '…' resolved to no files` |
| Групповой путь в квалифицированной ссылке | `Module reference '…' must name one file: a group import cannot be used in a qualified name` |
| Ссылка на незагруженный модуль | `Module '…' is not loaded` |
| Файл/пакет не найден (fatal) | `Module '…' not found: …` |
| Цикл импорта (fatal) | `Cyclic module dependency detected: …` |
| Файловый путь с подпутём / каталог без `\\` | `file path cannot have subpaths; use a module path (two leading backslashes)` / `directory import requires a module path (two leading backslashes)` |

### Вывод зависимостей файлов {#module-deps}

`trust --emit-module-deps <входной файл>` печатает граф файловых зависимостей правилами make
(`<target>: <deps>`): правило `.cppt` входного файла и правило артефактов каждого модуля
(`.hpp`, `.cppt` при наличии out-of-line определений). Зависимости транзитивны: заголовок модуля
подключает заголовки своих импортов, поэтому артефакт зависит от ВСЕХ источников и заголовков
компиляции, а также от использованных архивов пакетов (иначе изменение интерфейса глубокого
модуля даёт stale build). Пути — относительные от текущего каталога; вывод пригоден для включения
в Makefile.

### Скомпилированная форма файла {#module-compiled}

Скомпилированная форма файла — это **тот же исходный текст** (`.src`), в котором вместо тел
объявлений стоят предварительные объявления (`f(...):Int32 := ...;`) и native-импорты
(`name(...) := %sym...;`). Отдельного вида загрузки нет: загрузчик, парсер, конвертер и семантика
работают с ней так же, как с исходной формой, C++-прототипы и определения типов публикует сгенерированный заголовок модуля (см.
[Заголовок модуля](#module-header)); сайт импорта содержит только `#include` этого заголовка
(`@[include(\...\)]`/`@[link(\...\)]` собираются там же).

Ограничения формы:

- generic-функции/операторы требуют тела (C++ `template`) и в declaration-only форме не представимы:
  exported generic без тела **и без определения в этом же модуле** — ошибка компиляции Trust
  (сравнение квалифицированного имени и C++-суффикса сигнатуры): заголовок обязан содержать тело;
- native-декларации должны нести `@[include(\...\)]`/`@[link(\...\)]` — иначе TU импортёра не соберётся;
- имена в интерфейсном тексте должны быть квалифицированы (`ns::Type`), чтобы не зависеть от импортов.

Файл без определений (только объявления и native-импорты) не создаёт собственной единицы трансляции:
его интерфейс публикует заголовок `.hpp`, поэтому `.cppt` для него не генерируется (заголовок при
этом генерируется — см. ниже).

### Заголовок модуля (`<enc>.hpp`) {#module-header}

Для каждого импортируемого файла компилятор генерирует C++-заголовок с именем
`<кодированное имя>.hpp` (см. «Префиксы путей и заголовок»). Содержимое — **экспорт-набор файла**
(без автоматического namespace модуля): объявления экспортных типов (forward или полное определение — как в
экспорт-наборе), прототипы функций, `extern`-переменные;
первая строка — `#pragma once`. Нативные декларации и entry остаются вне обёрток
(квалифицированное внешнее имя / глобальный символ). Заголовок самодостаточен (компилируется как
отдельная единица трансляции), позиции объявлений для отладки/переходов остаются в `.cppt` модуля.

- **Заголовок публикует ровно экспорт-набор:** forward в интерфейсе остаётся предварительным
  объявлением (клиент видит неполный тип), полное определение в интерфейсе публикуется полностью.
  Определение типа из тела за forward'ом интерфейса в заголовок не попадает — это реализация
  владельца (эмитится в его `.cppt`).
- **Неполный тип:** клиенту доступны только невладеющие ссылки (`ptr`/`ref`; владеющая `unique`
  требует полного типа). Проверка полноты действует и при **выводе типа** (`h := make();`):
  полнота определяется по объявлению callee (его возвращаемому типу), а не только по явной
  аннотации переменной.
- **Клиент включает заголовок:** на месте оператора импорта C++-код содержит `#include "<enc>.hpp"`;
  единица трансляции модуля тоже начинается с `#include` своего заголовка и не повторяет
  опубликованные определения.
- **Реэкспорт (фасад):** импорт внутри блока интерфейса (`\lib(a, b);`) публикует имена владельца;
  заголовок фасада — umbrella: `#pragma once` + `#include "<enc владельца>.hpp"`. Если в блоке
  интерфейса фасада нет собственных объявлений, других объявлений в заголовке нет; иначе к
  `#include` добавляются собственные объявления фасада. Владелец имени не меняется — определение
  и C++-символ остаются у него. Namespace-алиас по области действует в пределах объявившего модуля и
  **не экспортируется** импортёрам (реэкспорт namespace-алиасов не поддерживается).
- **Тела generic/constexpr free-функций попадают в заголовок:** exported generic (`<T> f(...)`)
  и `@[constexpr]` free-функция публикуются определением, поэтому клиент инстанцирует/использует
  их из другого модуля; `.cppt` эти тела не повторяет. Ссылка такого тела на `__::`-хелпер —
  Trust-диагностика (в заголовке он невыразим).
- Заголовок получает **каждый** импортируемый файл, включая declaration-only (у которого `.cppt`
  нет). Headerless root-программа заголовка не имеет.
- Граф зависимостей (`--emit-module-deps`) содержит правило и для заголовка. Зависимости
  **консервативны**: правило заголовка ссылается на все исходники, заголовки и архивы пакетов
  компиляции, а не только на прямые импорты модуля (иначе изменение интерфейса глубокого модуля
  могло бы дать stale build).

Предкомпилированная форма (бинарный интерфейс файла) в текущей версии **не поддерживается**: интерфейс
файла — только исходный текст. Возможное направление развития — представить скомпилированный файл как
нативную библиотеку с устойчивым именем и импортировать его существующим механизмом native-деклараций;
отдельного ABI-контракта файлов язык не вводит. Границы реализации — в [Статусе](../status/).

### Алиасы имени (`f :- g;`) {#func-alias}

Различие объявления, предварительного объявления, нативной привязки и алиаса сведено в таблицу
[Объявление, определение и алиас](../operators/create/#declaration-vs-alias): `:=` **никогда** не
создаёт алиас.

Алиас — **новое имя существующей функции или значения/константы** (курирование фасада): клиент
работает с коротким именем (`f`), тогда как реализация и C++-символ остаются у модуля-владельца.
Оператор `:-` объявляет алиас в блоке интерфейса файла; в файле без блока интерфейса — в теле
(там действует default-public):

```trust-lang
\facade {
    \lib(g);
    f :- g;
};
```

- Для функции алиас связывается с **набором перегрузок** цели: выбор сигнатуры выполняется при
  вызове по аргументам, как у обычной перегрузки; типы и реализация — цели. Для значения/константы
  алиас — второе имя того же места хранения: чтение и запись нормализуются на цель.
- Собственная C++-функция для алиаса **не эмитится**: в сгенерированном коде вызов печатается
  C++-именем цели вместе с её identity-суффиксом (`g_P10N5_3AInt32_(1)`). Заголовок файла
  включает заголовок владельца цели (umbrella `#include`).
- Имя-алиас входит в экспорт-набор файла (клиент видит его коротко — `f`), если объявлено в
  блоке интерфейса или в файле **без** блока интерфейса. В теле
  файла **с** блоком интерфейса алиас, как и прочие объявления вне блока, файл-приватен и
  импортёру не виден.
- Правая часть — имя ЦЕЛИ, введённое импортом этого файла (`f :- g;` после `\lib(g)`); ссылка
  на неразрешённое имя — ошибка. Форма с подписью (`f(x:Int32):Int32 :- g;`)
  не поддерживается; для типа используется `::-`, а не `:-` (явная диагностика).
- Ключевое слово `alias` — та же операция в стиле `import … as …`: `alias g as f;`
  (имя) и `alias T as :MyT;` (второе имя типа, см. ниже). Вид определяется `:` у нового имени.

### Алиасы типов (`:A ::- T;`) {#type-alias}

`::-` объявляет **второе имя уже существующего типа** — тот же `TypeId`, что у цели (номинальный
тип не создаётся). Форма работает и для межмодульной цели:

```trust-lang
:MyInt ::- :Int32;
:MyPoint ::- Point;
```

Эквивалентная запись через ключевое слово `alias`: `alias Point as :MyPoint;`.

C++-тип не эмитится: аннотации и конструктор через имя-алиас печатаются именем цели. Новый
номинальный тип объявляется оператором `::=` (см. [Создание объектов](../../operators/create/)).

Границы реализации — в [Статусе](../status/).

### Видимость имён {#visibility}

- **Top-level объявления файла — экспортируются** (default-public): идентичность имени в КОМПИЛЯТОРЕ
  включает модуль (разные модули различимы), но в C++-символ модуль не входит. **Имя модуля —
  НЕ префикс разрешения** (`\модуль::имя` запрещено): имя вводится импортом; голое имя после
  импорта нескольких модулей с одинаковым экспортом неоднозначно — экспорты разводят областями имён.
- **`_:: { ... }` / `_{ ... }` на top-level файла — protected**: видны текущему файлу и файлам
  той же группы проекта или того же пакета; внешним импортёрам не экспортируются. В C++ текущего
  бэкенда эмитятся плоско (module-level), видимость обеспечивает семантика Trust.
- **`__:: { ... }` / `__{ ... }` на top-level файла — private**: видны только текущему файлу;
  в C++ эмитятся в anonymous namespace (internal linkage).
- **`:: { ... }` / `name:: { ... }`** — экспортируемые области имён. Их объявления имеют
  статическое время жизни: после выхода из блока они доступны квалифицированно (`name::f`),
  а содержимое `::` — без квалификации. В C++ эмитятся как namespace с тем же именем, вызов
  `name::f` → `name::f`. Модуль автоматического namespace НЕ создаёт: одноимённые экспорты
  разных модулей без общей области имён дают `multiple definition` (диагностируется компилятором).
- Внутри одного файла дубликаты запрещены всегда. Private-имена разных файлов не конфликтуют
  (идентичность включает файл); экспортируемые — конкурируют.
- **Те же маркеры задают вариант наследования** в списке родительских классов
  (`:D ::= __::, :A, ::, :B{ }`): маркер — standalone-элемент списка, действующий на все
  последующие базы до нового переключения; дефолт — public для всех типов
  (private/protected — только явным маркером). См. [Классы](../types/class/#inheritance-access).
- **Те же маркеры задают C++-доступ методов и полей** в теле класса (`__::;` / `_::;` / `::;`):
  standalone-член, действующий на все последующие члены; дефолт — public.
  См. [Классы](../types/class/#member-visibility).

### Границы алиасов и импорта {#alias-limits}

- **Импорт позиционен** (см. выше) — он не поднимается к началу блока, в отличие от большинства
  языков; импорт действует на текущий скоуп.
- **Цепочек алиасов нет:** имя-алиас на имя-алиас нормализуется на КОНЕЧНУЮ цель;
  namespace-алиас, целью которого служит другой namespace-алиас (в т.ч. экспортированный
  фасадом), не поддерживается — цель обязана быть областью имён модуля.
- **Отрицающих масок нет:** маска только выбирает видимые имена (`*`, `?`), исключение не выражается.
- **Гранулярность видимости — три уровня:** файл (`__::`), группа/пакет (`_::`), экспорт файла;
  промежуточной гранулярности (как `pub(in path)`) нет.


## Пакеты {#package}

Манифест пакета — единственный файл с информацией о пакете — `trust.toml` в корне каталога
(его наличие и есть признак пакета). Формат файла — TOML. Обязательное поле — `name`;
дополнительно допускаются `description`, `authors`, `license`, `module-root`, `[[layout.layers]]`,
`[[artifact]]` и `[[link.headers]]`. Декларация зависимостей (`dependencies`) в текущей версии
не поддерживается — см. [Статус](../status/).

Пакет всегда **один**: архив не содержит импортируемых вложенных пакетов. `.trust` внутри пакета —
обычный файл/ресурс, а не вложенный пакет. Если пакету нужен другой пакет, он подключается отдельно
через пути поиска, а не рекурсивной упаковкой. `module-root` задаёт корень, относительно
которого вычисляются заголовки файлов пакета (по умолчанию — корень архива).

Поле `version` — **semver самого пакета**, не версия компилятора. Упаковщик сохраняет авторскую
версию; если в исходном `trust.toml` её нет, в манифест архива подставляется версия компилятора
(`TRUST_VERSION_SHORT`) как provenance. Версия компилятора, которым собран пакет, фиксируется
отдельно — в `[build].toolchain`. Совпадение версии пакета с версией компилятора не требуется:
пакет версии `1.2.3` можно собрать любым компилятором.

Пример манифеста:

```toml
name = "demo"
description = "Демонстрационный пакет"
```

### Создание пакета {#pack-create}

Пакет создаёт компилятор:

```
trust --package <каталог> [-o <файл>.trust]
```

По умолчанию упаковывается всё дерево каталога (исходники `*.src`, C++-заголовки, прочие
файлы, а также `*.trust`-файлы как обычные файлы — они не становятся импортируемыми вложенными
пакетами); build-артефакты (`.trust/`, `*.cppt`, `*.src_map`, `*.o`, `*.so`, `app`) исключаются.

Если пакет должен содержать не всё дерево (или файлы берутся из разных каталогов), раскладка
описывается **в самом манифесте** — таблицами `[[layout.layers]]`:

```toml
name = "demo"

# Исходники: каталог манифеста, рекурсивно; в пакет идут только *.src
[[layout.layers]]
source-dir = "."
archive-dir = "src"
patterns = ["*.src"]

# Заголовки: подкаталог inc; попадут в include/demo/ с сохранением структуры
[[layout.layers]]
source-dir = "inc"
archive-dir = "include/demo"
patterns = ["*.hpp"]
```

| поле | смысл |
|---|---|
| `source-dir` | каталог-источник относительно каталога манифеста (по умолчанию `.`); обходится **рекурсивно** (подкаталоги входят автоматически) |
| `archive-dir` | каталог внутри архива (по умолчанию `.`); относительный путь файла от `source-dir` сохраняется |
| `patterns` | glob-маски **имён файлов** (`*`, `?`); файлы, не совпавшие ни с одной маской, в пакет не входят |

Ошибкой (без fallback) считаются: несуществующий каталог `source-dir`, абсолютный `archive-dir`
или `archive-dir` с `..`, пустой/невалидный `patterns`, слой без единого подходящего файла, а
также явно пустой список слоёв и два слоя, дающих один и тот же путь в архиве.

В архив кладётся копия манифеста с полем `version` (авторская версия пакета; при отсутствии —
версия компилятора как provenance) и автоматически добавленными таблицами `[build]`
(`formatVersion`, `toolchain` — версия компилятора, `created` — дата/время) и `[files]`
(MD5 каждого файла); исходный `trust.toml` при этом не изменяется. По умолчанию архив
называется `<name>.trust`.

### Артефакты провайдера {#pack-artifact}

Пакет может описывать **контракт линковки** с нативной библиотекой. Это не список файлов, а
правила: как логическое имя библиотеки превращается в `-l`/`-L` и какие include-каталоги нужны.
Пакет сам по себе **не добавляет link-опции** — линковка появляется только при реальном
использовании (`@[link("...")]` или `[[link.headers]]`).

```toml
name = "native_async"

[[layout.layers]]
patterns = ["*.src"]

[[layout.layers]]
source-dir = "include"
archive-dir = "include"
patterns = ["*.hpp"]

[[layout.layers]]
source-dir = "lib"
archive-dir = "lib"
patterns = ["*.cpp", "*.hpp"]

[[artifact]]
provides = ["native_async"]  # логическое имя для @[link("native_async")]
kind = "source"              # source | package | toolchain | system
sources = ["lib/thread_pool.cpp", "lib/async_mutex.cpp"]
link-options = ["-pthread"]

# Потребность САМОГО артефакта: подключается транзитивно при его линковке.
[[artifact]]
provides = ["trust-runtime"]
kind = "toolchain"
libs = ["trust-runtime"]
requires = ["gmp"]

# Потребность: используемый заголовок -> логические библиотеки.
[[link.headers]]
header = "trust/rational.hpp"
libs = ["trust-runtime"]
```

| `kind` | смысл |
|---|---|
| `source` | исходники `sources` лежат **в пакете** и компилируются компилятором приложения в `libtrust_third_party.a`; `libs` запрещены |
| `package` | файлы библиотек лежат **внутри пакета**; `libs` — относительные пути (например `lib/libfoo.a`) |
| `toolchain` | библиотека предоставляется toolchain и ищется рядом с `trust`, в `lib/`, `../lib/`, `LD_LIBRARY_PATH`; `libs` — логические имена (`-l<name>`) |
| `system` | системная библиотека линковщика (`-l<name>`), путь ищет линковщик |

Обязательные поля: `kind`, `provides`; для `source` — `sources`, для остальных — `libs`.
Дополнительные: `link-options` (например `-pthread`; для `source` попадают и в компиляцию, и в
линковку), `capabilities` (например `with-torch`; отсутствие — диагностика до линковки) и
`requires` (логические библиотеки, нужные **самому** артефакту: подключаются транзитивно при его
линковке; ссылка на собственный `provides` — ошибка).
Заголовки провайдера всегда лежат в `include/` пакета (этот путь добавляется автоматически);
отдельных include-полей у артефакта нет. Имя из `provides` должно быть уникальным среди
используемых пакетов; коллизия — ошибка.

`trust-runtime` и `gmp` — такие же артефакты, как `tensor_cpu`/`pthread`. В пакете стандартной
библиотеки `trust-runtime` объявлен как `kind="toolchain"` с `requires = ["gmp"]`: архив
`trust-runtime.a` содержит объекты, собранные с GMP, поэтому `-lgmp` нужен при **любой** линковке
runtime, а не только при использовании `BigInteger`/`Rational`. Правила `[[link.headers]]` поэтому
перечисляют только `trust-runtime`, а `gmp` приходит через `requires`. Программа без
runtime-заголовков (обычный hello world) по-прежнему **не линкует** `trust-runtime`.

### Распаковка пакета {#pack-extract}

Пакет распаковывает компилятор:

```
trust --extract <файл>.trust [-o <каталог>]
```

Записи архива проверяются на выход за пределы каталога назначения (защита от path traversal), а
манифест `trust.toml` из архива разбирается и валидируется. Если `-o` не задан, распаковка идёт в
подкаталог `<name>/` (имя из манифеста) текущего каталога.

### Просмотр пакета как каталога {#pack-view}

Пакет `.trust` — обычный архив gzip-compressed tar, поэтому его содержимое открывается любым
архиватором (`tar`, 7-Zip, ark и т. п.). В файловом менеджере Midnight Commander архив можно
открывать как каталог прямо в панели, добавив правило в файл расширений `~/.config/mc/mc.ext.ini`
(он создаётся копированием системного `/etc/mc/mc.ext.ini` по команде `F9` → Command → Edit
extension file):

```ini
[trust]
Shell=.trust
ShellIgnoreCase=true
Include=tar.gz
```

После сохранения файла (или перезапуска mc) нажатие Enter на файле `<name>.trust` входит внутрь
архива как в каталог. Секция `Include=tar.gz` переиспользует встроенную в mc обработку tar-архивов;
правило по имени `.trust` должно находиться выше секции `[gzip]` (секции сопоставляются сверху вниз).

### Подключение пакета при компиляции {#pack-use}

Компилятор загружает исходники не только из отдельных `*.src`, но и из пакетов `.trust`. Пакет
адресуется префиксом `\\\`: `\\\pkg\file` — корневой файл пакета, `\\\pkg\group\file` — файл группы
пакета. Пакет распаковывается компилятором во временный build-каталог
(`<build-dir>/packages/<name>-<md5(archive)[0..12]>/`), а не в дерево исходников пакета, и файлы грузятся
оттуда как обычные исходники. Внутри пакета пути `\`/`\\` разрешаются от **корня пакета**
(`module-root` манифеста), а не от проекта; для другого пакета используется `\\\other\...`.

Пути поиска пакетов (в порядке проверки): локальный пакет в области импортёра, затем `--package-path`,
затем `TRUST_PACKAGE_PATH`, затем встроенный каталог `share/trust` (`TRUST_RESOURCE_DIR` перекрывает
его) и текущий каталог. Если пакет найден в нескольких корнях разными архивами — это ошибка, а не
«первый победил».

Если пакет объявляет `[[artifact]]`, его include-каталоги добавляются к сборке, а link-опции —
**только при наличии потребности** (`@[link("...")]` на использованной декларации или
`[[link.headers]]` для использованного заголовка). Извлечение пакета само по себе link-опции не
добавляет.

Все файлы пакета доступны компилятору: каталог распакованного пакета и его подкаталог `include/`
добавляются к путям поиска заголовков при сборке сгенерированного C++ (`-Ipackages/<name>` и
`-Ipackages/<name>/include`). Поэтому C++-заголовки пакета рекомендуется размещать в `include/`:
они подключаются через `@[include("header.hpp")@]` / `#include <header.hpp>` без копирования в
build-каталог.

При создании пакета в копию манифеста добавляется таблица `[files]` — контрольные суммы (MD5) каждого
файла (кроме самого `trust.toml`). При распаковке компилятор сверяет содержимое с `[files]`:
несовпадение, отсутствие или лишний файл — ошибка; отсутствие самой таблицы `[files]` (нет данных о
целостности) — тоже ошибка. Это контроль целостности (защита от повреждения и подмены), а не проверка
подписи издателя: подпись пакетов и разрешение версий в текущей версии не реализованы — см.
[Статус](../status/).


### Параметры пакета (сводка) {#pack-params}

| Параметр / опция | Где задаётся | Назначение |
|---|---|---|
| `name` | `trust.toml` | обязательное имя пакета (строчные латинские буквы, цифры, `_`) |
| `description`, `authors`, `license` | `trust.toml` | необязательные информационные метаданные |
| `version` | `trust.toml` (необязательно) | semver пакета; упаковщик сохраняет авторскую версию (при отсутствии подставляет версию компилятора как provenance); версия toolchain — `[build].toolchain` |
| `module-root` | `trust.toml` | корень для заголовков файлов пакета; **по умолчанию корень архива** |
| `source-dir` | `[[layout.layers]]` | каталог-источник относительно манифеста; **по умолчанию `.`** |
| `archive-dir` | `[[layout.layers]]` | каталог в архиве; **по умолчанию `.`** |
| `patterns` | `[[layout.layers]]` | обязательный список glob-масок имён файлов (например `["*.src"]`) |
| `kind` | `[[artifact]]` | обязательный: `source` (исходники в пакете), `package` (файлы внутри пакета), `toolchain` (рядом с `trust`) или `system` (`-l`) |
| `provides` | `[[artifact]]` | обязательный список логических имён библиотек (для `@[link("...")]`/`[[link.headers]]`) |
| `sources` | `[[artifact]]` | обязательные для `kind="source"` пути к `.cpp` внутри пакета |
| `libs` | `[[artifact]]` | обязательные для `package`/`toolchain`/`system`: пути внутри пакета или имена `-l` |
| `link-options` | `[[artifact]]` | необязательные флаги; для `source` — и компиляция, и линковка (`-pthread`) |
| `capabilities` | `[[artifact]]` | необязательные требования к возможностям toolchain (например `with-torch`) |
| `header`, `libs` | `[[link.headers]]` | обязательные: используемый заголовок → логические библиотеки (demand-driven линковка) |
| `[build]`, `[files]` | архив `trust.toml` | генерируются упаковщиком: provenance и MD5-целостность |
| `trust --package <каталог> [-o <файл>.trust]` | CLI | создать пакет из каталога |
| `trust --extract <файл>.trust [-o <каталог>]` | CLI | распаковать и проверить пакет |
| `TRUST_RESOURCE_DIR` | env | перекрыть корень `share/trust` для `\\\pkg` |
| `TRUST_PACKAGE_PATH` | env | дополнительные каталоги поиска для `\\\pkg` (через `:`) |
