Конвейер (`pipeline`) оркеструет шаги компиляции. Ниже перечислены основные этапы.

## Этапы

1. **Получение данных** - чтение исходного кода из строки или главного файла
   программы и инициализация контекста компиляции (`Context` из модуля `diag`).
2. **Лексический и синтаксический анализ** - единый вызов `Parser::ParseWithSource`
   для реального файла/модуля либо `Parser::ParseText(text, sourceName)` для
   текстовых фрагментов. Внутри - Flex/Bison (лексер `syntax/lexer.l`, парсер
   `syntax/parser.y.in`). Результат - Term-дерево (`TermPtr`).
3. **Конвертер Term→AST** - класс `TermToAstConverter` (`ast/term_to_ast.hpp`)
   рекурсивно преобразует Term-дерево в новый AST (`SyntaxSeq`). Нереализованный
   синтаксис (TermID с `Kind=Unimplemented`) сообщается диагностикой `Severity::Error`.
   При ошибках после парсинга семантика и транспиляция не запускаются.
4. **Семантический анализ** - единое однопроходное ядро `NameResolutionPass`
   (компонент `semantic`): построение таблицы символов, создание структур данных и
   типов, инстанцирование шаблонов, проверка типов, разрешение областей видимости,
   система эффектов, проверка trust-контрактов. Опциональные анализаторы
   подключаются через `InlineAnalysisHook` (например, `LintHook`, gate `FlagKind::Lint`).
5. **Оптимизация и унификация AST** - не реализована (planned).
6. **Генерация C++ кода** - `CppTranspiler` преобразует AST в исходный код C++
   (`.cppt`) с сохранением атрибутов. См. [Генерацию C++ кода](codegen/).
7. **Компиляция C++ кода** - конвейер генерирует рядом с `.cppt` файлы
   `Makefile` и `build.conf` и собирает исполняемый файл через внешний компилятор.

## Модули и DSL

Реальный файл парсится через `ModuleLoader::parseSourceModule`; встроенный DSL
`trust/dsl.src` загружается через `Parser::ParseText(..., "trust/dsl")`.
Фиктивные (in-memory) источники помечаются в source map префиксом `@`.

## Ошибки парсинга и LSP

`PipelineOpts::allow_semantic_on_errors` (CLI `--semantic-on-errors`, LSP включает
всегда) разрешает запускать семантический анализ на частичном AST при ошибках
лексера/парсера; транспиляция при ошибках не выполняется. `Pipeline::releaseTypes()`
отдаёт владение `TypeRegistry` вызывающему (для LSP, чтобы `TypeId` в `SymbolIndex`
оставался валидным).

## CLI

Опции драйвера (`trust`, `trust-lsp`, `trust-dap`) объявляются единообразно через
таблицу `DriverOption` + `parseDriverArgs` (arity-aware парсер). См.
[Компилятор (CLI)](../tooling/cli/) и [Предупреждения](../diagnostics/warnings/).
