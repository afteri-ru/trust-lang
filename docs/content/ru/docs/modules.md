*TrustLang* собирается из нескольких уровней артефактов — от исходного текста до готового
приложения. Ниже — **целевая модель** модульной структуры и **причины** зафиксированных решений.

**Границы применимости.** Часть уровней уже реализована, часть — только спроектирована.
Актуальный статус и границы — в разделе [Статус и планы](status/).

## Модуль

**Модуль** — логическая единица языка (единица импорта и связывания). Лексически это одна и та же
конструкция подключения, независимо от того, где модуль физически расположен:

- в **файле** `*.src`;
- в **пакете** `*.trust` (в том числе вложенном; модуль может находиться внутри другого модуля
  или файла);
- в **предкомпилированном пакете** `*.pcp`, если модуль уже компилировался ранее.

Файл `*.src` — **всегда файл**, а не пакет и не модуль: файл является лишь одним из носителей модуля.

## Уровни

```
.src          файл исходного текста
.trust        пакет: файлы .src и/или вложенные пакеты (портативный)
.cppt/.hppt   производный C++ (генерация из .src); вручную не редактируется
.pcp          предкомпилированный пакет: код + семантика; per-platform (C++ ABI, без рантайма)
.a / .so      библиотека: линкуемый бинарник по C++ ABI, без семантики
app           приложение: результат сборки файлов, пакетов и библиотек
```

## Артефакты

| Артефакт | Что это | Назначение |
|---|---|---|
| `*.src` | файл исходного текста на TrustLang | единственный источник истины |
| `*.trust` | пакет: файлы `*.src` и/или вложенные `*.trust` + метаданные | распространение исходников; композиция |
| `*.cppt` | сгенерированный C++ | реализация для внешнего компилятора |
| `*.hppt` | сгенерированный C++-заголовок | проекция ABI для C/C++ |
| `*.pcp` | предкомпилированный пакет: код + семантика (per-target) | ускорение сборки; интероп по C++ ABI |
| `*.a` / `*.so` | библиотека: линкуемый бинарник по C++ ABI, без семантики | разделение кода между приложениями |
| приложение | итоговый исполняемый файл | результат сборки |

## Решения и их причины

### Единственный источник истины — `.src`

`.cppt`/`.hppt` всегда производные и генерируются детерминированно.
*Причина:* исключается рассогласование «двух источников истины»; генерация остаётся под
контролем компилятора (как Vala→C, Nim→C, Qt moc).

### Композиция `*.trust`

Пакет может содержать вложенные `*.trust`; композиция рекурсивна.
*Причина:* мелкая гранулярность без отдельной сущности «компонент» — одно понятие, применённое
рекурсивно; под-пакет переиспользуем и адресуем самостоятельно. Прецеденты: Maven multi-module,
Cargo workspace, npm workspaces, Bazel, OCI index, Java Jigsaw.

### `.pcp` всегда платформенно-специфичен

Предкомпилированный пакет ориентирован на нативную сборку по **C++ ABI** и не предполагает
дополнительного рантайма.
*Причина:* переносимый бинарный артефакт «на все платформы» достижим только при наличии
собственного рантайма/VM (GC, исключения, потоки), что противоречит цели нативной линковки в
C++-процесс. Следствие — идентичность предкомпилированного пакета включает `{target, toolchain,
ABI-опции, stdlib, версия схемы метаданных}`.

### Семантический ABI: идентичность в символах

ABI формируется компилятором языка по собственным правилам, поэтому идентичность
модуля/версии/признаков закрепляется в символе; разные версии дают разные символы.
*Причина:* конфликт «кто победил» не возникает — версии сосуществуют. Требование —
**полнота идентичности** (иначе ODR). Принцип — на странице [Семантический ABI](sabi/).

### Порядок загрузки существенен только внутри одной идентичности

*Причина:* между разными идентичностями символы различны, поэтому порядок не влияет на
корректность; внутри одной идентичности экземпляр кэшируется по идентичности, и первая загрузка
определяет используемый. Требования: канонический детерминированный порядок, дедупликация по
полной идентичности, отсутствие циклов (DAG), определённое правило статической инициализации.

### Гранулярность trust-единиц — явная политика

Единица кэша и единица распространения различаются; нарезка trust-единиц декларируется
(по умолчанию 1:1, с возможностью явного задания).
*Причина:* пакет как атомарная единица кэша даёт грубую инвалидацию (изменение одного файла
пересобирает весь модуль) и барьер для зависимостей, хотя сама компиляция файлов параллельна.
Прецеденты: Bazel/Buck2 (цели), Debian (source→binary), Nix (outputs), Conan (components),
GHC (package db), OCaml (`.cmxa`).

### Адресация: разделитель `\`

Разделитель `\` — часть адресации внутри исходного текста `*.src` (области имён).
*Причина:* это элемент семантической адресации, а не формат артефактов, поэтому он не
пересекается с правилами имён файлов и манифестов. Внутренний C++-манглинг — деталь
кодогенерации (см. [Семантический ABI](sabi/)).

### Видимость: по умолчанию скрыто

Инкапсуляция задаётся на уровне областей имён, а не пакетов; пакет может не экспортировать ничего.
*Причина:* инкапсуляция должна быть сколь угодно мелкой. Уровни: локальный для единицы
трансляции (безымянная область имён), внутрипакетный (скрытая видимость), публичный (экспорт в
семантическом интерфейсе). По умолчанию — скрыто, экспорт — явный.

### Портативность и распространение

Портативен `*.trust` (пакет исходников) и генерируемые из него производные; `*.pcp`
платформенно-специфичен.
*Причина:* платформенную специфичность определяет C++ ABI. Распространение — реестр/OCI/git/vendor.

## Менеджер пакетов {#package-manager}

Менеджер пакетов — **отдельный компонент** (самостоятельное приложение), а не часть компилятора.
Компилятор обращается к нему как к внешнему процессу по контракту «командная строка +
машиночитаемый (JSON) вывод»: управление зависимостями не встраивается в компилятор.

*Причина:* изоляция сбоев и домена безопасности — сеть/TLS остаются в менеджере, а компилятор
обходится без сети; отсутствует связность по C/C++ ABI (граница — протокол, а не ABI); менеджер
обновляется независимо, без пересборки компилятора. Прецеденты: `gcc` → `as`/`ld`; `cargo` →
`rustc`; в самом *TrustLang* компилятор уже делегирует внешним процессам (сборка внешним
C++-компилятором).

Компонент поставляется как **самодостаточное приложение** («толстая» сборка): используемые
библиотеки упакованы внутрь.

*Причина:* нет «DLL-hell» и необходимости искать набор разделяемых библиотек; один артефакт на
платформу; внутренние C++-зависимости не создают проблем совместимости ABI.

Реализация **переиспользует библиотеки, а не сторонний менеджер пакетов**: решатель зависимостей
(например, `libsolv`) и, при необходимости, готовый движок работы с conda-совместимыми пакетами.

*Причина:* сторонние менеджеры пакетов на собственном рантайме (Python/Ruby/Java) противоречат
минимальному набору зависимостей проекта; библиотеки же линкуются и упаковываются внутрь.

Метаданные разделены по потребителям на **слои**: манифест пакета (автор и компилятор), lock-файл
разрешённых версий, индекс реестра и манифест артефакта (для компилятора — семантический интерфейс,
см. [Семантический ABI](sabi/)).

*Причина:* у метаданных несколько потребителей (компилятор, менеджер пакетов, реестр), а контроль
целостности не может храниться в самом манифесте — иначе самоссылка.

Версия использует семантическое ядро `MAJOR.MINOR.PATCH`. Различия реализации (платформа,
инструментальная цепочка, ABI) относятся к **отдельному измерению сборки**, а не к версии.

*Причина:* версия отражает совместимость пакета, а вариант сборки — независимую характеристику;
смешение этих измерений искажает порядок версий.
