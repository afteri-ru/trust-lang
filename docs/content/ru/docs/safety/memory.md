Ни один способ управления памятью не является лучшим или универсальным: в разных условиях выигрывают разные подходы:

- Ручное управление памятью может делать всё, что угодно, кроме одного — гарантировать отсутствие ошибок.
- Анализ владения и заимствования на этапе компиляции позволяет доказать корректность кода без дополнительных
рантайм-проверок, но некоторые сценарии и алгоритмы не могут быть доказаны статически на этапе компиляции.
- Подсчёт сильных и слабых ссылок во время выполнения удобен для разделяемого владения, но имеет ненулевую
стоимость и не защищает от циклических и перекрёстных зависимостей.
- Сборка мусора упрощает работу со сложными циклическими структурами, но имеет самые дорогие накладные
расходы и недетерминированное выполнение.
- Ни один из перечисленных способов управления памятью не включает в себя вопросы межпотоковой
синхронизации доступа к памяти.

Поэтому выбирать только один способ управления памятью в языке программирования — это значит заранее ограничить его возможности и добавить лишние накладные расходы. Из этих соображений концепция управления памятью *TrustLang* допускает расширение реализации модели управления памятью с минимальным влиянием на синтаксис языка и определяется требованиями (гарантиями) для работы с памятью.

## Модель управления памятью {#concept}

- Семантика языка делит переменные не по способу внутренней реализации, а по семантике, т. е. переменная по значению может хранить данные в куче, но при копировании должно выполняться и создание копии всех её данных, находящихся в куче.
- Полное описание жизненного цикла объекта всегда включает в себя несколько **ортогональных** осей и никакая сокращённая символьная запись в принципе не может закодировать всё множество комбинаций (вид ссылки, доступ, принадлежность к региону (время жизни), наличие деструктора у объекта и т. п.). Поэтому сокращённая символьная запись типов переменных предназначена только для переменных, жизненный цикл которых компилятор может верифицировать в автоматическом режиме во время компиляции (преимущественно для **локальных областей**).
- В идентичность типов данных включаются не только типы ссылок, но и способы межпоточной синхронизации доступа.
- Так как требуется взаимодействие с C++-кодом, то от сырых указателей на данные полностью уйти нельзя, но для них вводятся жёсткие ограничения на уровне компилятора (статического анализатора), чтобы [ограничить ошибки при работе с памятью](https://github.com/rsashka/memsafe).
- Работа с памятью должна включать в себя и [защиту стека от переполнения](/ru/docs/safety/stack_check/).

Текущая модель управления памятью находится на стадии тестирования и будет задокументирована в [версии 0.7.0](/ru/docs/status/).
Обсудить эти и другие концепции проекта можно на Reddit https://www.reddit.com/r/trust_lang/

## Модель жизненного цикла: ортогональные оси {#rules}

Жизненный цикл объекта описывается несколькими **ортогональными** аспектами; каждый выражается своим атрибутом (один атрибут — один аспект).

| Аспект | Атрибут | Смысл | Входит в идентичность типа |
|---|---|---|---|
| Владение (вид ссылки) | `@[reftype(<kind>)@]` | кто и как владеет объектом | да |
| Доступ/синхронизация | 2-й/3-й аргумент `reftype` | как синхронизируется доступ | да |
| Зависимость объектов  | `@[borrowing@]` | кто и как владеет объектом | да |
| Область/времени жизни/region | `@[lifetime(<area>[, <name>])@]` | как долго валиден невладеющий view | нет (только анализ) |
| Разрушение | `@[deleter(D@)]` | как освобождается ресурс | да для `unique`, стирается для `shared` |
| Мутабельность | `@[readonly@]` / `^` | константность доступа | квалификатор |
| Стабильность адреса | `@[pin@]` | адрес — часть идентичности | **не реализовано** |

Вид ссылки задаётся атрибутом `@[reftype("...")@]` (или символическим маркером `&&`/`&*`/`&?`) перед **типом** (т.е. после `:`)
или перед **переменной** при использовании авто-вывода типа переменной.
Вложенные ссылки выражаются цепочкой отдельных ссылочных типов, а не «ссылкой на ссылку» в одном объявлении.

## Виды ссылок {#variables}

Все варианты вида ссылки (`RefType`):

| Вид (`@[reftype("…")]`) | Маркер | Смысл | C++-тип | Копируемость |
|---|---|---|---|---|
| `value` | — | владение значением (без ссылки) | `T` | по типу `T` |
| `shared` | `&*` | совместное владение (счётчик ссылок) | `trust::Shared<T>` | копируется (счётчик растёт) |
| `weak` | `&?` | слабая (невладеющая) ссылка на `shared` | `trust::Weak<trust::Shared<T>>` | копируется |
| `unique` | `&&` | эксклюзивное владение (единственный владелец) | `trust::StaticUnique<T>` (inline) / `trust::Unique<T,D>` (с deleter'ом) | **move-only** |
| `ptr` | `@[reftype("ptr")@]` | сырой указатель (только явно) | `T*` | копируется |
| `ref` | `@[reftype("ref")@]` | нативная ссылка (только явно) | `T&` | — |
| `mptr` | — | указатель на член | `T C::*` | копируется |
| `rref` | — | rvalue-ссылка | `T&&` | **зарезервирован, не реализован** |
| `ptrptr` | — | указатель на указатель | `T**` | **зарезервирован, не реализован** |
| `locker` | — | охранник доступа к `shared`/`weak` (результат `lock()`) | `trust::Locker<T>` | move-only |

Примеры:

```python
s : @[reftype("shared")@] Int32 := 5;    # канонически: вид у типа -> trust::Shared<int32_t>
u : @[reftype("unique")@] Int32 := 10;    # trust::StaticUnique<int32_t> (inline, zero-cost)
w : @[reftype("weak")@] Int32 := s;      # trust::Weak<trust::Shared<int32_t>>
x : &*Int32 := 5;                        # маркер у ТИПА: то же, что shared
&* y := 7;                               # маркер у ПЕРЕМЕННОЙ, тип опущен (авто-вывод) -> shared
&? z := & x;                             # weak из shared (авто-вывод)
&* bad : Int32 := 5;                     # ОШИБКА: вид у переменной, но у явного типа вида нет
&* dup : &*Int32 := 5;                   # ПРЕДУПРЕЖДЕНИЕ -Wref-kind-dup (лишний квалификатор)
```

**Копируемость.** `shared`/`weak` копируются; `unique` **move-only** — копирование (инициализация/
присваивание из другого `unique`) запрещено, перенос владения — только `a :=: b` (swap) или `a :=: _`.

**Нативные виды.** Сырые `ptr`/`ref` задаются только явным `@[reftype(...)]` (переходная ось
совместимости с C++) и не смешиваются с умными ссылками.

## Политики доступа (ось доступа и синхронизации) {#access}

Политика — 2-й (и при необходимости 3-й — класс реализации) аргумент `reftype`; входит в тип.
Пользовательские политики доступа задаются только для `shared`/`weak`. У `unique` политика тоже
есть, но она **фиксирована** и не параметризуется: монопольный (эксклюзивный) доступ
единственного владельца.

```python
s : @[reftype("shared", AccessMutex)@] Int32 := 5;    # trust::AccessShared<int32_t, AccessMutex>
```

| Вид | Политики | Форма доступа |
|---|---|---|
| `shared`/`weak` | `AccessMutex`, `AccessRwMutex`, `AccessSingleThread` | охраняемый захват `lock()`/`lock_const()` |
| `unique` | фиксирована: монопольный (эксклюзивный) доступ | прямой доступ `*u` (zero-cost) |

## Deleter: освобождение внешних ресурсов {#deleter}

Атрибут `@[deleter(D)@]` задаёт deleter-функтор (`D::operator()(V*)`) для **владеющих** видов:

```python
h : @[reftype("unique")@] @[deleter(FileDeleter)@] File := open_file(...);
```

- Допустим только на владеющих видах (`unique`/`shared`); на невладеющих — ошибка.
- Для `unique` `D` **входит в тип**: `trust::Unique<T, D>` (как `std::unique_ptr<T, D>`), поэтому
  `unique<T, D1>` и `unique<T, D2>` — разные типы.
- Для `shared` `D` **стирается** из типа (`trust::Shared<T>`) и применяется при создании/`adopt`.

## Области времени жизни (region) и `@[lifetime@]` {#region}

`@[lifetime(<area>[, <name>])@]` помечает **невладеющий view** (`ptr`/`ref`) границей валидности (регион). Контракт валидируется; статический анализ регионов и escape-правила возврата из функции — в разработке. Детали — в [Статусе](../status/).

## Стабильность адреса (`@[pin@]`) {#pin}

`@[pin]` (адрес — часть идентичности объекта) в текущей версии **не реализован**.

## Разыменование и захват {#lock}

Доступ к значению ссылки — оператор разыменования, одновременно выполняющий захват (для
`shared`/`weak` — с блокировкой при синхронизации):

- `*ref` — захват для чтения/записи;
- `*^ref` — захват только для чтения (const);
- `with(l = *ref) { ... }` — удержание захвата на весь блок; несколько ссылок — групповой захват.

Повторный захват одного объекта в одном выражении (`*a + *a`) — предупреждение `-Wdouble-capture`
(для синхронизированных ссылок это самоблокировка).

Охраняемый доступ к синхронизируемому объекту даёт гвард `trust::Locker<T>` (для `shared`/`weak`;
результат `lock()`/`lock_const()`). У `unique` политика тоже определена — монопольный
(эксклюзивный) доступ: владелец единственный, поэтому доступ `*u` прямой, без рантайм-гварда;
сырые `ptr`/`ref` также без гварда.

## Перемещение и обмен владением {#move}

Оператор `:=:`:

- `a :=: b` — обмен самих ссылок (владений) одного вида;
- `*a :=: *b` — обмен значений по ссылкам;
- `x :=: _` — перемещение в discard (владелец остаётся moved-from; для `unique`/`shared` ресурс
  освобождается автоматически);
- `@move(x)` → `x :=: _`, `@swap(a, b)` → `a :=: b`.
