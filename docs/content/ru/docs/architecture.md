### Границы архитектуры

- **TrustLang отвечает за безопасность, а не за скорость.** Многостадийное понижение (AST → HIR → MIR)
  существует для анализа и доказательства свойств; middle-end оптимизатора нет. Оптимизацию
  производительности выполняет C++ компилятор, которому передаётся сгенерированный код.
- **Safety-проверки обязаны переживать оптимизацию C++.** Они эмитируются как наблюдаемые операции
  (runtime-функции/`throw`), а не как потенциально устранимая арифметика; сохраняются сборкой и исполнением
  артефакта на `-O2/-O3`.
- **Компонент = каталог `include/<component>/`.** Публичный API объявляется явно — заголовки корня в
  манифесте `trust_component(PUBLIC_HEADERS ...)`; детали реализации — в internal-подкаталогах
  (`INTERNAL_DIRS`: `ast/nodes`, `semantic/typer`, `ir/hir`, ...); память internal-подкаталога — его `MEMORY.md`
  (необязателен там, где нет трудно-выводимых инвариантов: знания живут в WHY-комментариях кода).
  Include internal-подкаталога за пределами компонента запрещён (CTest `internal_boundary_guard`),
  полноту/доступность публичного API проверяет `public_api_guard`.
- **Делегирование зависит от целевого контракта бэкенда.** C++ ABI, layout и манглинг не моделируются, пока
  их предоставляет контракт C++-бэкенда; нативный бэкенд (LLVM) владеет ABI/layout/mangling в своём целевом
  контракте — это не делегирование C++. Целевые факты в языковую модель не попадают ни в одном случае.
- **Бэкенд подключается контрактом, а не правкой оркестратора:** стадии описаны данными
  (`BACKEND_STAGE_LIST`), целевой контракт — `include/pipeline/backend/` (контракт — internal-подкаталог `pipeline`); C++-сборка (`make`) — слой `toolchain`,
  не часть компиляционного конвейера.
- **Один владелец факта — единственный путь вычисления (обязательное требование архитектуры).** У каждого
  факта компилятора ровно одно хранимое представление (владелец) и ровно один именованный путь вычисления —
  аксессор владельца; второе хранилище того же факта запрещено, проекция читается только через аксессор.
  Идентичность сущности детерминирована и назначается владельцем представления; факт, принадлежащий
  внешнему инструменту (C++ ABI, layout, mangling), не моделируется повторно — только предикат и проверка.
  Нарушение — дефект архитектуры; полный перечень требований — `ARCHITECTURE.md` (раздел 3).

### Последовательность этапов обработки исходного текста программы

1. Входной поток исходного текста разбивается лексером на отдельные универсальные элементы
   (токены), каждый из которых несёт информацию о своём местоположении в исходном тексте.
2. Макропроцессор сравнивает последовательности токенов и при совпадении с заданной шаблонной
   последовательностью заменяет определение макроса на его тело.
3. Последовательность токенов анализируется парсером (Bison), который строит дерево разбора —
   Term. Term хранит структуру разбора и диапазоны токенов; для целей форматирования текста
   программы используется информация о положении между соседними элементами.
4. Дерево разбора (Term) и универсальные элементы (токены) конвертируются в конкретные узлы AST,
   с которыми работают все остальные компоненты приложения. Информация о местоположении узла в
   исходном тексте также сохраняется.
5. AST проходит семантический анализ: разрешение имён и областей видимости, проверка и вывод типов,
   перегрузка функций/операторов, проверка контрактов. Факты анализа материализуются в полях узлов AST;
   при ошибках компиляции кодогенерация не выполняется.
6. Типизированная AST понижается в HIR (структурная форма: раскрытие «сахара», метки/goto, временные
   анализатора) и MIR (CFG для потоковых анализов и верификатора). Гейты `verifyHir`/`verifyFlowModule`
   проверяют контракты представлений; после этого выполняются потоковые анализы (definite assignment,
   инвалидация производных представлений).
7. HIR попадает в генератор кода, который транслирует его в буфер исходного кода C++. Одновременно
   создаётся специальная карта отображения исходного текста программы на сгенерированный C++-код
   (SourceMapper), с помощью которой можно отслеживать трансляцию каждого фрагмента в итоговый C++-исходник.
8. Буфер исходного кода сохраняется в сборочный каталог. Рядом с транслированным `.cppt` помещаются
   настроенные файлы сборки `Makefile` и `build.conf`, с помощью которых можно собрать исполняемый файл
   внешним C++-компилятором без ручной настройки. Туда же записывается сжатая информация SourceMapper,
   которая может быть включена в бинарный файл для последующей отладки или подключена LSP-сервером для
   навигации по коду.
9. Если в сгенерированном C++ используются рантайм-заголовки TrustLang, они доставляются
   из пакета стандартной библиотеки `share/trust/stdlib.trust` (trust-исходники, реализации
   встроенных типов `builtin/*.src` рядом с их C++-заголовками `builtin/*.hpp`). Пакет распаковывается
   в каталог сборки, а `build.conf` добавляет include-пути `-Istdlib -Istdlib/include`; поштучного
   копирования заголовков нет. Критерии доставки: заголовки **стандартной библиотеки C++** (угловые
   скобки, `<...>`) предоставляет используемый компилятор C++; заголовки самого TrustLang (`@trust/…`
   для рантайм-примитивов, `@stdlib/builtin/…` — заголовки встроенных типов, `@stdlib/…` — остальная
   стандартная библиотека) находятся в пакете `stdlib.trust` и разрешаются через его include-пути.
   Реализации встроенных типов и библиотечные классы грузятся ЯВНО одним зонтичным модулем `\std();`
   (он же подключает runtime-реализации памяти/владения — `\mem();` — и прерываний/исключений — `\exceptions();`).
   Необязательные нативные библиотеки
   (tensor) поставляются отдельными provider-пакетами в `share/trust`; их `[[artifact]]`
   описывает include-каталоги и link-опции, которые добавляются только при реальном использовании
   (`@[link]`/`[[link.headers]]`). Source-пакеты (`kind="source"`) доставляются только исходниками:
   их компилирует компилятор приложения в `libtrust_third_party.a`.
10. Формальная верификация (AoRTE) реализована как отдельный транспилятор контрактов в формат SMT-LIB 2
   для внешнего SMT-решателя.
11. Бэкенд в любой другой язык программирования или сразу в LLVM предусмотрен архитектурой: LLVM-бэкенд —
   обязательная возможность целевой модели. В этом случае пропадёт возможность вставок C++-кода (но можно
   будет вставлять фрагменты кода другого языка), а ABI/layout/mangling становится фактом целевого контракта
   этого бэкенда, а не делегированием C++; универсальность появляется за счёт использования разных бэкендов.
