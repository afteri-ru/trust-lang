# Архитектура TrustLang — целевая модель

> status: architecture-target (to-be) — обязательный ориентир и критерий приёмки. Текущее состояние (as-is)
> описывает `MEMORY.md` компонент и может целевой модели не соответствовать.
> scope: архитектура компилятора целиком (язык, представления, идентичность, диагностика, границы компонент, бэкенды)
> owner: архитектурные решения проекта; изменения — по §7
> review_period: 90

## 0. Статус документа и правила работы с ним

Этот документ фиксирует **целевую архитектуру проекта** — то, к чему код обязан стремиться. Он не описывает
текущее состояние и не планирует работы: as-is живёт в `MEMORY.md` компонент (синхронизируется с кодом,
AGENTS.md §12).

Источник формулировок требований — практика промышленных компиляторов (Clang/LLVM, rustc, Go, Swift, Roslyn,
Zig, GCC), адаптированная к целям TrustLang; таблицы соответствия и обоснования в документ не входят.

Правила:

- **Требование = id + формулировка + конкретизация + способ проверки.** Требование без теста — не
  требование. Механизм контроля (тесты) — инженерная политика (§6), а не требование целевой модели.
- **Критерий необходимости (единственное основание включения).** Требование включается, только если его
  удаление делает неконтролируемым хотя бы одно из: **(a)** единственность источника факта; **(b)** границу
  «фронтенд → бэкенд»; **(c)** детерминизм и воспроизводимость артефактов; **(d)** наблюдаемую пользователем
  корректность (диагностика указывает на настоящую причину; артефакт собирается и работает); **(e)** возможность
  добавить целевой бэкенд без переписывания языковой модели. Требование, не меняющее (a)–(e), архитектурным не
  является: это стиль (`CODESTYLE.md`), предметная семантика языка или инженерная политика (§6).
- **Критерий проверки.** Проверка — смысловая: тип-система (`static_assert`, приватность, `friend`),
  поведенческий тест (вход → наблюдаемый результат), явное объявление намерения вместо порога. Система сборки
  контролирует только корректность кода и целостность среды сборки (раскладка, зависимости компонент,
  публичный API); проверки архитектурных требований — только тестами (AGENTS.md §16). Счётчики и пороги объёма
  (размер файла, число строк/пунктов/записей, байты документации) проверкой не являются: формальный поиск без
  анализа контекста не отличает нарушение от легитимного случая (AGENTS.md §15).
- **Статус «to-be» не ослабляет требование.** Ссылка на текущий код, `MEMORY.md`, `docs/` или комментарий не
  является основанием для исключения: `MEMORY.md` фиксирует текущее состояние, а не цель.
- **Допустимая проекция** признаётся только архитектурным решением, записанным в §4 (владелец факта,
  единственная точка инвалидации, причина, по которой это не второе хранилище). Ссылка на существующий код
  таким решением не является.
- **Расхождение с целевой моделью — отклонение.** Документ описывает цель; расхождение кода с ним устраняется
  приведением кода к целевому состоянию, а не правкой документа.
- Термины: **факт** — данные, которые хранятся; **предикат** — чистое вычисление над фактами (может не
  храниться); **кодек** — обратимое преобразование представлений (например, имя → C++-идентификатор);
  **аксессор** — единственный именованный путь чтения факта у владельца; **проекция** — производное
  представление, читаемое только через аксессор владельца.

## 1. Назначение и границы проекта

- **TrustLang отвечает за безопасность, а не за скорость.** Многостадийное понижение (AST → HIR → MIR)
  существует для анализа и доказательства свойств; middle-end оптимизатора нет. Оптимизацию выполняет
  целевой C++-компилятор.
- **Safety-проверки обязаны переживать оптимизацию C++.** Они эмитируются как наблюдаемые операции
  (runtime-функции/`throw`), а не как потенциально устранимая арифметика; сохраняются сборкой и исполнением
  артефакта на `-O2/-O3` (R52).
- **Компилятор владеет:** моделью типов и формы, идентичностью сущностей, диагностикой, модульной моделью,
  анализом владения/инициализации, контрактами и обязательствами, кодогенерацией в целевой язык.
- **Компилятор делегирует:** ABI, layout и манглинг — **целевому контракту** бэкенда (для C++-бэкенда это
  ABI/layout/mangling C++; для нативного бэкенда — ABI/layout целевой платформы, R4/R37); сборку и линковку —
  слою `toolchain` (не часть конвейера); проверку POD/тривиальности — целевому C++; оптимизацию — целевому
  компилятору.
- **Целевые бэкенды:** C++ (основной), SMT (контракты), `verify` (доказательства). **LLVM-бэкенд — часть
  целевой архитектуры** (обязательная возможность, независимо от того, реализован ли он сейчас): архитектура
  обязана допускать его без переписывания языковой модели (R37), а его ABI/layout/mangling — факты его
  целевого контракта, а не делегирование C++ (R4/E20).
- **Компонент = каталог `include/<component>/`.** Публичный API объявляется явно (`PUBLIC_HEADERS`),
  детали реализации — в internal-подкаталогах (`INTERNAL_DIRS`); include internal-подкаталога за пределами
  компонента запрещён.

## 2. Целевая модель уровней

| Уровень | Владелец данных | Единственные читатели | Единственный вход построения | Верификатор контракта |
|---|---|---|---|---|
| Текст → токены (Scanner) | `syntax/lexer` | `syntax/macro` | поток исходника | — |
| Макрораскрытие | `syntax/macro` | парсер | буфер терминов лексера | — |
| Term (дерево разбора) | `syntax/term` | `ast/convert` | парсер (Bison) | правила грамматики |
| AST (синтаксис + факты анализа в полях) | `ast` (структура), факты — их владельцы (§4) | `semantic`, `ir` (через клон), `transpiler` (через HIR) | `module_loader` → Parser → `TermToAstConverter` | `verifyTypedAst` |
| Семантика (типы, символы, видимость) | `types`, `symbols` | все слои — через аксессоры | `SemanticPassRunner` | `verifyTypedAst` (в точке записи — писатель, R13) |
| HIR (клон + lowering) | `ir/hir` | бэкенды (`transpiler`, `solver`, `verify`), flow-анализы | `Pipeline` через `buildHir` | `verifyHir` |
| MIR/CFG | `ir/mir` | flow-анализы, верификатор | `Pipeline` через `buildMir` | `verifyFlowModule` |
| Flow-анализы (CFG/dataflow по MIR) | `ir/mir` (CFG/места); результат прохода — диагностика | потребители — через аксессор результата, если он сохраняется | фаза `FlowAnalyses` после `buildMir` | `verifyFlowModule` |
| Обязательства и доказательства | `verify` | `Pipeline` (гейт `--verify`) | стадия `Verify` | `makeProofReport` (Envelope ≠ доказано) |
| Артефакты и source-map | `pipeline` (запись файлов), `sourcemap` (mapping) | `toolchain`, LSP, отладчик | `Pipeline` по непустому target-пути | проверки стадий бэкенда |

Правила модели:

- **Ни один уровень не читает данные нижележащего уровня мимо его аксессора** (R1/R12).
- **Один уровень — один вход построения.** Второй путь построения представления запрещён (R16).
- **Один уровень — один верификатор.** Потребители не перепроверяют форму представления (R16).
- **Данные анализа не пересчитываются на бэкенде:** кодоген читает факты из полей HIR и аксессоров `types`
  (R39).
- **Порядок фаз и стадий — данные** (`PIPELINE_PHASE_LIST`, `BACKEND_STAGE_LIST`), не `if` (R19).
- **Композиционный корень — не в середине графа:** `Context` — фасад с невладеющими ссылками, владелец
  жизненного цикла `TypeSystem`/`ModuleLoader` — `Pipeline` (R34).

## 3. Каталог требований

Требования разбиты на семейства. Нумерация стабильна: id не переиспользуется и не перенумеровывается.

### 3.A Владение фактами (R1–R15, R49, R53)

**R1. Одно хранимое представление факта и один аксессор.** У каждого факта компилятора ровно одно хранимое
представление (владелец) и ровно один именованный путь вычисления — аксессор владельца. Второе хранилище
того же факта запрещено; проекция допускается только как мемоизированное производное, читаемое исключительно
через аксессор. После материализации факт доступен только для чтения: публикация — единственная точка
перехода к неизменяемому состоянию, запись — только через зону-владельца. Владелец факта владеет и временем
жизни его представления: невладеющая ссылка на факт действительна только в пределах объявленного владельцем
scope (после разрушения носителя факт остался бы без владельца). Проверка «проекция == владелец»
не является целевым состоянием. Имя аксессора читается как «чей факт» (`fieldsOf`/`identityOf`/`is<Predicate>`);
стиль имён (`getData`/`getInfo` и т.п.) — предмет `CODESTYLE.md`, не архитектуры.

| Разрешено | Запрещено |
|---|---|
| повторный вызов единственной функции-вычислителя | вторая реализация того же вывода (дубль предиката/рендера/кодека) |
| производное, вычисленное на месте и не сохранённое | сохранённая копия факта в другом типе/контейнере/векторе |
| мемоизация у владельца с единственной инвалидацией | локальный кеш без владельца и точки инвалидации |
| идентичность через типизированный id | идентичность через текст/имя/адрес (текст — только для диагностик) |
| `EXPECT`/`FAULT` при нарушении контракта | silent fallback при отсутствии владельца |

Критерии приёмки R1 (применяются к **хранимому факту**; предикаты и кодеки им не подлежат):

1. **Тест удаления:** удаление поля-владельца даёт ошибки компиляции во всех точках использования; место,
   собравшееся без владельца, содержит копию факта.
2. **Зона записи:** писать может только зона-владелец; остальные получают `const`-доступ.
3. **Единственный аксессор:** нет прямой адресации владельца в обход аксессора (тест).
4. **Запрет equivalence-тестов:** тест равенства двух представлений легитимизирует дубль; нужен тест
   единственного пути. Сверка «проекция == владелец» не является целевым состоянием.
5. **Запрет ordinal coupling** (см. R14).

**R2. Единственный путь вычисления производного.** Производное значение вычисляется одним именованным
вызовом; для рекурсивных и дорогих выводов обязательны мемоизация у владельца и защита от циклов.
Чистые функции и кодеки мемоизации не требуют. Пересчёт мимо владельца запрещён.

**R3. Детерминированная идентичность.** Идентичность сущности назначает владелец её представления; порядок
анализа, адреса и счётчики сессии в идентичность не входят. Для объявлений — `DeclId` владельца объявления;
для параметризованных типов — структурный ключ. `TypeId` — индексная identity-view реестра: стабильна в
пределах прогона и является документированным исключением из требования межпрогонной стабильности.
Диагностики, сертификаты и отчёты ссылаются на эти идентификаторы, а не на адреса или счётчики времени.

**R4. Делегированный факт не моделируется.** Если истина принадлежит внешнему инструменту, TrustLang владеет
только предикатом и утверждением; предикат формулирует компилятор, проверку выполняет целевой инструмент
(в т.ч. `static_assert` в сгенерированном коде как верификация, а не источник истины). Делегирование
**определяется целевым контрактом бэкенда**: C++ ABI, layout и манглинг не моделируются, пока их предоставляет
контракт C++-бэкенда; для нативного бэкенда (LLVM) ABI/layout/mangling — факты его целевого контракта (E20), а
не делегирование C++. Из этого не следует ослабление R37: целевые факты в языковую модель не попадают ни в
одном из случаев.

**R5. Один канонизатор на отношение эквивалентности.** Типы — `identityOf` (`kStructural`/`kSemantic`/
`kCanonical`/`kCppInterop`; `operator==` типов вне владельца запрещён); имена — единый обратимый кодек
(`encodeIdent`/`decodeIdent`, обратимость — свойство кодека, проверяется тестом); «шаблонность» —
`cppTemplateParams`; сигнатуры — `FunctionIdentity::typeCode`. Второй канонизатор запрещён.

**R6. Явная граница «синтаксис / семантика».** `types` не содержит формы, принадлежащей `ast` (порядок,
`visibility`, инициализатор, `MapperRange`), и наоборот: AST не хранит форму record (поля, базы, методы) —
она принадлежит `types`. Общий мутабельный факт между слоями запрещён. Поля AST, несущие семантические
значения (`resolvedTypeId`, `inferredType`, `resolvedSignature`, `resultType`), — допустимое представление
факта владельца `types` для нужд бэкенда; они заполняются только семантикой и читаются только бэкендом.

**R7. Ленивая проекция.** Производное вычисляется по требованию, мемоизируется у владельца и
инвалидируется в одной точке.

**R9. Fail-closed.** Ни один слой не подменяет отсутствующий факт или владельца молчаливым значением:
пустой результат, `nullopt`, молчаливый `...` в рендере, подстановка `Any` без диагностики — запрещены;
нарушение контракта — `FAULT`/`EXPECT` с диагностическим текстом (ICE).

**R12. Через границу слоёв передаётся владелец (аксессор), а не копия.** Потребитель без права записи
получает read-model, а не мутабельный корень.

**R13. Проверка — в точке записи**, не в потребителе и не в пост-проходе по корню.

**R14. Запрещён ordinal coupling.** Два независимых контейнера одного набора не связываются по индексу;
связь — по ключу (имя/id) либо один контейнер записей.

**R15. Контракт ≠ реализация builtin.** У интерфейса встроенного типа одна реализация на `TypeId`
(повтор — диагностика); реализация добавляет члены единственным оверлеем, состояние берётся из нативных
базисов, а не из собственных полей.

**R49. Полнота модели владения.** Каждый хранимый факт компилятора имеет в §4 строку: владелец, аксессор,
зона записи и (если есть) единственную точку инвалидации проекции. Факт без строки в §4 — нарушение: у него
нет названного владельца, и R1 для него не выполняется по построению.

**R53. Антипаттерны запрещены без исключений.** Любая форма дублирования факта, теневого хранения и
«производного как источника» запрещена в любой зоне и на любом этапе. Запрещены (перечень обязательный,
но не исчерпывающий; частные случаи R1–R52): `double-bookkeeping` (вторая запись о том же факте),
`shadow-cache` (копия факта без владельца и точки инвалидации), `recompute-instead-of-query` (пересчёт
факта мимо владельца), `derived-as-source` (производное как источник истины), `stringly-typed identity`
(идентичность по тексту/имени; текст — только для диагностик), `eager-derived-materialization` (энергичная
материализация производного), `ordinal coupling` (R14: два контейнера одного набора, связанные по индексу).
Допустима ТОЛЬКО явная проекция §4: владелец + единственный аксессор + единственная точка инвалидации +
обоснование, почему это не второе хранилище; проекция вносится архитектурным решением (§7.3), а не ссылкой
на существующий код. Нарушение — дефект, а не «технический долг».

**Единственное исключение — промежуточный этап архитектурного рефакторинга.** Второе представление факта
(второй владелец, временный мост/кеш) допускается ТОЛЬКО внутри отдельного этапа рефакторинга архитектуры и
только если этот этап ЯВНО согласован в задаче на стадии планирования (с указанием, какой этап нарушает
промежуточную консистентность и почему его нельзя свести к «зелёному» инкременту). Исключение действует
исключительно на время этапа и не является результатом: временное представление обязано быть удалено к
завершению этапа (тест удаления по имени-алиасу; остаток после завершения этапа — дефект).

Проверка — смысловая: тип-система (приватность/`friend`/`static_assert`), «тест удаления», поведенческий
тест; формальный поиск по подстрокам/маркерам критерием не является (§0, AGENTS.md §15/§16).

### 3.B Представления и их контракты (R16–R19)

**R16. Один вход и один верификатор на представление.** AST после прогона семантики неизменяема (кроме
recovery); HIR — единственный вход бэкендов; MIR/CFG — единственный вход flow-анализов и верификатора.
Каждое представление имеет ровно один верификатор контракта (`verifyTypedAst`/`verifyHir`/`verifyFlowModule`);
потребители форму представления не перепроверяют. Нарушение контракта — ICE. Недостоверное представление
(ошибки фронтенда) не публикуется: бэкенды не запускаются, а стадия, требующая HIR/MIR при их отсутствии,
даёт ICE, а не тихий пропуск.

**R17. Клон и происхождение.** HIR — глубокий клон AST плюс lowering; `origin` — единственное хранимое
соответствие узла HIR исходному узлу AST (`nullptr` у синтетических). Клон не вводит вторых копий
семантических фактов.

**R18. Lowering — единственное изменение формы.** Развёртывается только «сахар» (statement-выражения,
метки/goto, временные анализатора); оптимизаций нет; safety-проверки остаются наблюдаемыми операциями.

**R19. Конвейер декларативен.** Порядок фаз и стадий бэкендов — данные; динамические условия (ошибки,
флаги) — внутри фаз. Новый бэкенд добавляется строкой таблицы, а не правкой оркестратора.

### 3.C Идентичность и именование (R21, R23, R26)

**R21. Две области идентичности.** Компиляторная идентичность (модуль + имя) и целевая C++-идентичность
(ABI-имя без модуля) — разные области; смешивать их запрещено. Модуль различает объявления в компиляторе и
не входит в C++-символ; одноимённые экспорты разных модулей разрешаются областями имён программиста.

**R23. Детерминизм идентичности объявления.** `DeclId` назначается владельцем объявления (не счётчиком
сессии/контекста) и переживает клонирование; порядок анализа и адреса в id не входят. Структурные типы
идентифицируются ключом `TypeKey`. `TypeId` — исключение (R3).

**R26. Первоклассная инстанциация.** Инстанциация идентифицируется ключом `(шаблон, типовые аргументы)`;
создаётся только владельцем (`types`), мемоизируется, имеет защиту от циклов и лимит глубины; материализация
членов — по требованию с мемоизацией у владельца. Неявное создание инстанциации мимо этого пути запрещено.
Признак вида инстанциации (primary/явная/неявная) хранится явным полем, а не выводится из ключа.

### 3.D Диагностика, ошибки, восстановление (R30–R32, R50)

**R30. Единый владелец стека контекста.** Точка сингезис-контекста (инстанциация, раскрытие макроса) —
состояние `diag` на `MapperRange`, снимаемое RAII-стеком. Диагностика «in instantiation of … / requested
here» формируется владельцем; кодоген собственных диагностик об инстанциации не создаёт. Ошибка целевого
C++ внутри инстанциации считается дефектом анализатора и покрывается тестом.

**R31. Одна модель диагностики.** Единая запись диагностики — единственный источник для text/json/sarif/LSP;
идентификаторы диагностик объявляются владельцем через X-macro; severity применяется только через реестр
опций; локация резолвится единым декодером.

**R50. Provenance раскрытия.** Цепочка раскрытия (макрос, инстанциация) принадлежит единой модели
диагностики (R31) и карте исходников: диагностика внутри раскрытия несёт и место использования, и точку
раскрытия, а не только тело макроса. Владельцы фактов: пара «место использования → определение макроса» —
карта исходников (`addMacroMapping`, input→input; читается аксессором владельца), динамический контекст
инстанциации — стек `diag` (R30). Цепочка наблюдается Note-записями той же модели (отдельного поля
provenance и структурного идентификатора связи нет: идентичность даёт локация записи плюс владелец карты);
рендеры (text/json/sarif/LSP) и LSP публикуют эти записи единым путём. Имя раскрытия (макрос, шаблон) —
проекция текста файлового буфера через механизм имён (R1: отдельно не хранится). Пара для инстанциации в
карту не пишется: точек раскрытия много (1:N), и цепочка восстанавливается динамическим стеком. Раскрытие
без цепочки — потеря наблюдаемой корректности диагностики (d).

**R32. ICE и восстановление.** Внутренняя ошибка компилятора в CLI — `Fatal` с бэктрейсом и кодом 1; в LSP —
`Error` и продолжение с частичным результатом; тихий `Error` вместо `Fatal` в CLI запрещён (маскирует
дефект). Ошибка синтаксиса оставляет восстановленный префикс AST; ошибочное подвыражение заменяется
узлом-ошибкой по принципу «diagnose-then-replace» вне `children()`; недостоверные факты не публикуются и до
бэкендов не доходят.

### 3.E Границы компонент и сборки (R33, R34)

**R33. Граница компонента.** Компонент — каталог `include/<component>/`; публичный API объявляется явно и
доступен потребителям, детали реализации — в internal-подкаталогах; include internal-подкаталога за
пределами компонента запрещён; компонент публикует один фасадный вход, а не набор точечных путей.

**R34. Ацикличный граф зависимостей.** Рёбра идут от потребителя к листу; ребро `types → ast` не вводится;
композиционный корень не размещается в середине графа; связь через значение-данные предпочтительнее
включения компонента.

### 3.F Бэкенды и переносимость (R37, R39, R40, R47, R48, R52)

**R37. Целевые факты принадлежат целевому контракту.** Факты, имеющие смысл только для конкретного бэкенда
(целевое C++-имя типа, целевые `#include`, библиотеки линковки, привязки нативных методов), размещаются в
целевом контракте бэкенда, а не в языковой модели. Языковая модель (`types`) описывает форму и идентичность
языка; появление второго бэкенда не должно требовать переписывания реестра.

**R39. Бэкенд не резолвит семантику повторно.** Вход бэкенда — HIR/MIR плюс поведенческие режимы,
переданные данными; обращение кодогена к таблице символов, опциям диагностики или повторному выводу типов
запрещено.

**R40. Артефакты и source-map.** Файлы артефактов пишет только оркестратор и только по явно заданному
target-пути; карта отображения исходника на сгенерированный код принадлежит `sourcemap`. **Каждая эмиссия,
происходящая из `.src`, получает mapping** — в любой выходной файл (связь «входной диапазон → диапазон
другого выходного файла» — нормальное состояние карты), напрямую либо через `origin` для синтетических узлов.
**Артефакт без карты запрещён**, в том числе заголовок модуля `<enc>.hppt` и umbrella-фасад: пользователь и
LSP открывают именно этот файл, и навигация из него в `.src` обязана работать. В карту не входят только
временные буферы, которые не сохраняются как артефакт (scratch-рендер с последующим удалением буфера).
**Владение диапазоном и именами.** Навигация между идентификаторами обеспечивается **name-mapping**
(`addNameMapping`: trust-имя ↔ C++-имя, связь 1:N и не ключуется диапазоном), а не диапазоном объявления.
Поэтому range-mapping объявления принадлежит **заголовочному** артефакту (`<enc>.hppt`), а `.cppt` мапит
диапазоны **тел/инициализаторов** и name-mapping идентификаторов; повторный range-mapping одного и того же
диапазона `.src` из другого артефакта запрещён (карта ключуется диапазоном 1:1 и обнаружит дубль как FAULT).
**Сгенерированные артефакты имеют суффикс `t`** (`.cppt`, `.hppt`) и не совпадают по расширению с настоящими
C++-файлами.
Проверка: инвариант владельца — сохранение выхода при активном no-op-режиме маппинга запрещено
(`EXPECT` в `save_output`); полнота маппинга (у каждого сохранённого выхода есть записи mapping) —
поведенческий тест; навигация из заголовка модуля в исходник — LSP-кейс.

**R47. Целевая выполнимость артефакта.** Сгенерированный код обязан компилироваться, линковаться и исполняться
в объявленной целевой матрице (компилятор × стандарт из целевого контракта) и не давать новых предупреждений
при включённых предупреждениях матрицы. Артефакт программы обязан линковаться без дублей определений: каждое
определение входит в сборку ровно один раз, публикуемый заголовок самодостаточен. Без этого «артефакт
корректен» не определено: успешная генерация без собираемого и исполняемого результата — не выполнение
требования.

**R48. Совместимость компилятора и рантайма.** Сгенерированный код идентифицирует версию ABI-контракта
рантайма (`TypeId`/`QualType` и рантайм-заголовки, E14); несовпадение версий — диагностика или ошибка
линковки, а не неопределённое поведение. Иначе safety-проверки исполняются против несовместимого рантайма.

**R52. Наблюдаемость safety-проверок в артефакте.** Safety-проверки (переполнение целых, деление/остаток на
ноль, проверка ссылок) остаются наблюдаемыми операциями в сгенерированном коде на всех уровнях оптимизации
целевой матрицы: артефакт, собранный с `-O2`/`-O3`, обнаруживает нарушение, а не устраняет проверку.
Проверка — lit-набор, собирающий и исполняющий артефакт на уровнях оптимизации матрицы; иначе заявленная
безопасность не отличима от устранённой оптимизатором проверки.

### 3.G Детерминизм и воспроизводимость (R42)

**R42. Воспроизводимость.** Один и тот же вход даёт идентичный вывод: результат не зависит от адресов
объектов, порядка обхода хеш-контейнеров и порядка загрузки независимых модулей (при сохранении семантики).
Порядок записей в производных артефактах (SMT-скрипт, сертификат, карта исходников) определяется порядком
объявлений/обязательств, а не неупорядоченными контейнерами. То же относится к потоку диагностик: порядок
диагностических записей детерминирован и не зависит от порядка обхода хеш-контейнеров и порядка загрузки
независимых модулей (иначе golden-проверки диагностик не воспроизводимы).

### 3.I Требования к компонентам (E1–E20)

R-требования недостижимы без требований к компонентам, через которые проходит факт. E-требования обязательны
в той же мере.

**E1. `types` — владелец формы и единственная зона записи.**
- именованные аксессоры формы (`fieldsOf`, `basesOf`, `templateParamsOf`, `instanceOf`) — единственный путь
  чтения формы другими слоями; прямая адресация полей хранилища вне `types` — нарушение;
- мутирующие примитивы зон закрыты (private + friend); публичные мутаторы доступны только зоне записи
  (семантика/`Pipeline`), потребители получают read-model;
- один вход нового прогона: новый экземпляр на прогон либо `reset()` с единственным вызывающим; смешение
  запрещено;
- мемоизация производных — у владельца с одной точкой инвалидации (`TypeCodeCache` — образец);
- один носитель типовых параметров объявленного шаблона (без второго реестра).

**E2. `ast` — владеет только синтаксисом.**
- AST не хранит форму record (поля/базы/методы) — она в `types`; семантические значения в полях узлов
  (`resolvedTypeId`, `inferredType`, `resolvedSignature`, `resultType`) — допустимое представление факта
  владельца `types` для бэкенда (R6);
- AST владеет порядком, `visibility`, инициализатором и `MapperRange` полей; `visibility` — единственный
  источник C++-доступа члена;
- идентичность объявления (`DeclId`) принадлежит объявлению (не узлу) и переживает клонирование;
- размещение формы record в AST запрещено (R6).

**E3. `semantic` — единственная точка материализации фактов.**
- форма record пишется только `defineRecord`; других писателей нет;
- проверка — в точке записи (R13); верификатор типизированной AST не становится владельцем факта и не
  заменяет запись;
- инстанциация создаётся через владельца (`types`), а не прямым обращением к интернеру;
- семантика не пишет в AST фактов, принадлежащих `types` (кроме разрешённых полей R6);
- POD/тривиальность — предикат семантики; утверждение в целевом коде — верификация, не источник истины.

**E4. `session`/`Context` — фасад, не владелец.**
- `Context` не владеет производными и языковыми фактами: те принадлежат компонентам-владельцам (§4), а
  фасад держит только их lifetime и невладеющие ссылки;
- факты самого прогона (доки макросов, пул интернированных текстов) — хранилище прогона в `Context`;
  это разрешённые строки §4 с названным аксессором, а не «новый факт в фасаде»;
- мутабельный доступ к реестру — только зоне записи, остальным read-model (R12);
- прочие новые факты в `Context` не добавляются: композиционный корень в середине графа недопустим.

**E6. `transpiler` — только чтение через аксессоры.**
- кодоген не хранит фактов: транзиентные проекции (например, наборы полей класса для одной эмиссии) не
  переносятся в поля/кеши и не склеиваются по индексу (R14);
- C++-имя — единый кодек (R5); печать номинального имени для диагностик отделена от кодогена;
- рендер параметров — единственный путь; молчаливая подстановка (`...`, `Any`) запрещена (R9);
- типы для эмиссии читаются только через аксессоры `types` (E1).

**E7. `module_loader` — владелец межмодульного интерфейса.**
- форма импортируемого record строится при разборе модуля-владельца и далее неизменна (R1);
- политика интерфейса (штамп модуля, экспорт-набор, установка интерфейса) — единственная точка мутации
  `visibility`; второй путь видимости не вводится;
- интерфейс не сериализуется между прогонами: форма пересобирается разбором владельца (§6).

**E9. `pipeline` — владелец процесса и порядка.**
- единственная точка построения HIR/MIR; порядок фаз — данные (R19);
- владелец жизненного цикла `TypeSystem` и `ModuleLoader`; политика повторных прогонов — одна (E1);
- мутабельное состояние прогона не хранится процессно-глобально: процессный глобал допустим только как
  неизменяемый — иначе второй прогон в том же процессе (LSP) получает второе хранилище факта (R1/E1);
- файлы артефактов пишет только оркестратор (R40).

**E12. `test` — контракт вместо эквивалентности.**
- «тест удаления» обязателен для каждого факта-владельца (R1);
- тесты равенства двух представлений запрещены как целевое состояние;
- тестовые фикстуры, собирающие факты без AST, переводятся на аксессоры в том же изменении, что и удаление
  дубля;
- тесты не пропускаются и не отключаются.

**E13. `symbols` — не владелец типов.**
- таблица символов хранит привязку имени и разрешённую сигнатуру/тип как **предикат объявления**, но не
  является вторым владельцем типа сущности: тип читается через аксессоры `types`;
- экспорт/видимость/неоднозначность — единственная точка решения (с привлечением правила видимости из
  `types`), второго правила нет.

**E14. `runtime` — единое определение идентичности типа.** `TypeId`/`QualType`/`TypeKind` определены один раз в
общем ABI-заголовке; изменение их представления — архитектурное решение, а не локальная правка. Версия этого
ABI-контракта — вход R48.

**E16. `verify`/`solver` — владелец обязательств и доказательства.**
- модель обязательств, статусы и сертификат принадлежат `verify`; решатель — сменный бэкенд доказательств;
- `Envelope ≠ доказано`; результаты — ровно по одному статусу на обязательство; сертификат байт-стабилен.

**E17. `sourcemap` — владелец карты отображения.**
- mapping исходника на сгенерированный код хранится только здесь; кодоген пишет карту единственной точкой
  (имя объявления → C++-имя) и не заводит собственных карт.

**E18. `syntax` — данные отделены от процесса.**
- дерево разбора (Term) — данные; парсер/макропроцессор — процесс. Списки термов/макросов/прагм объявляются
  x-macro единственным источником; текст и диапазон — независимые факты. Данные Term отделены от процесса
  парсера; смешение не углубляется.

**E19. `stdlib`/`package` — реализации и целевые факты builtin.**
- дескриптор встроенного типа — предобъявление языковой модели; реализация — отдельный модуль, владеющий
  целевыми фактами (C++-имя, include, линковка, привязки) и покрывающая все интерфейсные члены;
- одна реализация на тип; поставка — пакетом, без поштучного копирования заголовков.

**E20. `toolchain` — вне конвейера.**
- сборка и линковка целевого кода — слой `toolchain`; компиляционный конвейер его не вызывает и от него не
  зависит.
- целевой контракт (target triple, стандарт C++, выбор ABI, feature-set) — значение нейтрального владельца
  (`target`: `TargetContract::targetInfo()`): конвейер передаёт его стадиям, слой сборки читает его для
  `build.conf`. `pipeline` не зависит от `toolchain` (E20/R34), поэтому владельцем не может быть ни один из
  этих слоёв; политика выбора значений (какие опции их задают) — не архитектура (R37).

## 4. Модель владения

Таблица фиксирует владельцев фактов и **все допустимые проекции/кэши**. Допустимая проекция обязана иметь
владельца, единственную точку инвалидации и причину, по которой она не является вторым хранилищем; всё, что
не перечислено, целевой моделью не разрешено.

| Факт | Владелец (хранится) | Аксессор | Зона записи | Допустимая проекция/кэш и инвалидация |
|---|---|---|---|---|

**⚠ Целевые C++-факты не входят в идентичность языка (R37).** `TypeKey::tag` и `FunctionIdentity::typeCode`
не содержат целевых C++-имён (`cppTemplate`/`cppSuffix`): идентичность native-шаблона — языковой ключ
(объявленное имя/аргументы), а C++-имя — проекция контракта `target`; `cppSuffix` — целевой факт, не часть
`typeCode`. Компонент `types` (языковая модель) **не зависит** от `target` (R34); целевые факты читают
только потребители-бэкенды и семантические проверки через аксессор контракта.

**Тип поля record — владелец форма (`types`).** Объявленный тип поля хранится ровно в одном месте —
`TupleElementData::type` формы (`defineRecord`). `Symbol::type` — предикат объявления (E13), `VarDecl::inferredType`
поля — проекция AST-фактов для бэкенда (E2/R6), а не владелец типа поля; читатели типа поля используют только
аксессор формы (`fieldsOf`), читатели выведенного типа переменной — `ExprFacts`.

**Доступ члена record.** Источник — `AstNodeBase::visibility` объявления (AST, E2); форма хранит проекцию
`TupleElementData::access` (заполняет семантика при `defineRecord`); решение о доступе читает проверка доступа,
секции доступа эмитит кодоген по тому же факту видимости AST.

**Типовые параметры объявленного шаблона — один носитель.** До определения параметры (и маркер объявления)
живут в `TypeStore::m_declaredRecords`; `defineRecord` переносит их в форму (`RecordTypeData::templateParams`)
и стирает маркер (`takeDeclaredRecord`) — одновременно двух носителей нет.

**Долг §4.** Доступ к форме record — только через аксессоры владельца: `fieldsOf`/`basesOf`/
`templateParamsOf`/`instanceOf` (поля `RecordTypeData` приватны), к дескриптору типа — через именованные
аксессоры `nameOf`/`methodsOf`/`methodAliasesOf`/`baseTypeOf` (адрес `TypeDescriptor` наружу не выдаётся).
Целевые C++-факты (`cppName`/`includes`/`libs`/`cppTemplate`/`cppSuffix`/`methodDelegate`/`RuntimeSymbol`,
а также C++-имя ОБЪЯВЛЕНИЯ — `DeclCppFacts::cppNameOf`/`cppSuffixOf` под `DeclId`) имеют владельца — компонент
`target`; `types`/`ast` целевых фактов не хранят; `Decl` несёт только предикат `m_bindsNativeCpp` и временный
носитель имени до назначения `DeclId`. Строка §4 без аксессора владельца — ошибка §4 (R49); новый владелец
вводится архитектурным решением (§7.3).

## 5. Инварианты приёмки

Отдельного списка инвариантов нет: инвариант приёмки — это требование семейства R/E вместе с его способом
проверки (§0). Дублирование требований в виде второго нумерованного списка запрещено: два текста об одном
факте расходятся при любом изменении (R1).

## 6. Границы и не-цели

- **Layout/ABI/mangling не моделируются** — принадлежат целевому контракту бэкенда: C++ ABI для C++-бэкенда,
  ABI/layout целевой платформы для нативного бэкенда (LLVM) (R4/E20).
- **Middle-end оптимизатора нет** — единственное изменение формы это lowering (R18).
- **Модель фронтенда — цельно-программная:** кешируется только финальная сборка целевого кода; персистентная
  сериализация интерфейсов модулей не реализуется — форма пересобирается разбором модуля-владельца.
- **Инкрементальность/query-кеш не являются целью**; если появятся — кеш обязан иметь владельца, ключ и
  единственную точку инвалидации (иначе это `shadow-cache`, запрещённый R1/R7/R53).
- **Результаты flow-анализов не хранятся:** проход выдаёт диагностику. Если появится потребитель результата —
  это read-model владельца прохода с единственной точкой инвалидации; второй вход построения запрещён.
- **Специализации, рефлексия и LSP-hover не входят в ядро** целевой модели; они не должны нарушать R1–R53.
- **Движок анализов (`ir`/`analysis`: `AnalysisManager`, `dataflow`) не является требованием целевой модели:**
  владелец порядка и зависимостей анализов назван в §4; детали движка — предмет реализации, включать их в
  каталог требований не требуется.
- **Полная реализация нативного (LLVM) бэкенда — вне ядра:** целевая модель фиксирует подключаемость (R37) и
  контракт цели (E20); кодоген/layout/ABI-модель LLVM — не требование целевой модели.
- **Семантика языка не входит в архитектуру:** займы/инвалидация, контракты, правила доказательства, а также
  номинальность алиасов и гигиена раскрытия макросов — предметные документы; целевая модель фиксирует только
  владельца фактов, уровни и границы.
- **Устойчивость, лимиты, fuzz, поведение при OOM — инженерные политики**, не архитектура.
- **Механизм контроля требований — только тесты, не сборка:** архитектурные требования проверяются
  исключительно тестами. Система сборки контролирует лишь корректность кода и целостность среды
  сборки — раскладку файлов, зависимости компонент, доступность публичного API (структурные гейты), — и не
  содержит проверок архитектурных требований (AGENTS.md §16). Формальный поиск по подстрокам/маркерам
  критерием не является (§0, AGENTS.md §15).
- **Зоны проверок — политика целевого контракта:** TrustLang отвечает за концепции доверенного
  программирования (займы/инвалидация, контракты через решатель) в исходном коде; UB/санитайзеры и ABI-корректность —
  зона инструмента бэкенда, их политика одинакова для всех эмиссий. Сгенерированный C++ следует фиксированным
  шаблонам и не специализируется под конкретный исходник; зеркальная проверка в TL допустима как fail-fast и не
  подменяет целевую верификацию (R47, R52), а её расхождение с целевой — дефект, покрываемый cross-check-тестом.
- **Версия формата производных артефактов снята из каталога:** читающего потребителя производных артефактов
  (кроме карты исходников) нет; при его появлении вводится новый id (§7.1).
- **`debug`/`formatter`/`playground`/`lsp`/`driver`/`builddriver`/`module_api` — вне целевой модели**
  (компоненты и слои существуют, требований каталога не имеют). Их состояние — **не факты компилятора** и
  строк §4 не требует: сервисные кэши LSP (исходник+модель на документ), модель разобранных опций `driver`,
  оркестрация сборки/запуска `builddriver`, публичный интерфейс резолвера `module_api`. Хранимые факты §4 —
  факты компиляции; сервисный слой ими не владеет.
- **Полное отделение данных Term от процесса парсера** (E18); смешение не углубляется.
- **Ребро `ast`/`syntax` → `session` запрещено** (E4): фасад внедряется портами
  (`ConvertServices`/`ParserServices`), а `component_deps_guard` держит ребро в списке запрещённых —
  расширять его нельзя.

Отвергнуто как «не необходимое» (не является требованием; возвращать нельзя без пересмотра §0-критерия):
пользовательские коды диагностик и fix-it подсказки (DX, не (a)–(e)); отмена устаревших LSP-запросов
(поведение сервиса); краш-репро ICE (отчётность `driver`); обнаружение устаревших внешних артефактов
(политика `toolchain`); бюджеты времени/памяти компиляции (инженерная политика); «кодоген не вносит UB» как
декларативное требование (проверяется инструментом — UBSan/санитайзеры, а не формулировкой).

## 7. Порядок изменения документа

1. Новое требование получает свободный id в своём семействе; перенумерация и переиспользование запрещены.
2. Требование обязано иметь конкретизацию (компоненты/аксессоры/файлы) и способ проверки (тест).
3. Допустимая проекция вносится в §4 только как архитектурное решение (владелец, инвалидация, обоснование).
4. Изменение, затрагивающее код, сопровождается синхронным обновлением `MEMORY.md` затронутых зон (as-is).
5. Расхождение кода с документом — не основание изменить документ под код. Удаление требования
   возможно только явным архитектурным решением с обоснованием в разделе «Decisions».
6. Объём документа не является основанием для переноса требований: вынос семейства в отдельный документ —
   архитектурное решение при потере связности, а не реакция на размер (§0, AGENTS.md §15).

## Decisions

Нормативные решения, действующие в целевой модели. Снятые id не переиспользуются (§7.1); перечень
неиспользуемых id: R8, R10, R11, R20, R22, R24, R25, R27, R28, R29, R35, R36, R38, R41, R43, R44, R45,
R46, R51, R54, E5, E8, E10, E11, E15.

- **`TypeId` — документированное исключение из R3:** индексная identity-view реестра, стабильная в пределах
  прогона; межпрогонная стабильность требуется от `DeclId` и структурных ключей.
- **Критерий необходимости (§0 (a)–(e)) — единственное основание требования.** Формальные метрики (размер
  файла, число пунктов, поиск по подстроке) проверкой не являются (AGENTS.md §15). Принуждение владения —
  тип-система (приватное хранилище, `friend`/read-model зоны записи, `const`-аксессоры, `static_assert`),
  «тест удаления» и поведенческие тесты; гейты контролируют только среду сборки (границы компонент,
  раскладку, зависимости) — см. §6, AGENTS.md §16.
- **§5 (второй список инвариантов) не ведётся:** инвариант приёмки — требование семейства R/E вместе со
  способом проверки; второй текст о том же факте расходится при любом изменении (R1).
- **Архитектура ≠ семантика языка:** займы/инвалидация, контракты и правила доказательства — предметные
  документы; лимиты, устойчивость, fuzz и поведение при OOM — инженерные политики (§6).
- **R1 владеет временем жизни представления факта**, R42 распространяется на поток диагностик
  (детерминированный порядок), R47 включает линковку и исполнение в целевой матрице с однократностью
  определений (ODR, самодостаточный заголовок), R52 — наблюдаемость safety-проверок на `-O2`/`-O3`.
- **Состав целевой матрицы R47 — clang (основной) + g++ (второй компилятор), стандарт из целевого
  контракта (`c++23`); символ ELF-секции читается тем же носителем.** Сгенерированный код не опирается
  на расширения компилятора: встраиваемые данные (карта исходников, LICENSE, HTML/JS/CSS ресурсы) —
  байтовые массивы, а не директива `#embed` (C++26/GCC 15+, в `c++23` — только как расширение Clang).
  Проверка — lit-кейс (сборка, линковка, исполнение
  вторым компилятором + побайтное равенство ELF-секции `.debug_trust_map` и сохранённой карты);
  ось отключается только явно (`-DTRUST_SECOND_CXX=none`), отсутствие компилятора — ошибка конфигурации.
  Носители, отличные от ELF (PE/MSVC), целевой матрицей не покрыты.
- **R4 скоуп-зависим от целевого контракта.** C++ ABI/layout/mangling делегированы контракту C++-бэкенда;
  для нативного бэкенда ABI/layout — факты его контракта. Layout/ABI/calling convention/mangling — часть
  инструментария бэкенда: TrustLang хранит `triple`/стандарт/`features`/идентичность провайдера и владеет
  предикатом плюс утверждением-верификацией; собственной модели layout в целевой модели нет (E20).
  LLVM-бэкенд — обязательная возможность (R37), полная его реализация — вне ядра (§6).
- **Владелец целевого контракта — `target`, не `toolchain`:** `pipeline` не зависит от `toolchain` (ребро
  запрещено, E20), поэтому значения целевой платформы хранит `TargetContract` (аксессор `targetInfo()`),
  считаются они один раз при создании контракта, а `toolchain` читает их для `build.conf`.
- **Целевые C++-факты — только в `target`:** `TypeId → {cppName, preprocIncludes, libs, cppTemplate}`,
  `methodDelegate`, `RuntimeSymbol`, `cppSuffix` (ключ — `DeclId`), C++-имя объявления. Языковая модель
  (`types`/`ast`) хранит форму и идентичность и не зависит от `target` (R34/R37). Идентичность языка не
  содержит целевых C++-имён: `TypeKey::tag` и `FunctionIdentity::typeCode` ключуются объявленным именем и
  аргументами, native-шаблон — языковым ключом.
- **`Context` владеет фактами прогона, но не производными и не языковыми фактами:** доки макросов и пул
  интернированных текстов — его строки §4; пул переживает `Context` вместе с `PipelineResult` (R1/R12).
  Процессно-глобальное мутабельное состояние прогона запрещено (E9).
- **Бэкенд получает read-model, а не `Context`:** `BackendServices{RunServices, opts, loader}` (R12/R39);
  мутаторы `types` через фасад недостижимы.
- **R40: карта обязательна для каждого сохраняемого артефакта** (включая `<enc>.hppt` и umbrella-фасад);
  подавление допустимо только для scratch-буферов, которые не сохраняются. Полнота маппинга — поведенческий
  тест. Range-mapping объявления принадлежит заголовочному артефакту, `.cppt` мапит тела/инициализаторы и
  name-mapping идентификаторов (1:N).
- **Сгенерированные артефакты имеют суффикс `t`** (`.cppt`, `.hppt`); имя заголовка модуля строит
  единственная формула `location::moduleHeaderFileName`.
- **Отладочная навигация — следствие глобального покрытия `MapperRange`** (вход — `ReaderFile`, выход —
  `MapperFile`); отдельного слоя отладочной информации нет.
- **Результаты flow-анализов не хранятся:** проход выдаёт диагностику. Появится потребитель результата —
  read-model владельца прохода с единственной точкой инвалидации; кеширование/инкрементальность не являются
  целью, персистентная сериализация интерфейсов модулей не реализуется (форма пересобирается разбором
  модуля-владельца).
- **R50: цепочка раскрытия — Note-записи единой модели диагностики (R31)**; отдельных полей provenance и
  структурного id связи нет. Владельцы: пара «использование → определение макроса» — `sourcemap`
  (input→input), динамический контекст инстанциации — стек `diag`. Пара для инстанциации в карту не пишется
  (раскрытие 1:N, обратного индекса нет, потребителя нет); имя раскрытия — проекция текста буфера, не
  хранится. LSP публикует каждую запись в URI файла её диапазона.
- **R49 (полнота §4):** каждый хранимый факт имеет строку §4; к форме record и дескриптору типа доступ —
  только через аксессоры владельца (`fieldsOf`/`basesOf`/`templateParamsOf`/`instanceOf`,
  `nameOf`/`methodsOf`/`methodAliasesOf`/`baseTypeOf`), адрес дескриптора наружу не выдаётся. «Тест
  удаления» — процедура проверки при удалении/переименовании поля-владельца; отдельного исполняемого
  инструмента нет.
- **Семантические поля AST — представление факта владельца `semantic` для бэкенда (R6/R39):**
  `Binary::m_typeCheckConst` (статическая свёртка сравнения типов) и `Binary::m_overflowCheck`
  (классификация контролируемой арифметики); заполняет семантика, читает кодоген.
- **Версия формата производных артефактов не вводится:** читающего потребителя, кроме карты исходников,
  нет (R51 снят, id не переиспользуется); версия ABI-контракта компилятора и рантайма — R48/E14.
- **Зеркальная проверка в TrustLang допустима как fail-fast** и не подменяет целевую верификацию:
  запрещены второе хранилище целевого факта и замена целевой проверки результатом зеркальной.
- **Механизм контроля требований — только тесты:** архитектурные требования проверяются тестами; система
  сборки ограничена корректностью кода и средой сборки (AGENTS.md §16).
- **Антипаттерны запрещены (R53), приоритет — над удобством реализации.** Разрешена только проекция §4
  с владельцем и единственной точкой инвалидации. Исключение — только промежуточный этап архитектурного
  рефакторинга, явно согласованный в задаче на стадии планирования; временное представление удаляется к
  завершению этапа (остаток — дефект). Проверка — тесты и тип-система, не сборка (AGENTS.md §16).
