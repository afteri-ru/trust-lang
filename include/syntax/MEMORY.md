# Компонент syntax

Синтаксический компонент преобразует исходный текст в синтаксическое дерево `Term` —
универсальный узел, из которого компонент `ast` (конвертер `TermToAstConverter`) строит AST.

## Поток данных

```
Исходный текст
    │
    ▼
Scanner (Flex, lexer.l)   — лексический анализ, выдаёт термины (TermPtr)
    │
    ▼
Macro (macro.h/cpp)       — раскрытие макросов и обработка прагм
    │                      (встроен в Parser::GetNextToken)
    ▼
Parser (Bison, parser.y)  — синтаксический анализ, построение Term-дерева
    │
    ▼
Term → TermToAstConverter (ast) → AstNodeBase
```

Раскрытие макросов — не отдельная стадия: лексер подаёт термины в буфер
`Parser::m_macro_analisys_buff`, `Macro` раскрывает их до передачи в грамматику Bison.

## Основные сущности

- **`Term`** (`term.h`) — универсальный узел синтаксического дерева.
- **`TermID`** (`term_types.h`) — перечисление типов узлов из единого X-макроса `TERMS`
  (нереализованные — с `Kind=Unimplemented`, напр. `AWAIT/YIELD/WHEN_ALL/WHEN_ANY/FILLING/PARENT`)
  + `SYMBOL_TOKENS` (символьные терминалы). Каждый одиночный символ/оператор/скобка имеет
  собственный лексический TermID. Секция `%token` в `parser.y` **генерируется** из `TERMS` +
  `SYMBOL_TOKENS` на этапе configure (`cmake/generate_parsers.cmake`: `parser.y` из `parser.y.in`);
  ручного дублирования `%token` нет. Грамматика может переопределить `m_id` оператора по контексту
  (например `+` → `OP_MATH`, `<` → `OP_COMPARE`). `DOCUMENT` — документирующий комментарий: лексер
  сохраняет полный текст как `string_view` в `m_text`.
  Хвостовой вариант `///<` / `##<` возвращает отдельный bison-токен `DOCUMENT_INLINE` (Term
  остаётся `TermID::DOCUMENT`), чтобы грамматика отличала «док после statement» от «дока
  перед/standalone». Доки, привязанные к объявлению (ведущий `doc_list expression` или хвостовой
  `sequence DOCUMENT_INLINE`), грамматика кладёт в `term->m_docs` терма-идентификатора
  (`attachLeadingDoc`/`attachTrailingDoc`, см. `src/syntax/parser.cpp`), откуда
  `TermToAstConverter::convert` переносит их в `AstNodeBase::documentation`. Доки перед
  НЕ-объявлениями остаются отдельными leaf-узлами `Document` (bundle через `makeDocBundle`).
- **`Scanner`** (`lexer.h`) — Flex-лексер, наследник `yyFlexLexer`; читает текст через
  `Context`/`SourceMapper`.
- **`Macro`** (`macro.h`) — макропроцессор: определение/раскрытие/удаление макросов, стек скоупов
  по модулям, предопределённые макросы.

### Группировка макросов (инвариант)

- **Первый терм имени макроса — ключ ГРУППЫ.** Хранилище — `MacroScope` (map `хэш_первого_терма → SequenceType list`);
  `toMacroHash` берёт только `GetMacroId(term)[0]`. В одной группе может быть МНОГО макросов с
  одинаковым первым именем, но разной арностью (разным числом/составом дополнительных термов),
  например `break`, `break $label`, `break $a $b`.
- **Дубликат — только при полном совпадении сигнатуры** (всех термов). Разные арности одной группы
  НЕ являются дубликатами: в `EvalOpMacros` оба цикла проверки дубликатов снабжены guard'ом
  `GetMacroId(*iter).size() == GetMacroId(term).size()`. `::=` (create-only) на существующую сигнатуру
  → «Macros ... already exists»; `:=`/`=` — переопределение тела.
- **Раскрытие — longest-match.** `MatchMacro(buffer, macro)` возвращает число потреблённых термов
  буфера (0 — нет совпадения); `ExpandTermMacro` выбирает макрос группы с максимальным значением.
  Одинаковое число потреблённых термов у разных макросов группы — неоднозначность → Fatal.
- **Шаблон не матчит разделитель.** Шаблон (`$name`, `$...`) как терм сигнатуры не сопоставляется
  с `;`/END — иначе `@return;`/`@break;` ошибочно выбирали бы varargs/шаблонную форму с пустым
  аргументом вместо arity-1 формы.
- `IdentityMacro(buffer, macro)` — обёртка над `MatchMacro(...) != 0` (prefix-семантика сохранена;
  используется в тестах и регистрации).
- **`Parser`** (`parser.h`, `parser.y`) — Bison-парсер: связывает лексер и макропроцессор, строит
  Term-дерево, обрабатывает прагмы.

## Унифицированное представление последовательности (`Term::m_sequence`)

Единая грамматическая модель всего языка:

```
Module   := Sequence
Sequence := Expression | Expression ';' Sequence | ';' | ';' Expression | Sequence ';'
Expression ::= assign | follow | match | repeat | with | … | '{' Sequence '}'
```

Пустые операторы `';'` разрешены в `Sequence`: ведущие (`; x`), хвостовые (`x;`), одиночные
(`{ ; }`) и подряд (`;;` — валиден как пустой оператор). `Sequence`, состоящая только из пустых
операторов, возвращает пустую `SEQUENCE`-терм (без statement), чтобы не попадать в AST как
`TermID::SEMICOLON`.

Верхнеуровневая `sequence` модуля и вложенные `{ ... }`-блоки строятся из единого нетерминала
`expression` и хранятся в едином поле `m_sequence` (`SequenceType = std::vector<TermPtr>`).
`AppendBlock(force=false)` добавляет блок как дочерний элемент (граница области видимости
сохраняется в AST — иначе объявления «протекают» в охватывающий скоуп). Нетерминал `body` —
вспомогательный для тел конструкций (одиночное выражение или блок), подмножество `expression`.

## Создание терминов (`Term::Create`)

- `Create(TermID, std::string text, range, lex_type)` — **копирует** текст; безопасно для локальных
  строк и литералов (ручное создание).
- `Create(TermID, lex_type, const char* text, size_t len, range)` — строит `std::string_view`
  **без копирования**; используется в лексере (`lexer.l`), где текст токена живёт в `SourceMapper`
  (данные должны пережить Term).
- Для намеренного обрезания в `parser.y` используется явная копия `Create(id, std::string(data(), N), ...)`.

## Конфликты грамматики

Грамматика без reduce/reduce и без shift/reduce-конфликтов (`%expect 0`). Источники конфликтов
устранены структурно: EMBED — обычное выражение с обязательной `';'`; хвостовой док `///<` / `##<` —
отдельный токен `DOCUMENT_INLINE`; соседние доки не сливаются в один `doc_list` (doc_list — одиночный
`DOCUMENT`); самовложенность `separator` убрана (`;;` в sequence валиден как пустой оператор).
Подробности — в комментарии к `%expect` в `parser.y.in`.

## Ошибки лексера/парсера: Fatal → Error

Семантические ошибки разбора (лексика/грамматика, макросы, прагмы/опции, невалидный токен,
пустая последовательность и т.п.) отчётом `Severity::Error`, а не `Severity::Fatal` — они не
бросают исключение, и пайплайн (в LSP-режиме `allow_semantic_on_errors`) может продолжить
до анализатора на частичном AST. Остаются `Severity::Fatal`/throw только ошибки безопасности
(переполнение стека макросов, циклические модули, внутренняя логика). После мягкого отчёта
обеспечен корректный `return`/`continue` (без out-of-bounds и бесконечных циклов);
`Macro::CheckMacro` возвращает false при ошибке — некорректный макрос не регистрируется.
