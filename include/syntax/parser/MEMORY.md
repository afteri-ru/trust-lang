## Architecture

Bison-грамматика и `Parser`: сборка Term-дерева, восстановление после ошибок, прагмы/предопределённые
макросы в `GetNextToken`. Входы грамматики — `syntax/grammar/`.

## Facts and invariants

- **Семантические ошибки разбора → `Severity::Error`, НЕ Fatal:** пайплайн (в LSP) продолжает на
  частичном AST. Fatal/throw — только ошибки безопасности.
- **⚠ Восстановление после синтаксической ошибки — на границах ОПЕРАТОРА и ЧЛЕНА КЛАССА:**
  `sequence: error` / `<seq> error` и `class_props: error` дают ПУСТУЮ `SEQUENCE` с диапазоном ошибки;
  накопленные операторы сохраняются. `yyerrok` НЕ вызывается; форма `sequence separator error`
  несовместима (S/R-конфликт на токене `error`). Лимит ошибок принадлежит `DiagnosticEngine` — `Parser`
  счётчик НЕ ведёт; после лимита `YYABORT`, частичный AST возвращается.
- **⚠ Ловушка позиции синтаксической ошибки:** брать её из `Parser::m_recent` (реально потреблённые
  bison-токены), а НЕ из `tokenStartOffset()`/`m_current_pos`: `GetNextToken` упреждающе буферизует
  термины и курсор «убежал» вперёд.
- **Унифицированная последовательность:** верхний уровень и вложенные блоки — из единого нетерминала;
  `AppendBlock` сохраняет границу области видимости (иначе объявления «протекают» в охватывающий скоуп).
- **⚠ `class_props` — СОБСТВЕННЫЙ SEQUENCE-контейнер, НЕ связь через `m_right`:** `m_right` члена — его
  RHS/тело; связывать список членов через `m_right` нельзя (рвало тела методов/инициализаторы).
- **⚠ Forward-объявление класса:** `class_type_def: class_type_bases ELLIPSIS` маркер ELLIPSIS в
  `m_sequence`; `native_class_fwd` — RHS ЛЮБОЕ имя (native с `%`), явная форма заполняет `m_template`.
  Dot-члены — dedicated `class_member` (ведущая '.' — экземплярный член), не общий `assign_lval`.
- **⚠ `tmpl_ctor` — явная конструкция шаблон-типа в позиции значения** (`:Box<Int32>(...)`): отдельное
  правило даёт РОВНО один дополнительный S/R на `type_class • LT`. Затрагивает только `:`-формы;
  `a < b`/`x:Int32 < 5` не тронуты.
- **⚠ Лямбда: `LAMBDA` (FuncDecl) + `LAMBDA_CALL` (CallExpr) — НЕ токены:** захваты в `m_sequence`
  (НЕ в `m_args` — туда позже пишутся параметры), параметры — `m_args`, тело — `m_right`. Прямая форма
  `lambda(args)` не поддерживается (грамматика принимает её ради явной диагностики).
- **`FILLING` (`... expr ...`) — Kind `Filling` (класс `Sequence`),** правило `arg` ОБЩЕЕ для всех `args`.
- **Оператор-объявление — обычная функция с СИСТЕМНЫМ именем** (`__eq__`, `__getitem__`); отдельного
  операторного нетерминала нет. `REFLECTION` — только для embed-выражений. Контракты едины для
  функций/методов/операторов.
- **⚠ Операторы сравнения типов:** `<~` — ОТДЕЛЬНЫЙ лексерный токен (двухсимвольный, обходит ловушку
  `:T<...` = шаблон-аргументы); `~~`/`~~~` — `OPERATOR_DUCK`. Оператор `~` больше нигде не существует
  (`TILDE` — только деструктор `~Name()`).
- **⚠ Наборы типов (`:A + :B`) — грамматика БЕЗ новых конфликтов:** `type_set_expr: types | … PLUS types |
  … MINUS types`; RHS `::=` и inline `:(:A + :B)`. Ведущий `:` перед `(` ОБЯЗАТЕЛЕН (иначе конфликт с
  вызовом/словарём). Guard «`m_id = TYPE`» ОБЯЗАН исключать `TYPE_SET`, иначе набор затирается до типа.
- **⚠ `%expect 3` не меняется:** `type_item` vs `type_item_tmpl` — намеренный «инвертированный» шаблон:
  в операнд-позиции `<` обязан оставаться сравнением (`1:Bool < var`).
- **⚠ Границы унификации «аргументы vs шаблон»:** голое имя в `<>` — ТИП-аргумент, то же в `()` —
  ЗНАЧЕНИЕ; `args` и `template_args` не сводимы в один нетерминал без запрета голых выражений-аргументов.
