## Token и Sequence

`SyntaxToken` — универсальный элемент последовательности токенов, объединяющий лексемы лексера (`Lexeme`) и узлы AST (`AstNodePtr`).
Реализован как наследник `std::variant<Lexeme, AstNodePtr>` с шаблонными методами доступа.

- Наследует конструкторы и операторы присваивания от `variant`.
- `get<T>()` — возвращает `T*` или `nullptr` при несовпадении типа (через `std::get_if` для `Lexeme` и `dynamic_cast` для наследников `AstNodeBase`).
- `is<T>()` — проверка типа (делегирует `get<T>() != nullptr`).
- `as<T>()` — возвращает `T&`, кидает `std::bad_variant_access` при несовпадении.
- Единый внутренний helper `try_get_impl<T>(const variant*)` содержит всю логику dispatch между `Lexeme` и `AstNodeBase`. `const`-методы вызывают его напрямую, non-`const` — через `const_cast`.
- `using SyntaxSeq = std::vector<SyntaxToken>` — единый тип последовательности.

### Поток данных

```
Flex/Lexer → Sequence → MMProcessor → Sequence → ParserAST
```

### Примечания

- Внутренние поля AST (`m_dims`, `m_args`, `m_body`) используют `SyntaxSeq`.
- Внутренние методы mmproc работают напрямую с `SyntaxSeq`, извлекая `Lexeme` через `Token::as_lexeme()` где необходимо.

## Иерархия узлов AST

`AstNodeBase` — базовый класс для всех узлов AST. Хранит **только** `m_kind` и
`TermPtr m_term` — указатель на исходный синтаксический узел (Term), из которого
построен AST-узел. Текст (`text()`) читается из `m_term`. Диапазон (`range()`) для простых
узлов читается из `m_term`; составные узлы (Binary, control-flow, VarDecl, FuncDecl, MatchStmt)
переопределяют `range()` и вычисляют полный охват statement'а **на лету по узлам-детям**
(`Binary/ControlFlowStmt/IfStmt/MatchStmt/VarDecl::range` в `ast_nodes.cpp`). Для узла БЕЗ `m_term`
(ручной/test-only, синтетический) `range()` возвращает **невалидный range** `{}` (без EXPECT),
а `text()` — EXPECT. Это необходимо: родители считают свой охват по `child->range()` (см.
`spanOfNodes`), поэтому ручные дети обязаны «мягко» сообщать об отсутствии source-range.

**Две группы конструкторов (правило):** у каждого узла ровно две семьи, не смешиваются:
(1) терм-конструктор `X(Kind, TermPtr, Context* ctx = nullptr)` — данные (text/range/дети)
читаются из `m_term`; при `ctx != nullptr` узел сам рекурсивно строит детей через
`TermToAstConverter` (`convert`/`convertSeq`: Sequence→`m_body`, Binary→`m_left`/`m_right`);
используется TermID-visitor `TermToAstConverter`; (2) manual-конструктор без `TermPtr` — для ручного
создания (тесты), `text()` из Term недоступна (иначе `EXPECT`), `range()` возвращает невалидный range.
Гибриды вида `Binary(k, term, left, right)` / `HasText(k, text, term)` запрещены.
Рекурсивное построение детей — через класс `TermToAstConverter` (объявлен в
`ast/term_to_ast.hpp`) — **внутренний API ast_lib**: его вызывают терм-конструкторы узлов
(`ast_nodes.cpp`, тот же `ast_lib`), внешним потребителям использовать его не следует (публичный
вход конвертации — `TermToAstConverter::termToAst`).

**Конвертер НЕ мутирует исходный Term.** Расширенные диапазоны statement'ов вычисляются **на
лету** в override'ах `range()` узлов по ранжам их узлов-детей
(`Binary/ControlFlowStmt/IfStmt/MatchStmt/VarDecl/FuncDecl`).
`Term` остаётся неизменным после конвертации (проверяется тестом `ParserTest.ConverterDoesNotMutateTerm`).
Нереализованные TermID (с `Kind=Unimplemented` в `TERMS`: `AWAIT/YIELD/WHEN_ALL/WHEN_ANY/FILLING/PARENT`)
при конвертации (`convertForKind<Unimplemented>`) сообщают диагностику `Severity::Error` и отбрасываются
— тихих пустых узлов нет.

**Понижение (lowering):** реализовано в классах узлов согласно их Kind — каждый класс
переопределяет `virtual AstNodeBase::lower(AstNodePtr& self, LowerCtx& ctx)` (см.
`ast/lowering.hpp` + `src/ast/lowering.cpp`), рекурсивно понижая своих детей и вставляя
синтетические узлы (`SemicolonStmt`, `GotoStmt`/`LabelStmt`). `LowerCtx` (inFunction, funcName,
pendingContinue) и векторные помощники `lowerBody`/`lowerBodyNode`/`lowerNode` живут в компоненте
`ast`; семантический анализатор только запускает `lowerBody` на корневом векторе операторов.

**Текст и нормализация:** `Binary`/`JumpStmt`/`CallExpr` читают `text()`/`range()` из `m_term`.
Классы HasText-семейства (Literal, Sequence/ScopeBlock/ModuleNode, ArgNode, IdentName/IdentType/
Decl/VarDecl/FuncDecl, ContextMacro) хранят локальный текст в едином поле `m_text` —
терм-конструктор копирует текст из `m_term` и нормализует через `normalizeTermText`
(срез ведущего `:` у TypeName и хвостового `^`; признак `^`→attr::ReadOnly применяется отдельно
в `convertAttrsToNode`). Для калле вызова (`obj.method^()`, `f^()`) `^` — валидный
immutable-квалификатор: `canHaveImmutableQualifier(CallExpr)=true`, поэтому диагностика
«Immutable qualifier...» не срабатывает, а `attr::ReadOnly` ставится на ВЫЗОВ (CallExpr) через
`convertAttrsToNode` и служит маркером const-вызова (кодген → `const_cast<const T&>(obj)`).
Имя VarDecl/FuncDecl/ArgNode для операторных термов (`:=`, `::=`,
ARGUMENT) берётся из `m_left` (fallback — `term->getText()`). Для ручных узлов `range()` без
Term возвращает невалидный range (без EXPECT).
`AstNodeAttr` — промежуточный класс, наследующий `AstNodeBase` и добавляющий
поддержку атрибутов (`m_attrs`). Документирующий комментарий — leaf-узел
`Document` (kind=Document) в классе `AstNodeAttr`: `text()` читает полный текст
комментария (string_view, включая маркеры `/**`, `///`, `///<`) из `m_term` без
нормализации/`^`-анализа; `lower()` — унаследованный no-op.

**Доступ к телу через virtual-аксессор:** `AstNodeBase::as_sequence()` / `const`
(аналог `as_attr()`) возвращает узел как `Sequence*` (или `nullptr` для листьев).
`Sequence` переопределяет его. Обходчики (напр. `collectBodyStatements` в транспиляторе)
получают `m_body` через аксессор без kind-`static_cast`; kind-фильтрация остаётся через
`is_block_kind` (Attr — не блочный).

**Единый dump-формат:** `detail::dumpQuotedName(kind, text, indent, prefix)` (token_base.hpp)
формирует заголовок `Name 'text'` (prefix — напр. `:` для TypeName); используется в
`IdentName/IdentType/ArgNode/ModuleNode/Decl::dump`. Имя выводится однократно.

### Полная иерархия

Полная иерархия `AstNodeBase → AstNodeAttr → HasText → ...` и состав полей — в `ast/ast_nodes.hpp`
(а также `ident_name.hpp`, `token_type.hpp`). Ключевые неочевидные моменты:
- `HasText` — единый носитель текста (`text()` из `m_text`); узлы без `m_text` читают текст из `m_term`.
- Листья `Program|VarRef|EmbedExpr|EnumLiteral|Document|...` — `AstNodeAttr`; бинарные kinds
  (`TypeDecl|NameDecl|AssignOp|...|ArrayAccess`) — `Binary`; `sequence|Attr|StructDecl|...|Tuple` — `Sequence`.
- Синтетические (вставляются lowering): `LabelRef` (`GotoStmt`/`LabelStmt`, range невалиден), `SemicolonStmt`.
- Детерминированный класс узла задаётся **ВТОРЫМ полем `PARSER_TOKEN_KINDS`**, а не вручную (см. Facts).

**Детерминированный класс узла (kind→класс):** конвертация в `ast/term_to_ast.cpp` строится как
класс-`TermID-visitor` `TermToAstConverter`: вход — `dispatchTerm`, генерируемый из X-макроса
`TERMS` (по методу `visit_<NAME>` на каждую пару `_(NAME, Kind)`). **Конвертер выполняет
ТОЛЬКО класс-селекцию узла; раскладку детей строит сам терм-конструктор узла**
`X(Kind, TermPtr, Context*)` (рекурсивно через `convertChild`/`convertChildren`). Generic-путь
`TermVisitorDefault::convertForKind` берёт класс узла ТОЛЬКО из `PARSER_TOKEN_KINDS`:
`make_shared<node_type_for_kind_t<Kind>>(Kind, term, &ctx)` (для бинарных kinds через
`if constexpr std::is_same_v<node_type, Binary>` дополнительно расширяется range терма).
Класс-селекция (спец-оверрайды `visit_<NAME>`), где один TermID неоднозначен по классу:
- `Ident → CallExpr | IdentName` (структурный предикат «есть конвертируемые дети»);
- `CREATE_NAME → FuncDecl | VarDecl` (`:=` — оператор объявления функции И переменной:
  сигнатура функции в `m_left` (`m_left->isCall()`) → FuncDecl, иначе → VarDecl);
- `CREATE_TYPE → Binary(TypeDecl)` (`::=` — оператор синонима типа; NATIVE не выделяется);
- `ARGUMENT → ArgNode` (ЕДИНЫЙ узел аргумента: имя в m_left, тип в m_type, значение в m_right);
- `MODULE → IdentName | ModuleNode` (isCall + непустой m_sequence);
- `DICT → DictLiteralNode` (подкласс `Sequence` с полем `m_type` — аннотация типа литерала,
  `nullptr` = словарь; интерпретируется анализатором по типу из реестра) — элементы строятся из
  канонических пар (name, term) грамматики `args` (argName из parser.y) и нормализуются к ЕДИНОЙ
  форме `Binary(AssignOp)` (left=Ident-метка или пустой, right=значение) — отдельного пост-прохода
  нормализации нет. Никаких строковых дискриминаторов ("Tuple") нет: класс (кортеж/словарь/каст)
  определяет анализатор по типу из реестра.
- `RANGE → RangeExpr` (подкласс `Sequence` с полем `elementType` — элементный тип диапазона,
  вычисленный анализатором join'ом типов операндов; `m_body=[start, stop, (step)]` из `m_args`
  терма `range`). Доп. слот `operandTypes` — явные аннотации типа операндов (`stop:Type`, напр.
  `0..100:Rational`), переносимые конвертером (`visit_RANGE`) из `m_type` терма-операнда для
  учёта при join (аннотация `:Rational` делает элементный тип Rational). Тип выражения —
  параметризованный структурный `Range<Elem>` (registry `getOrCreateRangeType(elementType)`),
  по которому кодогенерация эмитит `trust::Range<ElemCpp>`.
- `STRWIDE`/`STRCHAR` с `m_args` (правило `string: strtype call`) → `CallExpr` (callee = `Literal`
  StrWide/StrChar) — строка как формат-строка `"{}"(args)` / `'{}'(args)`;
- `TYPE` с `m_args`: терм-слой делает ТОЛЬКО механическую раскладку, класс узла определяет
  анализатор по СЛОТУ (тип/значение) и типу из реестра:
  - все аргументы — ТИПЫ (`Tuple(:Rational, name:Type)`) → параметризованная аннотация `IdentType`
    с параметрами (позиционные → IdentType, именованные → ArgNode(name, type));
  - иначе (аргументы — значения/имена-переменные/литералы/вызовы: `:Tuple(1,2)`, `:Tuple(n, n)`,
    `:Int8(x)`, `:Point(a, b)`) → ЕДИНЫЙ узел `DictLiteralNode(m_type=TypeName, элементы=имя=значение)`.
    `:Tuple(n, n)` — это СОЗДАНИЕ кортежа из значений (аналог вызова функции), а не аннотация.
    В value-слоте анализатор по типу из реестра решает кортеж (kind=Tuple) / каст / конструктор;
    в type-слоте аннотация обрабатывается `resolveType`. Никаких сравнений имён типов и эвристик
    по числу аргументов нет.
  Каст/конструкция выполняется через типизированный `DictLiteralNode` (отдельного `CastExpr` нет).

Раскладка детей по классам: `Sequence`→`m_body`, `Binary`→`m_left`/`m_right`,
`IdentType`→`m_dims` (из `term->m_type`, ARGS `[...]`)/`m_params` (из `term->m_args`, call `(...)`),
`CallExpr`→`m_callee`/`m_args`, `FuncDecl`→`m_params`/`m_type`/`m_body` (функция = CREATE_NAME
с сигнатурой в `m_left`; мутация `m_mapperRange`=[имя, оператор], без тела — признак функции),
`VarDecl`→`m_type`/`m_initializer` (+ семантическое поле `inferredType` — выведенный конкретный
тип нетипизированной переменной, заполняет `NameResolutionPass`, читает транспилятор),
`ArgNode`→`m_type`/`m_value`. Это соответствует
инварианту: разные kinds с одинаковой формой данных используют ОДИН класс (`node_type` из
`PARSER_TOKEN_KINDS`); kinds «с детьми/телом» (`sequence|Attr|StructDecl|StructField|EnumDecl|EnumMember|TryCatchStmt|
CatchBlock|RefMakeExpr|RefTakeExpr|ArrayInit|DictLiteral|Tuple|Ellipsis`) → `Sequence`;
бинарные → `Binary`; leaf-kind'ы (`Program|VarRef|EmbedExpr|EnumLiteral|BlockStmt|
ThenBlock|ElseBlock|WhileElseBlock|MatchingCase|MatchingElseBlock`) → `AstNodeAttr`. Отдельные
классы остаются там, где есть доп. поля: `ScopeBlock` (+m_blockCounter), `ModuleNode`
(+m_moduleIndex), `IdentName`, `IdentType`, `Literal`, `ArgNode`, `FuncDecl`, `VarDecl`,
`RangeExpr` (+elementType, +operandTypes),
`JumpStmt`, `ControlFlowStmt`/`IfStmt`/`WhileStmt`/`DoWhileStmt`, `MatchStmt`, `CallExpr`.

`ContextMacro` (kind=`ContextMacro`) — лист-маркер контекст-макросов
(`@::`/`@__NAMESPACE__`, `@__FUNCTION__`, `@__FUNCSIG__`, `@__FUNCDNAME__`); `text()` — имя
макроса с возможными ведущими маркерами стрингификации (`@#`/`@#'`/`@#"`). Создаётся парсером
из терминала `MACRO_CONTEXT` (термин `_(MACRO_CONTEXT, ContextMacro, T)`). Это **транзитный** узел: раскрывается в семантике в том же обходе
`NameResolutionPass` (в `Literal(StrChar)` или `IdentName`) и до транспилятора не
доходит (его `visit_ContextMacro` = `FAULT`).
`SemicolonStmt`/`LabelRef` — отдельные классы СИНТЕТИЧЕСКИХ узлов lowering (парсер их не создаёт;
generic-путь `TermToAstConverter` имеет uniform-терм-конструктор-заглушку `(Kind, TermPtr, Context*)`, чтобы
`TermToAstConverter` компилировался). `LabelRef` покрывает ДВА kinds — `GotoStmt` (`goto name;`)
и `LabelStmt` (`name:;`): они несут одинаковые данные (одно имя метки), поэтому один класс
по конвенции «одинаковые kinds с одинаковой формой данных → один класс».

`HasText` — промежуточный класс-«носитель текста»: концентрирует поле `m_text` и override
`text()` для узлов, хранящих текст локально (в отличие от `Binary`/`JumpStmt`, читающих
`text()` из `m_term`). **Единый** носитель текста в иерархии: помимо Literal/Sequence/ArgNode/
ContextMacro его использует и `IdentName` (имя в `m_text`, не в отдельном `m_name`) — и,
через него, `IdentType`/`Decl`/`VarDecl`/`FuncDecl`. `LabelRef` — отдельный класс
(своё `m_name`) как СИНТЕТИЧЕСКИЙ узел метки.

### Диспетчеризация по типу узла (kind-visitor)

`include/ast/kind_visitor.hpp` — единая диспетчеризация AST-узлов ПО KIND (не по классу).
Классы AST (`Binary`, `AstNodeAttr`, …) — это контейнеры данных (формат хранения); семантика
узла целиком в `ParserToken::Kind`. Поэтому visitor строится по kind:

- `KindVisitor` — абстрактный контракт: по одному типизированному методу
  `visit_<Kind>(const <класс>&)` на каждый kind (one kind → one class). Основные
  потребители (`SemanticAnalyzer`, `CppTranspiler`) наследуют ЕГО и реализуют все
  55 метода (no-op для неиспользуемых kinds). «Не переопределил → не компилируется».
  Генерируется X-макросом `PARSER_TOKEN_KINDS`.
- `dispatchKind(node, visitor)` — исчерпывающий `switch(kind)` БЕЗ default (генерируется из
  `PARSER_TOKEN_KINDS`); `static_cast` по kind всегда однозначен. Для `Kind::END` — FAULT.
- Используется в `SemanticAnalyzer::analyzeNode` и `CppTranspiler` (см. `src/semantic/analyzer.cpp`,
  `src/transpiler/transpiler.cpp`). Тот же механизм ляжет в основу будущих анализатора/оптимизатора.

Каждый `ParserToken::Kind` статически маппится на C++ класс через `NodeTypeForKind<K>`,
генерируемый X-макросом `PARSER_TOKEN_KINDS` в `token.hpp`. Несколько Kind могут
маппиться на один класс (например операторные kinds → `Binary`, `ReturnStmt`/`ThrowStmt` → `JumpStmt`),
но каждый kind имеет СВОЙ метод `visit_<Kind>`, поэтому диспетчеризация идёт по kind.

### Операторные kinds и бинарность

Единый kind `BinaryOp` заменён на операторные kinds (`TypeDecl`, `NameDecl`, `AssignOp`,
`MathOp`, `BitwiseOp`, `CompareOp`, `LogicalOp`). Тип операции — сравнением `kind()` с
конкретным kind (например `TypeDecl` для `::=`). Текст оператора берётся из `m_term->getText()`.
Проверка «бинарный ли узел» выполняется в
generic-пути `TermVisitorDefault::genericNode` через `if constexpr (std::is_same_v<node_type, Binary>)`
(compile-time, по `node_type` из `PARSER_TOKEN_KINDS`). `is_block_kind` остаётся (генерируется
из `PARSER_TOKEN_KINDS` по `node_type`). Диспетчеризация `TermID→Kind` — из единого X-макроса
`TERMS` (`include/syntax/term_types.h`, записи `_(NAME, Kind[, T])`): `dispatchTerm` в
`term_to_ast.cpp` (записи с `Kind=Unimplemented` (`AWAIT/YIELD/WHEN_ALL/WHEN_ANY/FILLING/PARENT`)
сообщают пользовательскую диагностику `Severity::Error` с позицией
«конструкция '…' не реализована» и возвращают nullptr через `convertForKind<Unimplemented>`;
`TermID::END` — FAULT). Конвейер (pipeline) при `errorCount>0` после ParseAST не запускает
semantic/transpile. Ручные switch-списки не поддерживаются.

Терм-конструкторы узлов строят детей через свободные хелперы `convertChild(ctx, term)` /
`convertChildren(ctx, term, out)` (обёртки над `TermToAstConverter::convert`/`convertSeq`,
`ast/term_to_ast.hpp`) — это устраняет дублирование `TermToAstConverter conv{ctx}; ...`
в `ast_nodes.cpp`. `convertModuleBody(ctx, term, out)` строит тело модуля: SEQUENCE-термы
рекурсивно разворачиваются (`convertSeq` → `flattenInto`) в top-level операторы, а BLOCK-термы
(пользовательские скоупы) сохраняются как `ScopeBlock` — границы блоков `{ ... }` не теряются.

### Распределение полей по классам

- Поля AST распределены по специализированным классам; единого god-class `AstNode` нет.
- `AstNodeBase` хранит только `m_kind` и `TermPtr m_term`; `text()`/`range()` читаются из Term.
- `m_text` сохранён только там, где это семантически нормализованная строка: `IdentName`,
  `ArgNode`, `Sequence`/`ScopeBlock`/`ModuleNode` (метка/имя), `Literal`.
- `m_left`/`m_right` — только у `Binary` (бинарные kinds, MemberAccess, ArrayAccess).
- `m_callee`/`m_args` — только у `CallExpr` (CallExpr).
- `IdentName` наследует `AstNodeAttr`.
- `ArgNode` — ЕДИНЫЙ узел позиции списка аргументов (параметр функции, элемент словаря/enum/variant,
  аргумент вызова): text()=имя ("" — безымянный), +m_type (явный тип), m_value (значение), resultType
  (разрешённый тип значения, ставит семантика).
- `ScopeBlock` — отдельный класс для блоков с меткой, наследующий `Sequence`.
- Все специализированные классы объявлены в `include/ast/ast_nodes.hpp`, реализации — в `src/ast/ast_nodes.cpp`.
- `syntax_lib` больше не зависит от `ast_lib`; `ast_lib` линкуется с `syntax_lib` PUBLIC
  (ast хранит `TermPtr`). Разрыв циклической зависимости убран.

Объявления классов: `ident_name.hpp`, `token_type.hpp`, `ast_nodes.hpp`.
Реализации: `ident_name.cpp`, `token_type.cpp`, `ast_nodes.cpp`, `token_base.cpp`.

## Система модулей

Система модулей обеспечивает загрузку исходных файлов (`source`) и бинарных
разделяемых библиотек (`binary`), дедупликацию загрузки и защиту от
циклических зависимостей.

### ModuleRecord

`ModuleRecord` — запись в реестре, существующая в единственном экземпляре
для каждого уникального `moduleId` (канонический путь или имя).

Поля:
- `m_moduleId` — канонический идентификатор модуля
- `m_handle` — `std::variant<MapperFile, void*>` (для source-файлов или dlopen handle)
- `m_body` — исходное Term-тело модуля (результат макропроцессинга). Единственное
  хранимое поле-«тело» (аналог `ModuleNode::m_body`): хранится как `TermPtr`,
  а в `AstNode` конвертируется рекурсивно при построении `ModuleNode`.

### ModuleRegistry

`ModuleRegistry` определён в `include/pipeline/module_registry.hpp` (компонент **pipeline**).
Реестр загруженных модулей на динамическом массиве. Идентификация модулей — только по индексу (`std::size_t`). Доступен через `ModuleLoader` (`Context::loader()`).

Методы:
- `getOrLoad(moduleId)` — получить существующий загруженный модуль
  или создать новую запись. FAULT при циклической зависимости
  (запись существует, но `m_body` ещё не заполнен). Возвращает индекс.
- `isLoaded(index)` — проверка по индексу (наличие заполненного `m_body`).
- `setBody(index, term)` / `body(index)` — установить/получить Term-тело модуля.
- `moduleName(index)` — получение имени модуля по индексу.
- `count()` — количество зарегистрированных модулей.

Публичный доступ — только по индексу. `moduleId` используется ТОЛЬКО при первичной загрузке.

### ModuleNode

`ModuleNode` — AST-узел, наследник `Sequence`. Создаётся при загрузке модуля
(source). Хранит `m_moduleIndex` (`std::size_t`) — индекс записи в `ModuleRegistry`.
Имя модуля доступно через унаследованный `text()`.

Дополнительные поля:
- `m_exports` (`std::vector<TermPtr>`) — **отфильтрованный** экспорт-интерфейс конкретного сайта
  импорта (декларации-термы экспортов, фактически вносимые в скоуп). Заполняет анализатор
  (`resolveImportExports` в pipeline) из `collectExportedDecls` по маскам `\module(...)`.
- `m_isImport` — true для сайта импорта (`\module(...)`, терм-конструктор), false для корневого
  модуля главного файла.
- `m_importMasks` — список glob-масок фильтра интерфейса (пусто = все экспорты).

Поток создания ModuleNode:
1. `ModuleLoader::parseSourceModule()` парсит модуль (`Parser::ParseWithSource`,
   `expand_module=true`) и сохраняет исходное Term-тело в `record->m_body`
   (без пре-конвертации в AST).
2. Построение `ModuleNode(moduleIndex, term)`: его `m_body` заполняется через
   `convertModuleBody(ctx, record->m_body, out)` — рекурсивной конвертацией `record->m_body`
   в AstNode. SEQUENCE-термы (синтаксические контейнеры) рекурсивно разворачиваются
   (`convertSeq`/`flattenInto`) в top-level операторы: контейнер тела модуля НЕ становится
   отдельным `ScopeBlock`-узлом (модуль сам открывает глобальный скоуп), а пользовательские
   `{ ... }` (BLOCK-термы) сохраняются как `ScopeBlock` (область видимости блока
   не теряется при транспиляции).

При повторном использовании того же модуля создаётся новый `ModuleNode`,
но ссылающийся на ту же запись в реестре (общий `m_body`).

### Детекция циклических зависимостей

При вызове `getOrLoad()`: если запись уже есть в `m_modules`, но её
`m_body` ещё не заполнен, значит модуль в процессе загрузки — FAULT.

### Модуль в иерархии AST

`ModuleNode` (kind=ModuleDecl): `m_moduleIndex`, `m_isImport` (сайт импорта `\module(...)`), `m_exports`, `m_importMasks`, `text()`=каноническое имя модуля, `m_body` (от Sequence). Состав полей — в `ast_nodes.hpp`.

## Система типов

Trust-lang использует **закрытую систему типов**. Любой новый тип данных, создаваемый пользователем, обязан наследоваться от одного из уже существующих (расширять его). Это позволяет писать обобщённый код, работающий с любым совместимым типом данных.

Функции, объявленные без явного указания типов (или работающие с несколькими обобщёнными типами), являются неявными шаблонами, которые компилятор автоматически инстанцирует для одного или нескольких конкретных типов по мере необходимости.

Для полиморфизма несвязанных абстракций (когда типы не находятся в одной ветке наследования, но обладают схожим поведением) используются операторы  **утиной типизации** как во время компиляции, тк и во время выполенния.

Для каждого типа можно определить **подтипы** (`SubType`) — типы данных, область допустимых значений которых ограничена дополнительными предикатами. На аппаратном уровне они идентичны базовым типам и служат исключительно для доказательства корректности программы на этапе компиляции.

### Базовые и аппаратные типы данных

- **Примитивный (нативный) тип** — тип данных, напрямую поддерживаемый архитектурой процессора (CPU/GPU). Обычно имеет фиксированный размер в байтах.
- **Тип-значение (Value Type)** — тип, переменные которого хранят данные непосредственно. При копировании создается независимая копия. Разрешено создание временных неизменяемых заимствованных ссылок на Value-типы (аналог const T& в C++ или &T в Rust), но запрещено их преобразование в управляемые ссылки (Shared Type), что гарантирует, что время жизни ссылки не превышает время жизни локальной переменной.

- **Ссылочный тип (Reference Type)** — тип, переменные которого хранят не само значение, а ссылку на объект. Копирование копирует только ссылку.
- **Сильная ссылка (Shared Type)** — ссылочный тип, управляющий жизненным циклом данных. Гарантирует отсутствие циклических ссылок, что достигается за счет статической проверки графа отношений владения для типов на этапе компиляции. 
- **Слабая ссылка (Weak Type)** — ссылочный тип, который не влияет на время жизни объекта (не владеет им). Может принимать значение `null`.
- **Захваченная ссылка (Lock Reference)** — временный объект с разыменованной ссылкой на данные, которая гарантированно не может быть `null`. Создаётся на основе сильных или слабых ссылок (с обеспечением атомарности и захватом объекта синхронизации для многопоточного доступа). Существует только в виде локальной переменной с временем жизни до конца текущей области видимости (RAII).
- **Функция (Function)** — указатель на фрагмент исполняемого кода.
- **Замыкание (Closure)** — функция, захватывающая переменные из своего лексического окружения и сохраняющая доступ к ним даже после уничтожения исходной области видимости.
- **Виртуальная системная переменная «результат выполнения последней операции»** — создаваемый компилятором алиас временной переменной (доступной только для чтения), в которую записывается результат вычисления последнего выражения.

### Структурные и объектно-ориентированные абстракции

- **Пространства имён (`namespace`)** — предотвращают коллизии имён в глобальной области видимости.
- **Модули (`module`)** — иерархическая организация кода на уровне файловой системы (исходные файлы или скомпилированные динамические библиотеки с декларативным API).
- **Шаблоны (`Template`)** — средство обобщённого программирования.
    - **Коллекции** — абстракции для хранения данных других типов.
    - **Итераторы** — абстракции для последовательного обхода коллекций.
    - **Ленивые итераторы** — итераторы для ленивых вычислений (генерация «на лету», чтение из сети, трансформации без выделения буфера памяти).
- **Структуры (`Struct`)** — иерархические абстракции для простых данных (POD) без виртуальных функций.
- **Классы (`Class`)** — структуры данных с полиморфизмом времени выполнения, реализованным через виртуальные функции и таблицы виртуальных методов (`vtable`).
- **Перечисление (`Enum`)** — фиксированный набор именованных констант.
- **Кортеж (`Tuple`)** — упорядоченный набор данных фиксированной длины без создания отдельного класса.
- **Типобезопасное объединение (`Variant`)** — контейнер, который хранит значение одного из нескольких типов и автоматически управляет их конструкторами/деструкторами.
- **Тензоры (`Tensor`)** — многомерные массивы для примитивных типов данных (`libtorch`).
- **Закрытые области видимости (Closed Variable Scopes)** — области видимости, в которых обращение к внешним (нелокальным) переменным требует их явного импорта. Являются концепцией «ООП наоборот» (ограничивают доступ кода к внешнему окружению). На этой основе реализуются чистые функции и контроль обращения к данным из потоков.

## Базовые элементы синтаксиса (AST-уровень)

- **Объявления (`Declarations` / `Decl`-узлы)** — узлы AST, вводящие новые имена (переменные, функции, типы). Не выполняют вычислений в рантайме.
- **Выражения (`Expressions` / `Expr`-узлы)** — вычисляемые конструкции, возвращающие значение определённого типа.
- **Инструкции (`Statements` / `Stmt`-узлы)** — формируют поток выполнения. В качестве возвращаемого значения используют результат последнего выражения.

#### Узлы объявлений (`Declarations` / `Decl`-узлы)
- **Type Declarations (Объявления типов):** Классы, структуры, объединения, перечисления.
- **Variable Declarations (Объявления переменных):** Локальные/глобальные переменные, поля классов (`FieldDecl`).
- **Function / Method Declarations (Объявления функций/методов):**
    - `FunctionDecl`: Свободная функция.
    - `CXXMethodDecl`: Метод класса с неявным параметром `this`.
    - `ConstructorDecl` / `DestructorDecl`: Методы жизненного цикла.
    - `Closure`: Замыкание.
- **Объявления и инстанцирования шаблонов.**

#### Выражения и операторы (`Expressions` / `Expr`-узлы)
- Операторы присваивания значения (создание объектов, присвоение значения и обмен значениями, на основе которое реализована `move` семантика).
- Арифметические и логические операторы.
- Операторы получения ссылки и операторы захвата (разыменования) ссылки.
- Операторы сравнения и побитовых операций.
- Вызовы функций.
- **Selection Statements (Ветвление):**
    - Условный оператор: `if -> then`, `else if -> then`, `else -> then`.
    - Выражение оценки (`Estimate`): Аналог оператора `switch`/`match` с явным указанием способа сопоставления значения с образцами:
        - `==>` — проверка на равенство с автоматическим приведением типов;
        - `===>` — проверка на точное равенство (включая совпадение типов);
        - `~>` — сопоставление по имени типа (номинальная типизация);
        - `~~>` — утиная типизация (сопоставление по набору полей с автоматическим приведением типов);
        - `~~~>` — строгая утиная типизация (сопоставление по набору полей с точным совпадением типов).
- **Циклы (`Loop`):**
    - С постусловием (`do-while`) и предусловием (`while`). Цикл `while` поддерживает ветку `else`, выполняющуюся, если условие входа изначально было ложным.
    - Обход итераторов.
- Преобразования типов и литералы.
- Генераторы (`comprehensions`) для заполнения контейнеров.
- **Специальные узлы AST:** Пропуск `_`, диапазон `..`, многоточие `...`.

#### Инструкции (`Statements` / `Stmt`-узлы)
- **Модуль (`Module`):** Исходный код модуля, состоящий из последовательности узлов AST.
- **Составной оператор / Блок кода (`Compound Statement`):** Группировка нескольких инструкций. Возвращает результат последнего выражения. Может быть безымянным `{ ... }`, именованным `ns { ... }` или анонимным `_ { ... }`.
- **Операторы перехода (Jump Statements):** `ReturnStmt`, `BreakStmt`, `ContinueStmt`, генерация исключений (`throw` / `rethrow`).
- **Блоки обработки исключений (Try Blocks):** `{+ ... +}`, `{- ... -}`, `{* ... *}`. Возвращают в системную переменную либо исключение, либо результат последнего выражения.
- **Менеджер контекста:** Захватывает одновременно несколько объектов синхронизации для выполнения группы действий. Поддерживает ветку `else` при ошибке захвата одной из ссылок.

## Дополнительные семантические механизмы

### Возврат последнего значения в блоках кода
На этапе анализа возвращаемого значения из блока кода компилятор автоматически внедряет локальную переменную с зарезервированным системным именем. Любой узел AST, прерывающий последовательный поток выполнения (такой как `return`, переходы или генерация исключения), а также логический конец блока, сохраняют результат вычисления последнего выражения в эту переменную.

### Дополнительная семантическая информация (Атрибуты AST)

**Примечание:** Код системы атрибутов находится в компоненте `ast` (`include/ast/attr.hpp`, `attr_pool.hpp`, `attr_builtin.hpp`, `attr_parser.hpp`).

Любой узел AST может быть помечен **атрибутами** — метаданными времени компиляции, которые передают дополнительную информацию компилятору, статическому анализатору или линкеру. Каждый атрибут идентифицируется `AttrId` (`uint32_t`):

`AttrId` (`uint32_t`): биты 0–29 — индекс в AttrPool, бит 30 — Builtin, бит 31 — Manual.

- Бит **Builtin** проставляется при регистрации и выводится из `Attr::m_def_range.isInvalid()`: встроенные атрибуты регистрируются через `register_builtin_attr` (без диапазона), пользовательские — через `register_attr` с валидным `MapperRange` места определения.
- Бит **Manual** проставляется автоматически при добавлении атрибута узлу через `add_attr` (ручная установка из `@[...]` или `^`). Для автоматически добавляемых атрибутов передаётся `false` вторым параметром: `add_attr(id, false)`.
- Поиск атрибута (`has_attr`) выполняется по базовому индексу без учёта битовых флагов.

Каждый атрибут хранит `Attr::m_def_range` — диапазон места определения в исходном коде:
- для пользовательских атрибутов — валидный `MapperRange` (передаётся в `register_attr`);
- для встроенных атрибутов — невалидный (`MapperRange{}`).
`parse_attr(ctx, range, name, params)` принимает `Context&`, `MapperRange`, имя и опциональные параметры и возвращает `std::optional<AttrId>`: она только ищет атрибут по имени в `ctx.attrs()`. Если атрибут не найден — выдаётся диагностическая ошибка "unknown attribute"; регистрация выполняется отдельно (`register_attr`/`register_builtin_attr`).

К встроенным атрибутам относятся:

#### Многопоточность без гонок данных (Data-Race Free Concurrency)

Для обеспечения безопасности многопоточного программирования на уровне компиляции используются определённые атрибуты:
- **Thread** - маркирует функции, выполняющиеся в отдельных потоках.
- **Send (Передаваемые типы)** - Маркировка данных, владение которыми может быть полностью передано в другой поток.
- **Sync / Threadsafe (Синхронизируемые типы)** - Маркировка данных, которые могут быть разделены между несколькими потоками одновременно.
- **Read-Only / Immutable (Неизменяемые типы)** - Маркировка данных, которые гарантированно не могут быть модифицированы после создания.


#### Защита стека от переполнения
Для предотвращения ошибок сегментации памяти (`Segmentation Fault`) при глубокой рекурсии в языке предусмотрен ручной и автоматический контроль размера стека.

Перед вызовом защищаемой функции выполняется проверка доступного пространства стека. Если свободного места недостаточно, программа генерирует стандартное исключение, которое может быть перехвачено и обработано на уровне приложения.

- **Ручной контроль:** Вызов служебной функции с явным указанием требуемого размера памяти.
- **Автоматический контроль:** Сопоставление текущего указателя стека с максимальным размером фрейма, вычисленным на основе данных из секции `.stack_sizes` (требуется компиляция с флагом `-fstack-size-section`).
- **Оптимизация:** Компилятор не генерирует рантайм-проверки для нерекурсивных функций с известным на этапе компиляции размером фрейма, добавляя проверки только для рекурсивных вызовов и динамической аллокации на стеке.

### Система эффектов (Effect System)
Для обеспечения строгой чистоты кода на уровне семантического анализа введена **Система эффектов**. Trust-lang разделяет функции по спектру их влияния на состояние системы на три категории:
- Математически чистые (константные `func^(arg) :- ...`): Не имеют доступа к внешнему состоянию. Возвращают гарантированно одинаковый результат при одинаковых аргументах. Разрешена оптимизация времени компиляции (CTFE) `__attribute__((const))`.
- Без побочных эффектов (не константные `func(arg) :- ...`): Имеют доступ **только для чтения** к глобальному состоянию и внешним ресурсам. Запрещено любое изменение нелокальных данных. Разрешена оптимизация общего исключения подвыражений (CSE) `__attribute__((pure))`.
- Стандартные функции и замыкания - Имеют право на чтение и запись любого доступного состояния в соответствии с правилами потокобезопасности.


### Формальный анализ и контрактное программирование

Поддерживаются декларативные контракты на уровне синтаксиса сигнатур функций. Для этого используются макросы `@require` (предусловие) и `@ensure` (постусловие) между объявлением и телом функции.

Формальный анализ доказательства корректности реализуется с помощью статическую проверку динамических выражений **AoRTE** (*Absence of Run-Time Errors*), которая не дает ложных срабатываний (если компиляция успешна, то неопредленого поведения рантайме в рамках доказанных свойств гарантированно нет).

Формальный анализ не пытается доказать абсолютную правильность всей программы. Он используется локально для доказательства определённых пользователем утверждений с помощью:
*   Контрактов функций `@require` и `@ensure`.
*   Внутренних утверждений в коде через `@trust`.

Анализ выполняется во время компиляции программы за счет встроенного SMT-решателя или с помощью использования внешних инстурментов (например, Z3). Неконстантные выражения, используемые в контрактах, должны быть вычислимы на уровне типов данных или ограничены предикатами подтипов (`SubType` для  сужения диапазона допустимых значений переменных до интервала).

#### Локальный AoRTE и утиная типизация в рантайме

Поскольку контрактная верификация (AoRTE) применяется локально к конкретным утверждениям, конфликт разрешается разделением кода на верифицируемые (доказуемые) зоны и динамические зоны. 

Если в функции используется динамическое сопоставление по утиному типу (~~> или ~~~>), SMT-решатель не пытается анализировать внутреннюю структуру объектов в рантайме. Вместо этого компилятор генерирует безопасное ветвление.

При использовании контрактов @require на границе динамического кода - Выражение сопоставления утиного типа транслируется в монадический контракт, и в случае несовпадения интерфейса в рантайме генерируется перехватываемое исключение, что предотвращает неопределённое поведение.

Компилятор преобразует это в безопасную проверку наличия членов структуры, гарантируя, что вызов метода или обращение к полю данных произойдёт только после успешной проверки. Локальное свойство AoRTE для этого блока доказывает, что «если выполнение дошло до этого места, то метод или поле данных  гарантированно существует».

## Обобщённый обход детей (children())

`AstNodeBase::children()` (`include/ast/ast_nodes.cpp`) возвращает вектор всех дочерних узлов
AST по kind (для листов — пустой). Это единый механизм полного обхода дерева, используемый
семантикой (`NameResolutionPass`), гарантирующий посещение каждого узла независимо от kind.

Покрытие:
- Sequence/блоки/модуль (sequence, Attr, ScopeBlock, ModuleDecl, ArrayInit, DictLiteral, Tuple,
  RefMakeExpr, RefTakeExpr, Ellipsis, TryCatchStmt, CatchBlock, EnumDecl/EnumMember,
  StructDecl/StructField) — m_body;
- Binary-выражения (AssignOp, MathOp, BitwiseOp, CompareOp, LogicalOp, MemberAccess, ArrayAccess)
  — m_left + m_right; для объявлений (TypeDecl, NameDecl) — только m_right (m_left — имя
  объявления, его не резолвим как переменную);
- CallExpr — m_callee + m_args; IdentType — dims/params;
- JumpStmt (return/throw/break/continue) — только m_value (m_label — метка, не выражение);
- VarDecl — m_type + m_initializer; FuncDecl — m_type + m_params + m_body;
  ArgNode — m_type + m_value;
- IfStmt/WhileStmt/DoWhileStmt — m_cond + m_body + m_else (+ elseifs у IfStmt);
- SemicolonStmt — m_expr; MatchStmt — m_value + patterns/body веток + m_default.

### Литералы и коллекции (единая классификация и форма элемента)

- `is_literal_kind(Kind)` — единый набор литералов (`IntLiteral|FloatLiteral|StrChar|StrWide|
  RationalLiteral`). Используется типизацией литералов, `resolvedType`/`dictElementType` и
  кодогенерацией (обёртка значения точным C++-типом в `trust::TypedValue`), чтобы классификация
  литералов жила в одном месте, а не дублировалась в потребителях.
- `is_collection_literal_kind(Kind)` — `DictLiteral|Tuple|ArrayInit`. Элементы литерала коллекции в
  `m_body` строятся из канонических пар грамматики `args` и приводятся к ОДНОЙ форме
  `ArgNode` (имя в text(), явный тип в m_type, значение в m_value) — см.
  `term_to_ast::visit_DICT`/`appendDictElementsFromArgs`. Это устраняет три формы
  (raw/AssignOp/ArgNode) и даёт семантике и кодогенерации единый способ чтения name/value.
  `DictLiteral` реализован end-to-end (trust::Dict); `Tuple` (kind выставляется анализатором из
  DictLiteral по типу из реестра) — std::tuple; `ArrayInit` — структура та же, кодогенерация —
  отдельной задачей (нужен рантайм-тип контейнера); `EnumLiteral` (Set) — плейсхолдер (leaf).
  Предикат используется семантикой (`dictSizeOf`, `dictFieldTypeOf`) и классифицирует все
  коллекции единообразно; `Tuple`-доступ (`t.name`/`t.N`) при этом идёт отдельным путём по
  структурному `TupleTypeData` (см. `resolveTupleAccess`).
  Тип значения элемента словаря — единый источник: семантика сохраняет его на элементе-ArgNode
  (`ArgNode::resultType` из `resolvedType`), транспилятор читает в `emitTypedDictValue` (покрывает
  литералы, вложенные словари и выводимые выражения — не только `Literal::typeId`).
- **Явный тип члена `name:Type`/`name:Type=value` (enum/variant) хранится в ArgNode.m_type** — это
  отдельный слот узла аргумента, а НЕ обёртка в значении и НЕ параллельный вектор (см.
  `term_to_ast::appendDictElementsFromArgs`). Чтение члена (имя/тип/значение) — напрямую из ArgNode:
  семантика (`analyzeEnumDecl`/`analyzeVariantDecl`) и кодогенерация (`emitVariantStruct`) читают
  `ArgNode.text()/m_type/m_value` без разворачивания. Для enum значения читаются из `EnumTypeData`
  (вычисленные скаляры); для variant значение — AST-выражение (ArgNode.m_value). Данные (тип)
  уже есть в `argTerm->m_type` (как у типизированных членов Tuple → `ArgNode(name, m_type)`).

## Facts and invariants

- **Массив (kind=ArrayInit) — node_type DictLiteralNode** (не Sequence), чтобы нести хвостовую
  аннотацию `]:Type` в m_type и интернированный тип в поле `arrayType` (DictLiteralNode).
  `term_to_ast::visit_TENSOR` строит его (как visit_DICT); элементы — ArgNode (позиционные,
  имя="", значение в m_value, явный тип в m_type). ArrayInit включён в `is_collection_literal_kind`.
- **Тип-вызов `:Type^(args)` / `:Type(args):Elem`** (visit_TYPE): единый `DictLiteralNode` с
  контейнером в m_type (const `^` → attr::ReadOnly) и хвостовой элементной аннотацией в
  `arrayElementAnnotation`. Размерности `[...]` (ARGS-терм) — аннотация (IdentType с dims).


> ⚠ trap: связь Kind → класс AstNode НЕ 1:1 — РАЗНЫЕ kinds ОБЯЗАНЫ иметь ОДИНАКОВЫЙ класс при одинаковой структуре данных. Отношение kind→класс задаётся ВТОРЫМ полем `PARSER_TOKEN_KINDS` (node_type). ЗАПРЕЩЕНО создавать новый класс под новый kind при той же структуре данных.

- **ПРАВИЛО (kind↔класс):** (см. ⚠ выше) AstNode — только контейнер данных; kinds «с детьми/телом» → Sequence, leaf → AstNodeAttr.
- **ИНВАРИАНТ (visit):** полный набор `visit_<Kind>` у каждого потребителя (SemanticAnalyzer, CppTranspiler) — осознанная compile-time проверка полноты, это НЕ дублирование кода. ЗАПРЕЩЕНО выносить no-op в default-базу — только явное переопределение в итоговом классе.
- **TermID→Kind:** согласованный путь — TermID→Kind в X-макросе `NL_TERMS`.
- **MODULE-конвертация в AstNode** — только рекурсивная конвертация данных модуля (TermPtr m_body); реальная загрузка файла `ctx.loader()` ЦЕЛИКОМ в pipeline. В ast_lib только общее рекурсивное построение Term→AstNode.
