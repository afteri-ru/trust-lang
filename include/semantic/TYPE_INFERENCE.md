# Вывод типов в TrustLang - архитектура и обоснование

Этот документ описывает, как TrustLang выводит и проверяет типы значений в выражениях
и почему приняты ключевые решения. Это архитектурный обзор (принципы и причины);
детали реализации - в коде и в `include/semantic/MEMORY.md`, `include/transpiler/MEMORY.md`.

---

## 1. Назначение

Типизация выражений решает три задачи:

1. Выводить **конкретные** типы значений и переменных, сводя их к минимальному
   обобщённому типу из истории присвоений - вместо универсального `std::any`
   (который дорог: рантайм-хранилище, `any_cast` на каждом использовании и не
   участвует в арифметике без явной распаковки).
2. Генерировать **корректный C++** для операторов с учётом типов операндов.
3. Проверять типы - прежде всего **сужение** в типизированные цели - с понятной
   диагностикой и быстрым исправлением.

---

## 2. Принципы

### 2.1 «Выведенный» vs «явный» тип переменной
Переменная, объявленная с аннотацией (`x:Type := …`), имеет **фиксированный** тип -
это контракт. Без аннотации (`x := …`) тип **выводится** и может уточняться по мере
поступления данных.

**Почему:** явная аннотация - обязательство пользователя, его нельзя расширять.
Выведенный тип - производный, его безопасно доуточнять без лишних аннотаций.

**Где живёт признак (архитектурный момент):** признак «выведенный/фиксированный» закодирован
битом `kInferredFlag` (бит 31 младшей половины) в самом `TypeId` (`withInferred`/`typeIsInferred`/
`clearInferred`, `types/type_id.hpp`). Структурная идентичность типа интернируется на **63 битах**
(TypeKind в старших 32 + registry_index в младших 31); флаг - ортогональный квалификатор и НЕ часть
ключа интернирования: один и тот же дескриптор общий для `id` и `withInferred(id)`. Все операции
идентичности снимают флаг (`getIndexFromId` маскирует в одном месте реестра, `getCanonicalTypeId`
возвращает структурный), поэтому сравнения каноникой не замечают бит. Так признак едет вместе с
типом во все потребители (словари, бинарные операции, join) без отдельного параллельного канала и
без рассинхрона.

### 2.2 Итоговый тип - на узле объявления; инвариант синхронизации
Разрешённый тип существует в двух представлениях:
- **живой** тип на символе - рабочее значение во время анализа (расширяется join-ом);
- **итоговый** тип на узле объявления (`VarDecl`) - то, что читает транспилятор.

**Почему два места:** анализ отделён от кодогенерации, и к моменту транспиляции скоуп-стек
уже разрушен (имя из popped-скоупа по имени не найти). Поэтому финальный тип переносится на
сам AST-узел - он переживает весь конвейер.

**Инвариант:** на завершении анализа итоговый тип узла равен финальному живому типу символа;
**единственный источник для транспилятора - узел**. Это исключает пере-резолв по имени в
кодогенерации и отделяет анализ от генерации.

### 2.3 LUB (join) по истории присвоений, монотонно за один проход
Выводимая переменная получает тип как наименьшую верхнюю границу всех присвоенных значений:
`x := 1` → Bool, `x = 1000` → Int16, `x += 50000` → Int32.

**Почему:** это ровно «минимальный обобщённый тип из истории» - покрывает все присвоения,
но не шире. `join` ассоциативен и коммутативен, поэтому накапливается монотонно в одном
проходе без пересмотра скоупа.

### 2.4 Пост-порядок: тип выражения зависит от типов детей
Тип составного выражения вычисляется после типов его подвыражений (`a + b` - после `a`, `b`).

**Почему:** гарантирует, что к моменту типизации родителя известны типы всех детей, без
отдельного многофазового анализа.

### 2.5 Семантика результата операций - как в C++
`Int16 + Int16 → Int32`, `Int32 + Int64 → Int64`, `//` → Int64, Compare/Logical → Bool;
если среди операндов есть число с плавающей точкой - результат имеет тип с плавающей
точкой **большей ширины** (по правилам C++: `Float32 + Float64 → Float64`).

**Почему:** TrustLang транслируется в C++, поэтому перевод операций тривиален и предсказуем -
без сужающих кастов результата и без расхождения между языковой и машинной семантикой.

### 2.6 Литералы
- `0`/`1` → **Bool**;
- строка в одинарных кавычках `'…'` → **StrChar** (узкая);
- строка в двойных кавычках `"…"` → **StrWide** (широкая);
- целочисленный (кроме 0/1) → минимальный вмещающий Int (`1000` → Int16);
- вещественный → Float64.

**Почему:** минимальный конкретный тип по определению литерала, сочетается с 2.3
(последующие присвоения расширят при необходимости). Float → Float64 - чтобы не терять
точность. Ширина строки задаётся кавычками на уровне лексера (`STRCHAR`/`STRWIDE`) и
кодируется в `Kind` литерала (`StrChar`/`StrWide`) - отдельный признак-флаг не нужен.

**Продвижение auto-Bool в арифметике:** тип Bool, **выведенный** из литерала `0/1` (или из
inferred-переменной), в арифметике продвигается по общим правилам приведения (C++ `bool→int`
→ Int32): `1 + 2` → Int32, `d := (1, 2); d[0] + d[1]` → Int32 (см. `semantic/MEMORY.md`). Явный
`:Bool` (или результат сравнения/логики) в арифметике - **ошибка компиляции** (нельзя привести).

### 2.7 Сужение в типизированную цель - ошибка по умолчанию + fixit
Присвоение значения с типом шире целевого в **явную** переменную:
- литерал, влезающий в цель → безопасно (значение известно на этапе компиляции);
- литерал, не влезающий / переменная шире → **ошибка** с fixit «use cast `:Type(expr)`».

**Почему:** trusted-гарантия - не допускать молчаливой потери данных: сужение при
runtime-неизвестном значении (`Int64 → Int8`) недетерминировано, поэтому ошибка, а не
предупреждение.

Строки: сужение **StrWide → StrChar** (широкая в узкую) всегда ошибка - значение литерала
на это не влияет (любой `"…"` уже широкий), а строкового checked_cast нет. Для узкой строки
используйте одинарные кавычки `'…'`.

### 2.8 Явный каст `:Type(expr)` → `trust::checked_cast<Type>(expr)`
Каст - осознанное преодоление сужения. Он транслируется в рантайм-хелпер `trust::checked_cast`,
который проверяет попадание значения в диапазон цели и при выходе делает abort (панику), а не
молча усекает.

**Почему:** `static_cast` в C++ не проверяет диапазон - это потеря данных без сообщения.
`checked_cast` сохраняет trusted-гарантию даже для runtime-неизвестных значений (корректность
значения - ответственность пользователя, но система не даёт «тихо срезать»). Поэтому fixit из
2.7 предлагает именно этот каст.

### 2.9 `std::any`-операнды → `std::any_cast<CommonType>(operand)`
Если один операнд - `std::any` (явный `:Any` или невыводимый), а другой - конкретный числовой,
результат = продвинутый конкретный тип, и `any`-операнд оборачивается в `std::any_cast`. Оба
операнда `std::any` → тип невыводим.

**Почему:** `std::any` не участвует в арифметике C++ - его нужно «распаковать» до конкретного
типа. Это же делает операции над `std::any` корректными. Конкретные типы по-прежнему
предпочтительнее (без any_cast и рантайм-перегрузки).

---

### 2.10 Аннотации типов на узлах AST - сознательное решение, НЕ side-table

Тип значений хранится как аннотация прямо на узлах AST (`Literal::typeId`, `VarDecl::inferredType`,
`Binary::lhsType/rhsType/resultType/commonType`, тип значения элемента словаря -
`Binary::resultType`). Это сознательное архитектурное решение, и его НЕ следует менять на
отдельную side-table (карту `node → TypeId` вне узлов). Причины:

- **Динамический вывод по ходу анализа.** Тип выводимой переменной меняется во время обхода
  (join по истории присвоений) и должен фиксироваться на самом узле в момент завершения его
  обработки, чтобы пережить конвейер. К моменту кодогенерации скоуп-стек уже сброшен; внешняя
  side-table, наполняемая анализом и читаемая кодогенерацией, создаёт второй канал синхронизации
  без выигрыша в корректности и с риском рассинхрона двух представлений одного типа.
- **Единственный источник для кодогенерации - узел.** Транспилятор читает финальные типы с узлов,
  а не пере-резолвит по имени. Это отделяет анализ от генерации.

Для элемента словаря тип значения сохраняется на элементе-AssignOp (`Binary::resultType` из
`resolvedType`) - единый источник для `emitTypedDictValue`, покрывающий литералы, вложенные
словари и выводимые выражения (не только `Literal::typeId`). Элементы литерала коллекции
строятся из канонических пар грамматики `args` к ОДНОЙ форме `Binary(AssignOp)` (left=метка/пусто,
right=значение) - см. `term_to_ast::visit_DICT`.

## 3. Поток данных

```
Parser → AST
         │
         ▼
Анализ (однопроходный, пост-порядковая типизация)
  ├- признак «выведенный/фиксированный» - на символе (2.1)
  ├- тип выражения = f(типы детей) (2.4), по C++-семантике (2.5)
  ├- литералы → минимальный конкретный тип (2.6)
  ├- выводимые переменные → join по истории (2.3)
  │    → итоговый тип пишется на узел объявления (2.2)
  └- сужение в явные цели → ошибка + fixit (2.7)
         ▼
Кодогенерация (после анализа)
  ├- декларации: итоговый тип с узла (2.2)
  ├- операторы: тип-зависимо; std::any → std::any_cast (2.9)
  └- каст :Type(expr) → trust::checked_cast (2.8)
```

## 4. Доступ к типам из анализаторов (хуков)

Хуки получают ту же информацию, что и кодогенерация:
- **признак** выведенный/фиксированный - через `Symbol` (события объявления/разрешения);
- **финальные типы** узлов - через query-сервис контекста анализа
  (`resolvedType(node)`): для объявления - итоговый тип с узла, для бинарной операции - тип
  результата, для литерала - его тип. Хук сохраняет узлы во время обхода и читает типы по
  завершении анализа.

## 5. Рантайм и `inferred`

Признак «выведенный/фиксированный» - **только compile-time** свойство; в рантайм-коде его нет.
Проверка типа динамического (`std::any`) значения в рантайме идёт по фактическому хранимому
типу (`std::any_cast` / `typeid`), а не по происхождению типа. `inferred` влияет только на
анализ: расширять ли тип (join) или считать фиксированным (сужение → ошибка).

## 6. Известные ограничения

1. Составные присваивания на `std::any` (`z += 2` при `z:Any`) дают невалидное rvalue
   (`std::any_cast<…>(c_z) += 2`); требуют разворачивания в `z = z + 2`.
2. Каст `:Type(expr)` и тип-аннотация `:Type(Param)` (1 аргумент, без размерностей)
   синтаксически неразличимы в конвертации; кастом считается 1 аргумент без `[...]`.
3. Оба операнда `std::any` → тип результата невыводим.
4. Широкая строка `"…"` эмитится как `L"…"` (`std::wstring`); корректность широких
   многосимвольных строк (`L"…"` с non-ASCII) - отдельная задача на проверку.
