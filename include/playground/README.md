# playground - балансировщик и исполнитель trust-playground

Godbolt-стиль двухоконного playground работает по трёхуровневой схеме:

```
страница (hugo, статический сайт) → балансировщик (--playground) → worker-узлы
```

Единый бинарник `trust-playground` имеет два режима:

- `--playground` - **балансировщик**: принимает `POST /run` от статического сайта,
  ведёт реестр воркеров и диспетчеризует задачи на них. Вычислений не выполняет.
- (по умолчанию) - **исполнительный VPS (worker)**: сам подключается к
  балансировщику (исходящее соединение, двойной NAT не мешает), забирает задачи,
  выполняет транспиляцию через субпроцесс `trust-lsp --json` и возвращает результат.

## Сборка

```sh
cmake --build _build --target trust-playground trust-lsp
```

## Конфиг

Единый файл `key=value` (по умолчанию `/etc/trust-playground/trust-playground.conf`)
с префиксами `playground.` (балансировщик) и `worker.` (исполнитель). Строка **без**
префикса - запись реестра воркеров `label=token` (токен = 64 hex). Каждый режим
читает только свои ключи. Отозвать воркера = удалить строку из реестра + reload.

```sh
# балансировщик
./_build/trust-playground --playground --config /etc/trust-playground/trust-playground.conf
# воркер (задаётся токен, playground_url, lsp_bin)
./_build/trust-playground --config /etc/trust-playground/trust-playground.conf
```

## Протокол (reverse long-poll)

- `POST /run` (сайт) - тело = Trust-код → ответ JSON-контракт `lsp/HTML.md`;
  при отсутствии воркеров - `{ok:false, unavailable:true, instructionsUrl}`.
- `GET /health` → `{"status":"ok"}`; `OPTIONS /run` - CORS-preflight.
- `POST /poll` (воркер) - долгий запрос за задачей (`200`+job или `204` timeout);
  `POST /result` (воркер) - возврат результата. Токен обязателен (`403` иначе).
- `POST /download` (сайт) - тело = Trust-код. **Ленивая** сборка build-архива: отдельный
  запрос, заново обрабатывает файл (свежая транспиляция + сборка build-каталога самим
  `trust-lsp --emit-build-dir`), **без кеша** на балансировщике; ответ `200` +
  `application/gzip` + `Content-Disposition`; иначе `400/429/503/502`.

## Страница playground (glue-JS)

- Комбобокс примеров заполняется сразу (до загрузки Monaco), не бывает пустым.
- Под панелями - окно **лога**: в него пишется stderr `trust-lsp` (диагностика)
  при транспиляции (поле `log` контракта). **Изменяемый размер**: окна песочницы
  перетаскиваемые - вертикальный сплиттер между панелями Trust и Generated C++
  (ширина панелей) и горизонтальный над логом (высота лога).
- **Навигация из лога в исходник**: строки-заголовки диагностик
  (`файл:строка:колонка: severity: сообщение`) в логе кликабельны - клик переводит
  курсор редактора Trust на соответствующую строку. При наличии в логе ошибки
  (`error`/`fatal`) курсор автоматически встаёт на строку первой ошибки.
- На панели Generated C++ - кнопка **«⬇ Скачать»**: `POST /download` с текущим кодом -
  лениво собирает build-архив (заново обрабатывает файл) и скачивает `tar.gz`. Имя
  файла - `trust-lang-<версия>-generated.tar.gz` (формирует trust-lsp) из заголовка
  `Content-Disposition`.
- `GET /stats` - JSON-статистика балансировщика. Токен НЕ передаётся в URL: браузер -
  через форму `/stats/login` (cookie-сессия), скрипты - через заголовок `X-Stats-Token`;
  URL логина печатается при старте (`stats: http://…/stats/login`) и в `playground_run.sh`.

## Реализация

- `http.h/.cpp` - HTTP-ядро (`parseHttpRequest`/`serializeHttpResponse`), HTTP-клиент,
  base64.
- `config.h/.cpp` - парсер единого конфига с префиксами и валидацией токенов
  (в т.ч. `worker.lsp_opts` - доп. опции, всегда передаваемые в `trust-lsp`).
- `server.h/.cpp` - балансировщик: реестр, очередь, диспетчеризация, rate-limit,
  endpoint `/download`.
- `worker.h/.cpp` - исполнитель: слоты, HTTP-клиент (http/https), субпроцесс
  `trust-lsp --json` с лимитами (`setrlimit` + таймаут), захват stderr в `log`;
  для задач «собрать архив» (`/download`) вызывает `trust-lsp --emit-build-dir`.
  При запуске (до подключения к балансировщику) воркер прогоняет **самопроверку**:
  транспилирует простейшую программу и собирает из неё build-архив теми же путями,
  что и реальные задачи; при провале - не регистрируется, а выдаёт диагностику и
  завершается (fail-fast, напр. если нет `tar` или не находится `trust-runtime`).
- `lsp/html_emit.cpp` - glue-JS (комбобокс, лог, кнопка скачивания) и `trust-lsp`
  принимает `-W...` и пробрасывает их в pipeline (`ctx->opts().parse_argv`).

- шаблоны `*.service.in`, `nginx-balancer.conf.in`;
- статья о песочнице - `docs/content/ru/docs/sandbox.md` (архитектура, запуск воркера,
  запрос токена).

## Командная строка (trust-playground)

Единый бинарник в двух режимах: `--playground` - балансировщик; без аргумента - воркер.

- `--gen-token [n]` - сгенерировать n (по умолчанию 1) токенов воркера (64 hex-символа) и
  вывести по одному на строку. Удобно для регистрации воркеров в конфиге балансировщика.
- `--save-config` - сохранить эффективные worker-настройки в конфиг. Работает даже без
  `--playground-url`/`--token`: можно заранее задать `lsp_bin`, `max_parallel` и т.п.,
  а url/token добавить в конфиг вручную позже.
- Дефолт `worker.playground_url` - `https://playground.trust-lang.net` (публичный
  балансировщик). Для запуска воркера обязателен только `--token` (и `--lsp`).
- Статус связи песочницы с балансировщиком: публичный `GET /health` балансировщика
  возвращает `{"status":"ok","workers_connected":N}`; glue-JS раз в 5 c пингует его и
  показывает в статусной строке «балансировщик онлайн · воркеров: N», «…нет воркеров»
  или «нет связи с балансировщиком».
- Остановка по Ctrl+C: обработчики SIGINT/SIGTERM ставятся через `sigaction` **без**
  `SA_RESTART`, поэтому блокирующий `accept()`/`poll()`/`connect()` прерывается (`EINTR`),
  циклы перепроверяют `stop_` и процесс корректно завершается (и балансировщик, и воркер
  - слот-потоки воркера выходят сразу, не дожидаясь таймаута poll).

## Локальная разработка playground в Hugo

`docs/playground_run.sh` поднимает локальную среду за один запуск
(бэкенд: балансировщик + воркер; страница: hugo server). Скрипт НЕ генерирует
сайт/фрагменты - только запускает песочницу и hugo. Запуск обязателен из каталога `docs/`:

```sh
# из каталога docs/ (после сборки trust-playground и trust-lsp)
cd docs && ./playground_run.sh            # [backend_port] [web_port]
```

После запуска в консоли печатается адрес для открытия в браузере:

- при наличии **extended** hugo (с поддержкой SCSS) запускается `hugo server`:
  ```
  http://127.0.0.1:1313/ru/playground/
  http://127.0.0.1:1313/en/playground/
  ```
- иначе - генерируется автономная страница (`trust-lsp --html --html-full`) и
  раздаётся через `python3 -m http.server`:
  ```
  http://127.0.0.1:1313/playground.html
  ```

Требования: `trust-playground` + `trust-lsp` в `_build`; для полноценного hugo-сайта -
**extended** hugo (SCSS). Временные файлы (конфиг, страница, логи) - в
`_build/dev-playground`. Остановка:

```sh
pkill -x trust-playground          # бэкенд
pkill -f 'hugo server --source docs'   # hugo (если запущен)
```

# Полный справочник режимов playground

## 1. Два режима единого бинарника

Один и тот же бинарник `trust-playground` работает в двух режимах. Режим выбирается
**наличием флага `--playground`**:

| Режим | Запуск | Роль |
|-------|--------|------|
| **Балансировщик** | `trust-playground --playground [--config <file>]` | Принимает запросы сайта (`POST /run`), ведёт реестр воркеров, очередь и диспетчеризацию, отдаёт `/download` и `/stats`. **Вычислений не выполняет.** |
| **Исполнитель (worker)** | `trust-playground [--config <file>]` (без флага) | Сам подключается к балансировщику (исходящее соединение - двойной NAT не мешает), по reverse long-poll забирает задачи, транспилирует через субпроцесс `trust-lsp --json` и возвращает результат. |

Оба режима читают **один** файл конфига; каждый берёт только свои ключи
(префиксы `playground.` / `worker.`).

## 2. Настройки

Полный список опций и дефолты **не дублируются здесь** - они задокументированы
комментариями в коде конфигурации (`include/playground/config.h`) и в генерируемом
файле (`saveWorkerConfig`). Справочник CLI - `trust-playground --help`. Здесь только
важное для понимания архитектуры:

- Один файл `key=value`, префиксы `playground.` (балансировщик) и `worker.`
  (исполнитель); строка без префикса - реестр воркеров `label=token`.
- Каждый режим читает только свои ключи.
- Отозвать воркера = удалить его строку из реестра и перечитать/перезапустить конфиг.

## 3. Кто за что отвечает

**Балансировщик (`--playground`)** отвечает за: приём запросов сайта, валидацию
токенов воркеров и статистики, очередь и диспетчеризацию задач, кэш build-архивов
и их выдачу по сессионному токену, rate-limit, защиту от DoS, статистику и почтовые
алерты. **Вычислений не выполняет и исходного кода не хранит дольше, чем живёт задача.**

**Исполнитель (worker)** отвечает за: исходящее подключение к балансировщику
(reverse long-poll), выполнение транспиляции Trust → C++ через субпроцесс
`trust-lsp --json` с ограничениями памяти/времени/размера вывода, сборку build-архива
и возврат результата. Это единственный компонент, который исполняет код и обращается
к файловой системе.

**Сайт (glue-JS)** отвечает за: ввод Trust-кода, запрос `/run`, показ C++/лог и
ленивое скачивание build-архива по `POST /download`.

## 4. Инициация соединений (кто к кому подключается)

- **Сайт → балансировщик**: короткий `POST /run` (и `POST /download`, `GET /stats`).
- **Воркер → балансировщик**: сам инициирует исходящие соединения (`POST /poll`,
  `POST /result`). Это ключевая особенность: **балансировщик не имеет входящих
  соединений к воркерам**, поэтому двойной NAT и динамические IP воркерам не мешают.
- Отсюда reverse long-poll: воркер держит исходящий `POST /poll`, балансировщик
  отвечает, когда появляется задача, либо `204` по таймауту.

## 5. Жизненный цикл задачи (кто что делает)

1. **Сайт** шлёт `POST /run` с Trust-кодом; **балансировщик** валидирует размер и
   rate-limit, кладёт задачу в очередь.
2. **Воркер** по исходящему `POST /poll` забирает задачу, выполняет транспиляцию
   (`trust-lsp --json` с лимитами памяти/времени/вывода) и возвращает результат через
   `POST /result`. Для `/run` build-архив НЕ строится.
3. **Балансировщик** принимает результат только от воркера-владельца и отвечает сайту
   JSON-контрактом.
4. **Сайт** по клику «⬇ Скачать» шлёт `POST /download` с кодом → балансировщик диспатчит
   задачу «собрать архив» (`buildArchive=true`) → воркер вызывает
   `trust-lsp --json --emit-build-dir` → балансировщик сразу отдаёт `tar.gz`
   (проходной ответ, без кеша).

Остальные эндпоинты: `GET /health` (мониторинг), `GET /stats` (оператор, по токену),
`OPTIONS /run` (CORS-preflight). Развёрнутое описание эндпоинтов - в коде
`src/playground/server.cpp` (`handle`/`handleRun`/…).

## 6. Build-архив

- Генерирует **trust-lsp** (`--emit-build-dir`): build-каталог pipeline - `.cppt` /
  `_main.cppt` / `Makefile` / `build.conf` / `LICENSE` / `trust/` (рантайм-заголовки
  извлекаются из trust-runtime). Временные файлы удаляются.
- `build.conf` - **единый переносимый** (идентичен локальной сборке `trust build`):
  без абсолютных путей и без запекания компилятора - `CXXFLAGS += -I.` +
  `LIBS += -ltrust-runtime -lgmp`. Компилятор берётся из Makefile (`CXX ?= c++`) либо
  передаётся `make` на командной строке.
- Имя файла: `trust-lang-<версия>-generated.tar.gz` (формирует trust-lsp).
- Сборка - **лениво**, только по `POST /download` (заново обрабатывает файл, без кеша
  на балансировщике). Размер ограничен `max_archive_kb`.

## 7. Статистика (`GET /stats`)

`GET /stats` - JSON; `GET /stats?format=html` - HTML-страница (та же статистика,
читаемый вид для браузера). Аутентификация: заголовок `X-Stats-Token` (скрипты/curl)
или cookie-сессия после входа через `POST /stats/login` (форма, ввод `stats_token`);
`GET /stats/login` - форма входа, `POST /stats/logout` - выход. Токен НЕ передаётся
в query-строке.

Структура `balancer`: `workers_known`, `workers_connected`, `queue`, `in_flight`,
`max_queue`, `rate_limit_ips_tracked`, `rate_limit_resets`.
Массив `workers`: `token_hash` (первые 8 символов), `label`, `connected`, `capacity`,
`in_flight`, `assigned`, `completed`, `metrics` (метрики системы воркера из `/poll`).

## 8. Почтовые алерты

- **Событийные**: письмо отправляется **немедленно** при первом появлении события
  (нет воркеров, очередь полна, превышен `max_result_kb`, все воркеры отключились /
  восстановились). Повтор того же события в течение `alert_interval_sec` **не**
  отправляется (per-reason dedup), чтобы не спамить. Тело - причина + форматированная
  текстовая сводка статистики.
- **Периодические** (раз в `alert_interval_sec`, default - сутки): письмо с
  форматированной текстовой сводкой статистики.
  статистикой (`/stats`).
- Отправка: `alert_cmd` (по умолчанию `sendmail -t`) получает письмо из stdin
  (заголовки `From/To/Subject/Date`, текст). Включение - `alert_email`.

## 9. Безопасность

- **Аутентификация воркеров**: токены из реестра (`label=token`, 64 hex); без
  верного токена `/poll`/`/result` → `403`.
- **TLS (воркер → балансировщик)**: `playground_url` для не-loopback хоста обязан быть
  `https://`; открытый `http://` допускается только для `localhost`/`127.x`/`::1` -
  иначе auth-токен воркера и полезная нагрузка задач (исходники, результаты/архивы)
  шли бы открытым текстом (кража токена → подмена воркера).
- **CORS - opt-in**: `Access-Control-Allow-Origin: *` шлётся только на публичных
  браузерных эндпоинтах (`/run`, `/download`, `/health`, preflight). Токен-защищённые
  и воркерские ответы (`/stats`, `/poll`, `/result`) НЕ раскрываются чужому origin.
- **Статистика**: `/stats` только по `stats_token`.
- **Скачивание**: `/download` собирает архив **лениво** (только по запросу, заново
  обрабатывает файл); источник кода - в теле запроса; защита флуда через rate-limit +
  лимит `max_archive_kb`; чужие архивы не раскрываются (нет кеша/чужих job).
- **Rate-limit**: `/run` - до `rate_limit_per_ip` запросов/мин с одного IP; карта IP
  ограничена `max_rate_limit_ips` (сбросы считаются → `rate_limit_resets`).
- **Защита от DoS**: лимит одновременных соединений (семафор), таймаут и лимит
  чтения запроса (slowloris/огромный Content-Length), лимиты размера тела/архива.
- **Ограничения воркера**: память/CPU/размер вывода через `setrlimit` + таймаут.
- **Валидация настроек воркера при запуске** (`validateWorkerSettings`): `worker.lsp_bin`
  обязан существовать и быть исполняемым, `worker.project_dir` (если задан) - существовать
  и быть каталогом, `worker.lsp_opts` - корректными опциями (каждый НЕПУСТОЙ элемент
  начинается с `-`; ловит случайный токен/позиционный аргумент до того, как он дал бы
  `trust-lsp` ошибку "unknown option '<токен>'"; пустой список/пустые элементы допустимы -
  `worker.lsp_opts` может не быть настроен), числовые лимиты - здравыми. Воркер не
  регистрируется у балансировщика, если проверка не прошла.
- **Маскировка токена в публичных ответах**: токен воркера заменяется на `<redacted>`
  в любом результате задачи (`/result` → `/run`), даже если он ошибочно попал в
  stderr `trust-lsp` (например, как `unknown option '<токен>'`) - публичная песочница
  не получает конфиденциальный токен.

## 10. Развёртывание и тесты

- `playground_run.sh` (docs/) - локальная среда (балансировщик + воркер + hugo server);
