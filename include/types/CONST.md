# Константность объектов: архитектура и сравнение подходов

Документ описывает модель константности (неизменяемости) значений и переменных в Trust,
сравнение подходов в разных языках программирования и обоснование принятых решений.
Связанные источники: `types/MEMORY.md` (флаг `kConstFlag`), `types/type_id.hpp`, `semantic/MEMORY.md`,
`transpiler/MEMORY.md`.

---

## 1. Постановка

Признак константности нужен в двух ролях, которые часто смешивают, но это разные вещи:

1. **«Константность в типе»** - тип сам по себе константен (`const T`). Декларация `x^ := 42`
   порождает значение типа `const int8_t`. Этот признак влияет на C++-имя типа (`getCppTypeName`),
   на сигнатуры/прототипы функций и на манглинг.
2. **«Пер-переменная константность»** - переменная становится константной по мере анализа узлов AST
   (`x := 42; x^ += 1;` → далее `x` неизменяема). Это свойство **переменной**, а не типа; оно не
   входит в тип, не влияет на сигнатуры, а при кодогенерации (когда тип не константный) выражается
   через `const_cast<>()`.

Цель - единый ортогональный квалификатор `kConstFlag` (по аналогии с битом выводимости `kInferredFlag`),
который можно ставить и «на тип целиком», и «по мере анализа узлов AST», не ломая структурную
идентичность типов и сигнатуры функций.

---

## 2. Как это сделано в других языках

В системах типов сложились **два принципиально разных подхода**.

### 2.1. Константность как квалификатор типа (C/C++, D, Ada)

`const` входит в тип и контролируется системой типов (const-correctness).

**C / C++:**
- `const T x;` - переменная типа `const T`; сам `T` не «клонируется», `const` - квалификатор объекта.
- Различают **top-level const** (на самом значении/объекте) и **низкоуровневый const** (на pointee):
  `const int*` vs `int*` - это разные типы.
- **Top-level const НЕ участвует в сигнатуре и манглинге параметра по значению**:
  `void f(int)` и `void f(const int)` - один и тот же символ. А низкоуровневый const
  (`const int*` / `int*`) участвует в перегрузке и манглинге.
- `const_cast<>` - осознанное снятие/наложение top-level const. Снятие const с реально
  const-объекта и последующая запись - неопределённое поведение. Это «мост» между
  const-безопасным кодом и кодом, не ожидающим const.
- Внутренняя изменчивость данных через `const`-члены (`mutable`) или указатели.

**D:** `const`/`immutable` - квалификаторы, **транзитивные** (неизменяемость распространяется на все
вложенные данные), `immutable` - глобально неизменяемо. Это идёт дальше C++.

**Ada:** `constant` в объявлении - константа; неотъемлемая часть типизированного объявления.

**Вывод из подхода A:** const - часть типа, но top-level const «слабый» (не меняет сигнатуру),
низкоуровневый/транзитивный const «сильный» (меняет тип).

### 2.2. Мутабельность как свойство объявления/биндинга (Rust, Swift, Kotlin, Zig, TypeScript)

Тип **не содержит** информации о мутабельности переменной; это свойство самого объявления.

- **Rust:** `let x = ...;` (immutable binding) vs `let mut x = ...;`. Тип не знает, изменяем биндинг.
  Внутренняя изменчивость, когда нужна, - свойство **значения/типа**: `Cell<T>`, `RefCell<T>`,
  `Mutex<T>`, `AtomicU*`. «const_cast» аналога нет - снятие ограничений только через `unsafe`.
- **Swift / Kotlin:** `let`/`var` (Swift), `val`/`var` (Kotlin) - свойство объявления, не тип.
- **Zig:** `const x` vs `var x` - биндинг; по умолчанию `const`.
- **TypeScript / JS:** `const`/`let` - биндинг (неизменяема ссылка, не объект).

**Вывод из подхода B:** неизменяемость - свойство переменной, не тип; не влияет на интернирование
типов, сигнатуры и манглинг функций. Внутренняя изменчивость - отдельное свойство значения/типа.

### 2.3. Сравнительная таблица

| Язык | Механизм | Входит в тип? | Влияет на сигнатуру/манглинг? | Снятие | Транзитивность |
|------|----------|--------------|------------------------------|--------|----------------|
| C/C++ top-level | `const T x` | да (квалификатор объекта) | нет (параметр по значению) | `const_cast` (UB при записи) | нет |
| C/C++ pointee | `const int*` | да | **да** (разные типы) | `const_cast` (UB при записи) | нет |
| Rust | `let` / `let mut` | нет (биндинг) | нет | - (`unsafe`) | нет; через `Cell`/`RefCell` |
| Swift/Kotlin | `let`/`val` vs `var` | нет (биндинг) | нет | - | нет |
| D | `const`/`immutable` | да | да (транзитивно) | `cast` | **да** |
| Zig | `const` / `var` | нет (биндинг) | нет | - | нет |
| Java | `final` | нет (переменная/поле) | нет | - | нет |
| Ada | `constant` | да (объявление) | да | - | да |

## 3. Модель Trust

Trust использует **гибрид двух подходов**, что совпадает с разделением C++ top-level/low-level const:

| Признак | Аналог | Влияет на |
|---|---|---|
| «Константность в типе» (`x^ := 42` → `const T`) | C++ `const T` на объекте / тип-квалификатор | `getCppTypeName` → `const T`; прототипы/манглинг |
| «Пер-переменная константность» (ставится по мере анализа) | Rust `let` / C++ top-level / Kotlin `val` | **не** входит в тип, интернирование и сигнатуры; кодогенерация через `const_cast<>` |

### 3.1. Ортогональный бит `kConstFlag`

Один бит (бит 30 нижней половины `TypeId`), ортогональный структурной идентичности - по образцу
`kInferredFlag`. Хелперы `withConst`/`typeIsConst`/`clearConst` в `types/type_id.hpp`.

- **Интернирование/каноника/индекс**: бит снимается (`getIndexFromId`, `getCanonicalTypeId`,
  `EXPECT(!typeIsConst(child))` в `getOrCreateStructuralType`). `const T` и `T` разделяют слот реестра.
  Это конвенция top-level const: не плодит структурных типов и безопасна для манглинга.
- **`getCppTypeName`**: при `typeIsConst(id)` → лидирующий `const ` (для любой категории типа).
- **Применим к TypeId любой категории**: примитив, алиас, структура, класс, контейнер, тензор -
  const - квалификатор поверх структурного типа, а не свойство только «маленьких» типов.

### 3.2. Установка бита

- **«Константность в типе»** - ставится на сам тип при объявлении переменной с `^`/`attr::ReadOnly`
  (`semantic/name_resolution.cpp::analyzeVarDecl` - типизированные; `typeExpr` - нетипизированные,
  когда тип выводится из инициализатора).
- **«Пер-переменная константность»** - ставится на `Symbol::type` по мере анализа узлов AST
  (аналог `withInferred`); отдельный блок, см. §5.

### 3.3. Кодогенерация

- **Декларация переменной** (`transpiler.cpp::generateVarDeclToFile`): источник `const` - бит
  `kConstFlag` на типе переменной (разрешённый символ `s->type`), fallback - `attr::ReadOnly`
  (когда таблицы символов нет, напр. в unit-тестах). `x^ := 42` → `const int8_t c_x = 42;`,
  `obj^: C` → `const C c_obj = ...;`.
- **Прототипы функций**: константность определяется **только константностью типа**; пер-переменный
  бит в сигнатуру НЕ попадает (при построении структурного типа сигнатуры снимается `clearConst`).
  Top-level const параметра по значению в C++ не меняет манглинг - безопасно.
- **const_cast-мост** (пер-переменная константность, тип не константный): для тривиальных/простых
  типов `const_cast<T>(c_x)` (по значению, prvalue); для композитных/классов - `const_cast<T&>(c_x)`
  (lvalue, без лишней копии). Отдельный блок, см. §5.

## 4. Реализовано

- `kConstFlag` + `withConst`/`typeIsConst`/`clearConst`; `getIndexFromId` снимает оба бита
  (`types/type_id.hpp`).
- `getCppTypeName` даёт `const ` при `typeIsConst`; `getCanonicalTypeId` снимает const-бит;
  `getOrCreateStructuralType` запрещает const-бит в детях (`types/registry.cpp`).
- `resolveCppTypeId` учитывает const-бит (добавляет `const ` к базовому имени и к trust-имени алиаса)
  (`transpiler.cpp`).
- semantic ставит const-бит на `Symbol::type` при `^`/`attr::ReadOnly` (типизированные и
  нетипизированные переменные) (`name_resolution.cpp`).
- **Become-const и защита от записи** (`typeExpr`): LHS с `^` (`x^ += 1`) делает переменную
  константной (бит на `Symbol::type`); обычная запись в константную переменную - диагностика
  ошибки («cannot assign to constant variable»).
- `generateVarDeclToFile` берёт const **объявления** из `attr::ReadOnly` на узле (не из `Symbol::type`,
  т.к. became-const-переменная мутировалась до финализации и её декларация обязана быть не-const).

Проверка: `trust --emit-cpp` для `x^ := 42; y^: Int32 := 7; z: Int32 := 5;` даёт
`const int8_t c_x = 42; const int32_t c_y = 7; int32_t c_z = 5;`.
`x := 42; x^ += 1; x += 1;` → ошибка на последней строке; декларация `x` остаётся не-const.

## 5. Дальнейшие шаги (вне текущей задачи)

1. **const_cast-мост для пер-переменной константности (кодогенерация мест использования)**:
   тривиальные типы - `const_cast<T>(c_x)` (по значению); композитные/классы - `const_cast<T&>(c_x)`
   (lvalue). Требует отличать «стал константой» от «объявлена константной» и (для подстановки значения
   44) отслеживания константного значения (constant propagation) - это отдельная более крупная фича.
2. **Проверка записи в const через вложенные формы** (member/array/append `[]=` на const-контейнере,
   `++`/`--` на const-переменной) - расширение диагностики из §4.
3. При появлении указателей/ссылок на pointee - разделить низкоуровневую константность
   (должна входить в структурную идентичность) от top-level.


---

## 6. Итог

Модель Trust - ортогональный квалификатор `kConstFlag`, объединяющий «константность в типе»
(тип-квалификатор, влияет на `getCppTypeName`/прототипы) и «пер-переменную константность»
(свойство переменной, не влияет на тип/сигнатуры, выражается через `const_cast<>`). Это согласовано
с конвенцией C++ (top-level vs низкоуровневый const) и Rust (`let` vs внутренняя изменчивость):
тип не «загрязняется» биндинг-константностью, а типовая константность остаётся настоящим
квалификатором.
