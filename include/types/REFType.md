# Модель ссылок: архитектура и сравнение подходов

Документ описывает модель ссылочных типов в Trust: кодирование вида ссылки в `TypeId`/`TypeKind`,
причины выбора, ограничения и сравнение с C/C++ и другими языками. Разделы §7–§11 описывают модель
управления памятью на уровне операций: назначение и причины выбора, классы операций, виды/параметры/
контракты, унификацию (единая грамматика + сменные backend'ы) и ограничения. Связанные источники:
`types/MEMORY.md` (битовая структура `TypeKind`), `types/TYPE.md` (формат таблицы `RefType`),
`types/type_id.hpp`, `types/registry.hpp` (`RefTypeData`), `semantic/MEMORY.md`,
`attrs/attr_builtin.hpp` (атрибут `reftype`).

---

## 1. Постановка

Ссылка - способ доступа к объекту, находящемуся в другом месте памяти. В Trust модель ссылок
строится вокруг **одного признака ссылки на объявление** (`RefType`, плоский enum в `TypeKind`).
Возможные виды:

| Значение | Имя | Семантика |
|----------|-----|-----------|
| 0 | `kValue` | владение значением (без ссылки) |
| 1 | `kShared` | совместное владение |
| 2 | `kWeak` | слабая (не владеющая) ссылка |
| 3 | `kUnique` | исключительное владение (мнемоника/кодоген: `unique` → `trust::Unique`, см. §9.1) |
| 4 | `kPtr` | сырой указатель (`*`) — совместимость с C++ |
| 5 | `kMptr` | указатель на член (`::*`), `MemberPointerTypeData` |
| 6 | `kRef` | ссылка (`&`) — совместимость с C++ |
| 7 | `kRref` | rvalue-ссылка (`&&`) — совместимость с C++ |
| 8 | `kPtrPtr` | указатель на указатель (`**`) |
| 9 | `kLocker` | охраняемый доступ к reference-wrapper (`Shared`/`Weak`): RAII-охранник (результат `lock()/lock_const()`) |

**Двухосевая модель.** `RefType` смешивает две независимые оси: **владение временем жизни**
(`value`/`shared`/`weak`/`unique`) и **доступ к объекту** (сырой `&`/`*` против охраняемого
`locker`). `kLocker` — охраняемый доступ **только** к reference-wrapper (`trust::Shared`/`trust::Weak`),
результат `lock()/lock_const()`. Сырые ссылки (`ptr`/`ref`/`rref`) и эксклюзивное владение локера
**не имеют** — это другая идеология (прямой доступ без guard). Null-безопасность — отдельная ось (контракт
типа), а не guard-объект.

**Центральное правило:** один признак ссылки на объявление. Это **осознанное решение** для
упрощения понимания системы ссылочных типов (а не следствие 4-битного поля). Читатель и
компилятор всегда видят ровно один признак, без «лесенок» `ref<ref<ref<T>>>` в одной строке.
Вложенные модели выражаются **цепочкой отдельных ссылочных типов** (каждый уровень - отдельно
объявленный тип).

## 2. Кодирование

`RefType` - 4 бита (биты 16–19) в `TypeKind` (uint32). Значения 0–8 заняты, 9–15 зарезервированы.
Хелперы: `getRefType`/`withRefType` (`types/typekind.hpp`), строковые имена
`refTypeName`/`refTypeFromString` (для атрибута `@[reftype("...")]` и диагностики).

Применение признака к типу:

- **Fast-path (первая ссылка).** Первая ссылка на тип **без признака** (вид `kValue`) кодируется
  **битом**: `withRefType(type, kind)` - дёшево, без обращения к реестру. Например
  `@[reftype("ptr")] :Int32` → `TypeKind{Group=Integers, Data=32, RefType=kPtr}`.
- **Вложенность (ссылка на ссылочный тип).** Если базовый тип уже несёт признак (например нужно
  `shared<ptr<Int32>>`), создаётся **составной узел** реестра `RefTypeData{pointeeType}` через
  `TypeRegistry::getOrCreateRefType(kind, pointee)`. Вид несёт сам `TypeKind` узла
  (`Group::kReftype`, `RefType=kind`), `pointeeType` - тип, на который ссылается узел.

Узел интернируется структурно через `TypeKey{kind, children}` (аналогично
`MemberPointerTypeData`/`ArrayTypeData`/`FunctionTypeData`), поэтому одинаковый
`(вид, pointee)` даёт один `TypeId`, а `ptr<Int32>` ≠ `shared<Int32>` ≠ `Int32`.

### Источник признака: атрибут `@[reftype("...")]`

Вид ссылки задаётся атрибутом `@[reftype(<имя>)]` **перед переменной/типом**. Имя - одно из
мнемонических: `value/shared/weak/unique/ptr/mptr/ref/rref/ptrptr/locker`. Неизвестное имя или
отсутствие параметра - **диагностика ошибки** (без тихого fallback).

**Форма записи.** Параметры атрибутов хранятся как текст, поэтому имя вида можно указывать
**без кавычек** (`@[reftype(ptr)]` - рекомендуется, как `#[repr(C)]`/`@safe` в других языках)
или **в строке** (`@[reftype("ptr")]`) - обе формы эквивалентны. Битовая раскладка `TypeKind`,
где хранится `RefType` (биты 16–19), - в разделе «Битовая структура TypeKind» документа `TYPE.md`.

## 3. Как это сделано в других языках

### C / C++

- Синтаксические формы - **разные типы**: `T`, `T*`, `T&`, `T&&`, `T::*` - отдельные категории.
- Владение **ортогонально** синтаксису и выражается обёртками: `shared_ptr<T>`, `unique_ptr<T>`,
  `weak_ptr<T>`, `optional<T*>`.
- Вложение/совмещение - через композицию обёрток (`shared_ptr<T*>`): ось владения и ось
  «указателя» комбинируются. На практике в крупных проектах «shared-владение указателем»
  реализуется обёртками с custom deleter (`std::shared_ptr<FILE>(f, &fclose)`), type-erased
  `shared_ptr<void>`, интрузивным счётчиком (Qt `QSharedDataPointer`, OpenCV `cv::Ptr`,
  Chromium `scoped_refptr`), полиморфным `shared_ptr<Base>`.

### Rust

- `&T`/`&mut T` (заимствование) и `*const T`/`*mut T` (сырые указатели) - синтаксические
  категории; владение - `Box<T>`, `Rc<T>`/`Arc<T>`, `Weak<T>`.
- `&T` и `T` - **разные типы**; гарантии (эксклюзивность/алиасинг) даёт borrow-checker.

### Go / C# / D

- Указатели/ссылки - синтаксическая категория типа (`*T`, `ref`); владение-модель отдельно
  либо отсутствует.

### Вывод

Общий паттерн языков - **синтаксическая форма и владение разделены**. Trust сознательно
упрощает до **одного плоского признака** + **цепочек отдельных ссылочных типов** для
вложенности. Это даёт ясность («один маркер на тип») ценой отказа от совмещения осей в одном
объявлении.

## 4. Безопасность

Прямые операции с **сырыми** C++-видами (`ptr/ref/rref/mptr/ptrptr`) в Trust **запрещены** по
вопросам безопасности. Сырые виды применяются **только** через атрибут `@[reftype("...")]`.
Классические операторы (`&`, `*`, `&&`) дают **безопасные** виды (`shared/weak/unique/value`).
Это снимает неоднозначность символов: `&`/`*` однозначно отображаются на безопасные виды, сырые
виды достижимы только явно.

## 5. Ограничения (что нельзя)

1. Нельзя в **одном** объявлении сделать ссылку на ссылку на ссылку - признак ссылки один.
2. Признак ссылки - только один на тип-объявление.
3. «Совмещённое владение» в C++-смысле (`shared_ptr<T*>`) в одном объявлении **не выражается** -
   только цепочкой отдельных ссылочных типов (`Shared := @[reftype("shared")] :Ptr`).
4. **Предопределённые уровни-сокращения:** `kPtr` (`T*`, 1 уровень) задаётся только явным
   `@[reftype("ptr")]`;
   `kPtrPtr` (`T**`) **зарезервирован, но не реализован** (`@[reftype("ptrptr")]` → диагностика
   «reference kind ... is not implemented»). Произвольная/более глубокая вложенность
   (`T***`, `shared<ptr<T>>`) — цепочкой отдельных ссылочных типов.

### Nullability (без отдельного бита)

«Может быть пусто» **не требует отдельного бит-признака**:

- Сырые указатели (`kPtr`, `kPtrPtr`) и smart-виды (`kShared/kWeak/kUnique`) nullable «из
  коробки» - это врождённое свойство вида, а не отдельная ось.
- Когда нужен «нет значения» у не-ссылочного типа - это **тип-обёртка** в реестре
  (`optional<Int32>`, `optional<ptr<T>>`), как `std::optional`/`Maybe<T>`, а не квалификатор.

## 6. Реализовано

- `RefType` (плоский, 10 значений: `kValue`..`kLocker`) + `refTypeName`/`refTypeFromString`/`refTypeCppTemplateName`
  (`types/typekind.hpp`, X-macro `TRUST_REF_TYPE_TYPES`).
- `withRefType`/`getRefType` (fast-path бит); `replaceKind(TypeId, TypeKind)` (`types/type_id.hpp`) —
  перенос вида с сохранением низких 32 бит TypeId (index + поведенческие флаги).
- **Классификаторы вида (единый источник):** `isNativeRefKind`/`isSmartRefKind`/`refKindCompatible`,
  `RefAxis`+`refAxisOf` (оси Value/Shared/Unique/Native/Locker), `isSupportedRefKind`
  (`rref`/`ptrptr` зарезервированы, но НЕ реализованы → диагностика «not implemented»).
- **C++-имя и рантайм-заголовки ссылки — единый источник `types/ref_type.hpp`:** `refTypeCppName(kind,
  pointee[, deleter])` и `refTypeRuntimeIncludes(kind, sync)`. **Sync-backend использует РЕАЛЬНЫЕ типы
  реестра** (обёртка `type::AccessShared` + политика `RefTypeData::accessPolicyType`) и композируется в
  `TypeRegistry::getCppTypeName` (`AccessShared<T,Policy>` / `Weak<AccessShared<T,Policy>>`); строки C++-имён
  через API не передаются.
- `RefTypeData{pointeeType, deleterType, accessPolicyType}` + `TypeDataKind::kRefType` + `TypeRegistry::getOrCreateRefType`
  (`types/registry.hpp`, `types/registry.cpp`), группа `Group::kReftype`. `deleterType` (unique) и
  `accessPolicyType` (shared/weak) — ЧАСТЬ типа (входят в `TypeKey.children`): `unique<T,D1> != unique<T,D2>`,
  `shared<T,P1> != shared<T,P2>`; при них вид ВСЕГДА структурный узел (fast-path бит не применяется).
- Атрибут `@[reftype("...")]` (`attr::Reftype`, `attrs/attr_builtin.hpp`, `attr_builtin.cpp`).
- **Атрибут `@[deleter(D)]`** (`attr::Deleter`): deleter внешнего ресурса, ровно один аргумент - имя
  deleter-типа (встроенный `Group::kDeleterPolicy`: `FreeDeleter`, `FileDeleter`; либо нативный класс).
  Допустим только на владеющих видах `unique`/`shared`; для `unique` `D` входит в ТИП
  (`RefTypeData::deleterType`, `unique<T,D1> != unique<T,D2>`), для `shared` стирается.
  Валидация и применение - `NameResolutionPass::applyRefAttrs`; встроенные deleter'ы -
  `trust/resource.hpp` (`Group::kDeleterPolicy`, `isDeleterPolicyType`).
- Трансляция в `NameResolutionPass::analyzeVarDecl`: fast-path бит / узел для вложенности,
  диагностика неизвестного вида (`semantic/name_resolution.cpp`).
- Кодогенерация C++-имени: `TypeRegistry::getCppTypeName` эмитит `T*`/`T&`/`T&&`/`T**`,
  `trust::Shared<T>` (kShared)/`trust::Weak<trust::Shared<T>>` (kWeak)/`trust::Unique<T>`
  или `trust::Unique<T, D>` при deleter (kUnique)/`trust::Locker<T>` (kLocker),
  `MemberType Class::*` (mptr) и рекурсивно для вложенных
  `RefTypeData`-узлов; `CppTranspiler::collectTypeIncludes` добавляет `@trust/trusted-cpp.hpp`
  для shared/weak/unique и рекурсивно обходит детей `RefTypeData` (pointee + deleter,
  напр. `@trust/resource.hpp`) (`types/registry.cpp`,
  `transpiler/type_emit.cpp`). Создание ресурса с deleter - `<Wrapper>::adopt(handle, D{})`
  (`decl_emit.cpp`). Человекочитаемое представление типа для диагностики/hover -
  `TypeRegistry::getFullTypeName`: ссылочные виды показываются с видом (`shared<Int32>`,
  `unique<Int32, FileDeleter>`, `ptr<Int32>`), а не только базовым типом.
- **Спецслучай C-строки**: `StrChar + ptr + const` (`fmt: @[reftype(ptr)@] StrChar^`) - это
  `const char*` (а не `const std::string*`): `TypeRegistry::applyRefType` (единый источник
  fast-path/вложенности для семантики и транспилятора), спецправило в `resolveCppTypeId`
  (`types/registry.cpp`, `transpiler/transpiler.cpp`).
- **Тип `CString`** (`const char*`): встроенный невладеющий тип C-строки (`types/type_names.hpp`,
  `registerBuiltinType(type::CString, ..., "const char*")`). Результат нативного метода
  `StrChar.%c_str(): CString` - явная конверсия `s.c_str()` → `(c_s).c_str()`.
- **Методы типов**: реестр нативных методов на встроенных типах в `TypeRegistry`
  (`TypeDescriptor::methods` - `std::map<std::string, TypeId>` имя → функциональный тип,
  `addMethod`/`findMethod`); метод и функция - одно и то же (сигнатура = `FunctionTypeData`);
  нативность метода - по `%` в имени (`%c_str`), при генерации вставляется идентификатор без `%`;
  поиск ОДНОСТОРОННИЙ (обычное имя `c_str` находит и нативный `%c_str`; нативное - только
  точное). `addMethod` обеспечивает инвариант «одна форма имени» (вторая форма/точный дубль -
  EXPECT). Семантика проверяет наличие метода, число аргументов и тип возврата ДО генерации
  (`NameResolutionPass::handleMethodCall`).
- Тесты: `test/unit/types/reftype_test.cpp`, `test/unit/types/type_method_test.cpp`.

### Символический синтаксис ссылок (реализовано)

Помимо атрибута `@[reftype("...")]` ссылочные типы задаются символическими **маркерами/операторами**
(НЕ «сиглы» - сигл это первый символ ИМЕНИ, ссылка частью имени не является). **Позиция определяет
смысл** (см. `include/syntax/SYNTAX.md` «Ссылочные типы»):

- **Слева от `:=`/`=` - вид ссылки задаётся РОВНО В ОДНОЙ из двух позиций** (умные ссылки
  shared/unique/weak):
  - **у ТИПА** (каноническая): `x : &*Int32` (маркер) ИЛИ `x : @[reftype("shared")@] Int32`
    (атрибут);
  - **у ПЕРЕМЕННОЙ** (сокращённая), только при ОПУЩЕННОМ типе (авто-вывод pointee из
    инициализатора): `&* x := 5`;
  - `&* x : Int32` (вид у переменной, но у явного типа вида нет) - ошибка;
  - один и тот же вид в ОБЕИХ позициях (`&* x : &* Int32`, `&* y : @[reftype("shared")@] Int32`,
    нотация не важна) - предупреждение `-Wref-kind-dup` (default Warning): квалификатор у переменной
    лишний;
  - РАЗНЫЕ виды в позициях (`&* x : && Int32`) - ошибка `reference kind mismatch`.
  Терм `ptr lval` (`&&`/`&*`/`&?` → OPERATOR_PTR) разворачивается в
  `TermToAstConverter::visit_CREATE_NAME`: имя берётся из lval, маркер превращается в атрибут
  `@[reftype("...")]` на объявлении (вид ссылки - часть ТИПА, маркер задаёт его у переменной);
  дальше работают стандартные `applyRefAttrs` (семантика; повторное применение при совпавшем виде
  идемпотентно) и reftype-ветка `DeclEmitter` (кодоген).
  Кодогенерация: shared/weak - конструктор `trust::Shared/Weak<...>(init)` (для address-of-инициализатора
  `& x` - копирующая `= <init>`, чтобы избежать most-vexing-parse), unique -
  `trust::Unique<PoT> x = trust::make_unique<PoT>(init)`; для авто-вывода pointee берётся из
  выведенного типа (getPointeeType).
- **Справа/в выражении**:
  - `& expr` (address-of/borrow) - взятие ссылки; допустимо ТОЛЬКО для ссылочной переменной,
    weak получается ТОЛЬКО из shared (`& shared_var`); unique → ошибка, не-ссылка → ошибка.
    Типизация - `ExprTyper` (case `RefMakeExpr`), тип результата (weak) сохраняется в
    `RefMakeExpr::m_resultType` (транспилятору локальные символы недоступны), кодоген - эмиссия
    `trust::Weak<...>(c_x)` (`ExprEmitter::visit_RefMakeExpr`).
  - `* expr` - доступ к ДАННЫМ ссылочного операнда (семантика std::reference_wrapper<T>::get() -
    ссылка на данные). Для shared/weak - `*(ref.lock())` (под защитой/через weak; lock() бросает на
    истёкшей ссылке); для unique/ptr - `trust::checked_deref(c_u.get())` / `trust::checked_deref(c_p)`
    (БЕЗ UB на nullptr: `trust::checked_deref` бросает `trust::IntMinus` на нулевом указателе).
    Вид операнда (m_opRefKind) ставит семантика в `RefTakeExpr`, кодоген - `ExprEmitter::visit_RefTakeExpr`.
  - `a :=: b` - swap (интринсик `std::swap`), возвращает `&a`; типы должны быть совместимы
    (не обязательно ссылки). `var :=: _` → `std::move(var)` (перемещение в discard). Грамматика
    `assign_seq: assign_items SWAP assign_items`, узел `Binary(AssignOp)` с текстом `:=:`
    (term_to_ast `visit_SWAP`), семантика - `typeBinaryResult` (`utils::isSwapOp`), кодоген -
    `ExprEmitter::emitBinaryOpRaw`.
- **Контракт value-vs-reference** (`ExprTyper::checkAssignmentNarrowing` + `typeBinaryResult`):
  копирование ссылки в значение - ошибка + fixit `*<name>`; weak из unique - ошибка (ось
  владения); арифметика/сравнение над ссылками - ошибка (нет ссылочной арифметики) + fixit
  `*<name>`; swap - ошибка при несовместимых типах.

## 7. Модель управления памятью: назначение и причины выбора

**Назначение.** Модель обеспечивает автоматическое управление временем жизни объектов **без сборщика
мусора**: владение выражается *типом* ссылки, освобождение — детерминированным RAII, а безопасность
(отсутствие висячих ссылок, гонок данных и утечек от циклов) — статически и контрактно. Модель
описывается на уровне **операций над ссылками** и не зависит от конкретной реализации (backend'а).

**Причины выбора ключевых решений:**

- **RAII вместо GC** — детерминированное освобождение, предсказуемая производительность без пауз.
- **Один признак ссылки на объявление** (плоский `RefType`) — читатель и компилятор видят ровно один
  маркер; вложенность выражается цепочкой отдельных типов (см. §1).
- **Разделение осей: владение × доступ.** Владение временем жизни (`value`/`unique`/`shared`/`weak`)
  не смешивается с доступом к объекту (прямой vs охраняемый `lock`/`borrow`). Это устраняет
  неоднозначные комбинированные операции и «лесенки».
- **Минимальный набор видов.** Всё, что является *параметром, квалификатором или контрактом*, не
  вводится отдельным видом (см. §9): const-владение, backend, atomic, deleter, массивы, non-null,
  observer.
- **Guards policy-agnostic.** Охранник доступа (`Locker`) не знает способа
  синхронизации; политика принадлежит владеющему типу.
- **Единая грамматика операций + сменные backend'ы.** Один синтаксис операций для всех реализаций;
  backend (std-shared / intrusive / atomic / deleter) выбирается декларативно и ортогонально
  синтаксису (см. §10).
- **Default zero-cost.** Эксклюзивное владение — `unique_ptr` (без control block), разделяемое — один
  control block; никакой универсальной «тяжёлой» обёртки по умолчанию.

## 8. Модель операций над ссылками

Операции описываются **инвариантно к реализации** (backend'у): любой backend обязан покрыть эти классы
операций. Конкретный синтаксис и сопоставление операций с C++-кодогенерацией — в §6 и `CODE`-источниках.

### A. Создание и приобретение
- A1 владелец из значения: эксклюзивный (`b := v`) / разделяемый (`s := v`);
- A2 владелец из владельца: promote (эксклюзив→разделяемый), demote (разделяемый→эксклюзивный при
  единственном владельце);
- A3 наблюдатель из владельца (`w := & s`);
- A4 adopt внешнего ресурса (сырой handle + deleter) — не-память ресурсы;
- A5 aliasing-владелец на подобъект/член (продление жизни родителя) + lifetime-anchor;
- A6 владелец массива (`T[]`, длина);
- A7 «пустое/отсутствующее» создание (или запрет → non-null).

### B. Копирование, перемещение, передача
- B1 копирование (только разделяемое; refcount++);
- B2 перемещение (эксклюзивное/разделяемое; источник пуст);
- B3 swap (`a :=: b`) — обмен владением;
- B4 передача/возврат через границу функции (by value/ref).

### C. Доступ к данным
- C1 прямое разыменование `*ref` (mut) / `*^ref` (readonly);
- C2 доступ к полю через ссылку (`obj.*ref`);
- C3 охраняемый захват `lock()/lock_const()` (разделяемый) со сроком жизни guard'а;
- C4 неблокирующий захват `try_lock()`;
- C5 невладеющий view (observer) — чтение без захвата;
- C6 повторный/вложенный доступ (re-entrancy).

### D. Доступ и заём (borrow)
- D1 `unique` МОНОПОЛЕН: заём/alias ОТСУТСТВУЕТ (`& u` — ошибка); доступ `*u` прямой (zero-cost),
  допустимы только move/swap;
- D2 ESCAPABLE observer-ссылка есть ТОЛЬКО у `shared`: `Shared::borrow()/borrow_const()` →
  `SharedBorrowedRef`; НЕ владеет и НЕ продлевает жизнь, может покинуть скоуп/вернуться из функции;
  доступ ТОЛЬКО через `access()` (`Locker`) с re-check;
- D3 у `shared` источник НЕ опустошается (observer не снимает владение);
- D4 инвалидация observer-ссылок при гибели последнего владельца.

### E. Наблюдение (weak/observer)
- E1 создание наблюдателя; E2 проверка валидности (`expired`/`has_value`);
- E3 upgrade в владельца (`lock_shared`); E4 наблюдатель над `shared` (`SharedBorrowedRef`).

### F. Мультизахват
- F1 `with(a,b){...}` — упорядоченный/атомарный захват нескольких, освобождение в обратном порядке;
- F2 комбинирование нескольких borrow/observer; F3 устранение deadlock (детерминированный порядок).

### G. Конверсии владения и backend
- G1 promote; G2 demote; G3 shared↔weak; G4 native↔smart (только явно; смешение осей запрещено);
- G5 конверсии между backend'ами (std-shared↔intrusive↔atomic).

### H. Изменение, сброс, клонирование
- H1 мутация через владельца/borrow/guard (`*ref = v`); H2 `set`/замена;
- H3 `reset`/release (`:= _`), явное освобождение; H4 clone/deep-copy/COW; H5 отдача владения наружу.

### I. Идентичность, сравнение, aliasing
- I1 равенство/идентичность (`==`); I2 `owner_before`/порядок; I3 hash (контейнеры/ключи);
- I4 aliasing на подобъект; I5 интроспекция (`use_count`/`unique`/`expired`).

### J. Межпотоковые операции
- J1 синхронизированный захват (policy: mutex/rw/timeout/deadlock);
- J2 atomic publish/load/store ссылки + memory ordering; J3 порядок блокировок / мультилок.

### K. Самоадресация
- K1 `shared_from_this`/`weak_from_this`; K2 получение ссылки на себя/подобъект с продлением жизни.

### L. Ошибки, контракты, диагностика
- L1 null-deref → ошибка; L2 expired weak → ошибка/optional;
- L3 неподдерживаемая операция для (вид×backend) → **compile-time** диагностика (без fallback);
- L4 non-null контракт; L5 диагностика несовместимости осей/владения.

### M. Инфраструктура
- M1 контейнеры/массивы ссылок; M2 интероп со std/нативным; M3 представление операций в AST/term;
- M4 lowering по (вид×backend); M5 copy/move/noexcept-гарантии.

## 9. Виды ссылок, параметры и контракты

Классификация зафиксирована так, чтобы «один маркер на объявление» сохранялся, а всё не-владение
выражалось ортогональными средствами (параметр/квалификатор/контракт/библиотечная операция).

### 9.1. Виды ссылок (ось владения временем жизни, плоский `RefType`)
- `value` — владение значением (без ссылки);
- `unique` — эксклюзивное (монопольное) владение (C++-тип `trust::StaticUnique` / `trust::Unique<T,D>`);
- `shared` — совместное владение (refcount);
- `weak` — слабая (не владеющая) ссылка;
- нативные (совместимость с C++, задаются атрибутом): `ptr`, `ref`, `rref`, `ptrptr`, `mptr`;
- guard-результаты: `locker` (shared-capture).

### 9.2. Ортогональные параметры/квалификаторы (НЕ виды)
- **const-владение** — квалификатор pointee: `Shared<const T>` / `Unique<const T>` (атрибут
  `@[readonly@]`/`^` на pointee);
- **backend/policy** — аргумент `@[reftype(...)]` (sync, atomic);
- **deleter** — отдельный атрибут `@[deleter(<Type|fn>)]`; для `unique` **часть типа**
  (`Unique<T,D>`, как `unique_ptr<T,D>`), для `shared` — аргумент создания/`adopt` (type-erased,
  тип остаётся `Shared<T>`). Runtime реализован: `Unique<V,D>`,
  `Shared(V*, D)`/`Shared::adopt`; языковой атрибут `@[deleter]` **реализован** (см. §6): валидация
  в `applyRefAttrs`, `D` входит в `TypeId` для `unique`, кодоген - `<Wrapper>::adopt(handle, D{})`;
- **режим доступа** — `ReadOnly` как параметр guard'а.

### 9.3. Контракты и библиотечные операции (НЕ виды)
- **non-null** — контракт операций (deref/lock/borrow на пустом → ошибка) + `optional` для «нет
  значения»; `not_null` — библиотечный враппер;
- **observer** — **отдельный вид/тип наблюдения ЗАПРЕЩЁН и не вводится.** Наблюдение выражается
  существующими средствами: checked — `Weak` (только shared-family), unchecked — нативные ссылки
  (изолированы, как есть). Отдельного вида нет;
- **массивы** — specialization pointee (`T[]`), для языка используется `:Array`;
- **aliasing / `shared_from_this`** — обязательные операции shared-family (для прочих видов —
  compile-time ошибка); runtime реализован: `EnableSharedFromThis<V>` (K1) и `alias(owner, subobject)`;
- **atomic** — policy/backend `shared`;
- **COW/clone** — библиотечная надстройка (требует копируемости pointee).

### 9.4. Итоговые решения

| Вопрос | Решение | Обоснование |
|---|---|---|
| non-null | контракт + `optional`; не вид | move-from всегда даёт пустое состояние владельца |
| observer | `Weak` (checked, shared-only) + нативные (unchecked); **отдельный вид ЗАПРЕЩЁН** | checked над exclusive невозможен без control block |
| deleter/ресурсы | атрибут `@[deleter]` + `adopt`; не вид | одинаковая семантика владения, разное действие destruction |
| массивы | specialization pointee; не вид | для языка есть `:Array` |
| const-владение | квалификатор pointee; не вид | const ортогонален владению (как в C++) |
| aliasing / `shared_from_this` | операции shared-family | требуют control block и «первого владельца» |
| atomic | policy/backend shared; не вид | атомарность — свойство операций доступа |
| COW/clone | библиотека; не операция ядра | зависит от копируемости pointee |

## 10. Унификация: единая грамматика + сменные backend'ы

Стратегия: **синтаксис операций унифицирован**, а реализация storage — сменный backend, ортогональный
синтаксису. Выделяются уровни унификации:

- **L0 — типы-владельцы (storage):** отдельные типы (`Unique`/`Shared`/`Weak`/intrusive/atomic/
  deleter), у каждого оптимальная раскладка. Слияние в один тяжёлый шаблон запрещено (перф-регресс).
- **L1 — единый интерфейс доступа:** набор `operator*`/`->`/`get`/`bool` + guards (`detail::GuardBase`).
- **L2 — единый контракт ссылочного типа:** требования к обёртке, чтобы `Weak`/guards/дженерики
  работали с любым владельцем (`ValueType`, `get()`, `lock()/borrow()`, тип guard'а, `get_shared()`,
  `make_auto()`, `reclaim()`).
- **L3 — единый control block (опциональный backend):** собственный контрольный блок, дающий
  aliasing/deleter/intrusive/atomic/`shared_from_this` «в одном месте»; альтернатива обёртке над
  `std::shared_ptr`.

**Принятый компромисс:** L1+L2 сейчас; L3 — опциональный backend рядом со std-обёрткой (default
сохраняет zero-cost и интероп со std). Так «единая модель» = единый интерфейс + сменный backend, без
слияния всех типов в один.

**Выбор backend — декларативный** (прецедент — sync-policy): аргумент `@[reftype(...)]` (и/или
отдельные атрибуты вроде `@[deleter]`), с валидацией по виду. Кодоген отображает
`(вид, backend) → {C++-тип, инклюд, lowering}`; недоступные операции диагностируются (без fallback).

Примеры сопоставления:
```
@[reftype("unique")]                   -> trust::Unique<T>
@[reftype("unique")@] @[deleter(D)@]   -> trust::Unique<T, D>
@[reftype("shared")]                     -> trust::Shared<T>            (std, default)
@[reftype("shared", AccessMutex)]    -> trust::AccessShared<T, Policy>
@[reftype("shared", AtomicPolicy)]       -> trust::AtomicShared<T>      (backend; НЕ реализовано)
@[reftype("weak")]                       -> trust::Weak<trust::Shared<T>>
```

**Плюсы:** единый синтаксис/модель; backend меняется декларативно; прогрессивное внедрение без
big-bang; фичи (deleter/intrusive/atomic/aliasing) реализуются один раз; conformance-набор тестов ×
backend'ов; default zero-cost.

**Минусы/риски:** lowering зависит от `(вид×backend)` (таблица + риск рассинхрона → митигация единым
X-macro/тестами); feature-matrix и обязательная диагностика неподдерживаемого; семантика операций
должна совпадать у всех backend'ов (напр. atomic требует load→guard); рост числа policy-типов/групп в
реестре; конверсии между backend'ами — отдельная матрица; риск «размывания осей» (владение × доступ ×
backend) → нужен единый источник истины.

**Ограничение:** *вид владения* нельзя убрать из типа — `unique` и `shared` различаются
копируемостью/временем жизни. Унификация — на уровне **синтаксиса операций и контракта**, а не
«одного-единственного типа».

## 11. Ограничения

Ниже — принципиальные ограничения модели (не временные недоделки, а следствия решений).

1. **Вид владения нельзя убрать из типа.** `unique` и `shared` различаются копируемостью и временем
   жизни, поэтому единый «универсальный» указатель невозможен; унифицируется синтаксис операций и
   контракт, но не сам тип.
2. **Пустое состояние владельца принципиально возможно** (default-конструкция и move-from). Поэтому
   non-null выражается контрактом операций (+ `optional`/`not_null`), а не запретом состояния.
3. **Checked-наблюдатель над эксклюзивным владением невозможен** без control block; для `unique`
   доступны только scoped borrow (checked по построению) и нативные ссылки (unchecked).
4. **`shared_ptr` → `unique_ptr` невозможно** (у control block нет отвязки): demote `shared`→`unique`
   выполним только переносом **значения** pointee → меняется идентичность объекта и требуется movable `V`.
5. **COW/clone зависит от копируемости pointee**; `use_count()` не является потокобезопасным для COW без
   внешней синхронизации (стандартная оговорка `std::shared_ptr`).
6. **Aliasing на элементы контейнера небезопасен при реаллокации** (control block жив, а указатель на
   элемент может устареть).
7. **Atomic-операции требуют иного lowering** (`load → guard`), поэтому доступны только под
   atomic-backend; публикация ссылки между потоками — не «бесплатная» операция общего вида.
8. **Feature-matrix backend'ов неоднородна**: часть операций (aliasing/intrusive/atomic/
   `shared_from_this`) существует не во всех реализациях → обязательна compile-time диагностика
   неподдерживаемого (AGENTS: без тихого fallback).
9. **Default std-shared backend не даёт intrusive/многого aliasing** (объект должен быть создан через
   `shared_ptr`); собственный control block (L3) — опциональный backend, ценой прямой связи со std.
10. **Нативные (сырые) ссылки** задаются явным атрибутом; смешение нативных и
    умных ссылок, а также осей владения (`shared`↔`unique`) запрещено.
11. **Сильные циклические ссылки запрещены статически** (анализатор `RefCycleHook`); runtime предоставляет лишь
    `Weak` как ручной способ разрыва циклов. Диагностики: `-Wrecursive-shared` (цикл с owning-ребром `shared`
    → refcount-утечка; default error), `-Wrecursive-unique` (взаимное эксклюзивное владение `unique`-указателями
    неконструируемо), `-Wrecursive-value` (цикл по value-вложению/`StaticUnique` → бесконечный размер).
    Self-ссылка `unique`-указателем (`Node` владеет другим `Node`) — легальный owned-список, НЕ цикл.

## 12. Итог

Модель Trust - **один признак ссылки на объявление** (плоский `RefType`) + **цепочки отдельных
ссылочных типов** для вложенности. Это осознанное упрощение ради ясности и безопасности
(сырые виды задаются явным `@[reftype]`). Модель согласована с C/C++ в части
«синтаксические формы - разные типы» и «value/shared/weak/unique ↔ значение и умные указатели»,
но отказывается от совмещения осей в одном объявлении.

На уровне управления памятью модель описана как **набор операций (§8)** над **минимальным набором
видов (§9)**, с **единым синтаксисом и сменными backend'ами (§10)** и явными **ограничениями (§11)**.
Мнемоника эксклюзивного вида — `unique` (C++-тип `trust::Unique`).

## 13. Политики доступа (AccessPolicy): согласованная модель {#access-policy}

> **Статус: РЕАЛИЗОВАНО (только shared/weak).** Ось `Group::kAccessPolicy` объединяет СИНХРОНИЗАЦИЮ
> доступа для `shared`/`weak`: `AccessMutex`/`AccessRwMutex`/`AccessSingleThread` и слот `impl`
> (3-й аргумент `reftype`, композиция `trust::AccessShared<T, Policy, Impl>`; валидация по C++-концепту).
> `unique` МОНОПОЛЕН и политик доступа НЕ имеет: заём/alias запрещён (`& u` — ошибка), только move/swap.
> Историческое имя оси — `Group::kSyncPolicy`; раннее расширение на `unique` (`AccessStatic`/`AccessChecked`)
> УДАЛЕНО.

### 13.1 Идея

Ось **«политика доступа»** задаёт СИНХРОНИЗАЦИЮ доступа к разделяемым данным (`shared`/`weak`).
Владение (`RefType`: value/shared/weak/unique) — **отдельная ось**; `unique` монополен и политик не несёт.

### 13.2 Синтаксис

```
@[reftype( <kind> [, <policy> [, <impl>]] )]   +   @[deleter(<D>)]
```

| Поз. | Роль | Обязательно | Дефолт |
|---|---|---|---|
| 1 | `kind` | **да** | — |
| 2 | `policy` | нет (только shared/weak) | «нет sync» |
| 3 | `impl` | нет (требует явной `policy`) | default-impl политики |
| — | `deleter` (отдельный атрибут) | нет (owning-виды) | нет deleter |

`_` не используется: `deleter` вынесен в отдельный атрибут, поэтому «опционального в середине» в `reftype` нет.

**Таймаут детектора в атрибуте НЕ задаётся.** Это настройка рантайма, а не идентичность типа:
встроенный дефолт `SyncTimeoutDeadlock` (5 s) → `-fsync-deadlock=` (сборка) → `--trust:fsync-deadlock=`/
`--trust:fno-sync-deadlock` (старт программы); при необходимости пер-инстансного значения — **отдельный
impl** (иное поведение = иной тип) либо **аргумент конструктора** `AccessShared(value, timeout)`. Это
освобождает 3-й позиционный слот под `impl` и устраняет прежний конфликт `timeout`/`impl`.

### 13.3 Набор политик

| Policy | Форма | when | guard | thread_scope | exclusive | thread_safe | Стоимость |
|---|---|---|---|---|---|---|---|
| `AccessMutex` | `capture` | runtime | `capture` | multi | да | true | lock/unlock |
| `AccessRwMutex` | `capture` | runtime | `capture` | multi | нет | true | rw-lock |
| `AccessSingleThread` | `capture` | runtime | `capture` | single | нет | false | сравнение thread-id |

Guard доступа — единый `Locker` (policy-agnostic; способ синхронизации — во владельце). У `shared`
есть ESCAPABLE observer-ссылка `SharedBorrowedRef` (обёртка над `weak_ptr`; доступ через `access()`).

### 13.4 Разделение ответственности

- **policy** — семантика, lowering (`guard`), идентичность типа (`TypeKey`), правила анализатора;
- **impl** — C++-класс реализации; проверяется **по концепту** формы политики; **независим** от
  policy (один класс может обслуживать несколько политик);
- анализатор ключуется **по policy** из объявления, а не по классу-реализации.

### 13.5 Статика vs рантайм

- `unique` — монопольное владение БЕЗ заёма: доступ `*u` статически (zero-cost), alias запрещён;
- политики `shared`/`weak` — runtime-механизм синхронизации (`capture`): `Locker` + `Sync*`/`LockRelease`.

### 13.6 Расширяемость

- runtime-политики форм `capture`/`move` — регистрация типа + capability-метаданные → **без перекомпиляции**
  транспилятора;
- compile-time-политики — только с доработкой анализатора;
- новые формы lowering (atomic/txn/rcu) — компиляторный трек (иной lowering).

### 13.7 Историческая справка

Ось называлась `Group::kSyncPolicy` (`SyncMutexPolicy`/`SyncShared`/`resolveSyncPolicy`); переименована в
`kAccessPolicy` (`AccessShared`/`resolveAccessPolicy`). Расширение политик на `unique`
(`AccessStatic`/`AccessChecked`, runtime borrow-guard) реализовывалось, но УДАЛЕНО: монопольное владение
не имеет заёма/alias.

## 14. Модель жизненного цикла: reference- и lifetime-оси {#lifecycle}

Согласование reference-модели (§9, §13) с моделью времени жизни. Вид эксклюзивного владения называется
`unique` (`kBorrowed`→`kUnique`, `trust::Borrowed`→`trust::Unique`); он МОНОПОЛЕН и заёма/alias не имеет.

### 14.1 Ортогональные аспекты (один атрибут на аспект)

| Аспект | Атрибут | Слой | Входит в runtime-идентичность типа |
|---|---|---|---|
| Владение | `@[reftype(<kind>)]` | тип/кодоген | да |
| Доступ/синхронизация | 2-й/3-й аргумент `reftype` | тип/кодоген | да |
| Область жизни (region) | `@[lifetime(<area>[,<name>])]` | анализ (стирается) | нет |
| Разрушение | `@[deleter(D)]` | runtime-действие | да (`unique`); стирается (`shared`) |
| Мутабельность | `@[readonly]`/`^` | символ/pointee | квалификатор pointee |
| Стабильность адреса | `@[pin]` | анализ | не реализован (диагностика при использовании) |

Правила совместимости собраны в единой матрице (`checkQualifierApplicable`, `semantic/ref_kind.hpp`):
`deleter` применим только к владеющим видам (`unique`/`shared`); `lifetime` - только к **невладеющему view**
(Native-ось: `ptr`/`ref`/`rref`/`ptrptr`); `pin` пока не поддержан - использование даёт явную ошибку
(консистентно с `rref`/`ptrptr`). `pin`/`lifetime` регистрируются как built-in (`attr::Pin`/`attr::Lifetime`);
авто-выведенный атрибут помечается `add_attr(..., /*manual=*/false)` (`kAttrManualFlag`), по образцу
`stack_check_infer`. А признак built-in/user выводится из `MapperRange` при регистрации (`AttrPool`).
Квалификаторы (`deleter`/`lifetime`/`pin`) применяются только к объявлениям переменных/параметров; на
**возвращаемом типе функции** они не поддерживаются (кроме `reftype`) и дают явную диагностику.

### 14.2 Контракт `@[lifetime(<area>[, <name>])]`

- `area` (**обязателен**): `self` | `param` | `var` | `named` | `program` | `thread` | `scope` | `_`;
- `name` (опционален): обязателен ⟺ `area ∈ {param, var, named}`, иначе запрещён;
- `_` = «выведи здесь» (элизия для позиции); **отсутствие атрибута** = вывод по умолчанию;
- классы хранения (`static`/`auto`) в синтаксис **не выносятся** (это C-лексика, перегруженная; маппинг
  storage→region см. ниже).

Примеры: `@[lifetime(self)]`, `@[lifetime(param, x)]`, `@[lifetime(var, y)]`, `@[lifetime(named, a)]`,
`@[lifetime(program)]`, `@[lifetime(_)]`.

### 14.3 Storage duration × region

Регион view - это **bound**, а не место хранения; всегда `region(view) ≤ lifetime(anchor)`.

| Хранение / владелец | Выводимый регион |
|---|---|
| Глобал/статик/литерал; код (функции/типы) | `program` (программная длительность) |
| `@[thread_local]` | `thread` |
| Локальная/временная (стек) | текущий блок/вызов (`scope`, дефолт) |
| Heap за `unique`/`shared`-handle | регион **владельца-handle** (не heap) |

`program` валиден только при программно-долговечном anchor (стат. хранение либо постоянно удерживаемый
владелец). Инференс регионов/escape-правила - **отдельный трек** (borrow-checker): задача -
`include/semantic/BORROW_CHECKER.md`.

### 14.4 Что реализовано / вне этого шага

- **Реализовано:** переименование `unique`; регистрация `@[pin]`/`@[lifetime]`; единая матрица
  `checkQualifierApplicable` + валидация контракта `lifetime`; явные диагностики для `@[pin]`
  («не реализован») и для квалификаторов на возвращаемом типе функции.
- **Реализовано (доп., runtime):** ESCAPABLE observer-заём — `Shared::borrow()/borrow_const()` →
  `SharedBorrowedRef` (weak observer); доступ только через `access()` с re-check; инвалидация при
  гибели последнего владельца. `unique` observer-заёма НЕ имеет (монопольное владение).
- **Реализовано (доп., v1 borrow-checker):** статический анализатор `BorrowCheckHook` (всегда
  подключён; настраиваются только уровни `-Wborrow-<name>`): per-frame регионы из `Storage`, правила
  R1/R4/R5/R6, диагностики
  `borrow-region-mismatch`/`borrow-owner-moved`/`borrow-owner-mutated`/`borrow-static-unproven`.
  Спецификация - `include/semantic/BORROW_CHECKER.md`.
- **Отдельная ветка:** escape-правила return, запрет move/copy для `pin`, взаимодействие с
  ООП (методы/поля-view), корутинами (borrow через точку приостановки, self-referential фреймы),
  межпроцедурный анализ; элизия runtime-токена (смена политики доступа) - вне v1.


## 15. Нотация ссылок: локальная зона и граница API

Нотация вида ссылки разделена на две зоны с разными правилами:

| Зона | Разрешено | Запрещено |
|------|-----------|-----------|
| **Локально** (внутри модуля) | короткие маркеры `&&`/`&*`/`&?`, операторы `&`/`&^`/`*`/`*^`, авто-вывод через `:=` | — |
| **API** (экспортируемые имена: переменные, функции, поля) | только явный `@[reftype("...", policy, impl)]` (+ `@[deleter]`/`@[lifetime]`/`@[readonly]`) | короткие УМНЫЕ маркеры `&&`/`&*`/`&?` (нативные `ptr`/`ref` — только явный `@[reftype(...)]`) |

### 15.1 Короткие маркеры (локальная зона)

| Маркер | Вид | Мнемоника |
|--------|-----|-----------|
| `&&` | `unique` | удвоение = эксклюзивное владение («держу сам») |
| `&*` | `shared` | `*` = «много» владельцев |
| `&?` | `weak` | `?` = «может истечь» (наблюдатель) |
| авто | выводится | при опущенном типе (`:=`) |

### 15.2 Операторы (выражения)

| Оператор | Смысл |
|----------|-------|
| `&` | создать ссылку: заём (borrow) из `&&`, weak из `&*`. Из значения - ошибка |
| `&^` | const-ссылка (только чтение цели) |
| `*` / `*^` | доступ / const-доступ к значению |
| `:=:` | move/swap |

`borrow` как вид ссылки УДАЛЁН (`RefType::kBorrow`): заём `&` у монопольного `unique` ЗАПРЕЩЁН
(`& u` → ошибка «cannot take a reference to a monopolistic 'unique' owner»). `unique` — только move/swap.
Оператор `&` определён для `shared` (→ weak-наблюдатель). Зависимости данных (view-объекты) отслеживает
атрибут `@[borrowed]`.

### 15.2.1 Форма владельца `unique` (заёма НЕТ)

`unique` — монопольное владение; заём/alias отсутствуют.

| Сущность | C++ | Как получается |
|---|---|---|
| владелец `unique` | `trust::StaticUnique<T>` (inline, zero-cost) | `&& u := ...` / `u : @[reftype("unique")]` |
| владелец `unique` + `@[deleter(D)]` | `trust::Unique<T, D>` | атрибут `@[deleter]` |

```trust
u : @[reftype("unique")@] Int32 := 5;    # владелец: trust::StaticUnique<int32_t>
*u = 7;                                  # доступ к значению (не alias)
@swap(u, x);                             # обмен владением
b := & u;                                # ОШИБКА: заём монопольного unique запрещён
```

### 15.3 Два независимых канона константности

| | цель const (через ссылку) | цель mutable |
|---|---|---|
| **привязка const** (`^` на имени) | read-only вид; перепривязка запрещена | mutable вид; перепривязка запрещена |
| **привязка mutable** | read-only вид; **перепривязка разрешена** | mutable вид; перепривязка разрешена |

- `^` на имени = константность ПЕРЕМЕННОЙ (нельзя перепривязать/переместить); запись по хранимой
  не-const ссылке разрешена.
- const-ссылка (`&^`/`*^`) = константность ЦЕЛИ (запись через неё запрещена, кодогенерация -
  read-only захват); саму переменную перепривязать можно.
- Анализатор должен проверять оба канона НЕЗАВИСИМО, включая сочетание с move-only `unique`.

### 15.4 Реализация

- Различение «короткий маркер vs явный `@[reftype]`»: маркер ПЕРЕД именем конвертируется в атрибут
  `@[reftype]` с `manual=false` (`term_to_ast`), а явный атрибут имеет `manual=true`; вид-маркер В
  АННОТАЦИИ ТИПА распознаётся `refKindOfTypeNode` (тип-узел RefMakeExpr/RefTakeExpr).
- Правило границы API проверяется в `DeclAnalyzer`: не-локальная переменная (`!isInLocalScope`),
  тип параметра функции и возвращаемый тип функции при коротком УМНОМ маркере выдают
  `Severity::Error`. Локальный скоуп правило не затрагивает.
- **Lowering `unique`** (`TypeRegistry::getCppTypeName`, единый источник `types/ref_type.hpp`):
  без deleter'а → `trust::StaticUnique<T>` (значение INLINE: без heap/refcount, `sizeof == sizeof(T)`,
  move-only; уникальность/перемещение обеспечивает АНАЛИЗАТОР); с `@[deleter(D)]` → `trust::Unique<T, D>`
  (указательная обёртка, RAII-деструктор). Дереференс `*u`: StaticUnique → `(u.get())`; с deleter'ом →
  `trust::checked_deref(u.get())`. Форму доступа РЕШАЕТ анализатор (`RefTakeExpr::m_lowering`:
  Direct/StaticUnique/UniqueDirect/SharedLocked, `src/semantic/ref_expr_typer.cpp`); кодоген — буквальный
  `switch` по нему, без обращения к таблице символов.

### 15.5 Нативные ссылки

Нативные (сырые C++) виды `ptr`/`ref` совместимости с C/C++ задаются явным `@[reftype("ptr"|"ref")]`.
Виды `rref`/`ptrptr` зарезервированы и не реализованы.
